# GTD4Teams · 单服务器零停机发布方案

> 版本：v1（2026-09-28）
> 适用：一台 Linux 服务器（Ubuntu 已验），已装 Docker；SQLite 单文件存储；单实例部署
> 配套脚本：`deploy/` 目录；相关文档：[Docker部署方案.md](Docker部署方案.md)

---

## 0. 结论先行

| 项 | 做法 | 效果 |
|---|---|---|
| 拓扑 | 双槽位（`app-blue` / `app-green`）+ Caddy 唯一入口 | 同一时刻一个槽位服务，另一个作为发布目标 |
| 切流 | 重写 Caddy 上游顺序 + `caddy reload` | 平滑重载，**不断连接** |
| 校对 | `/api/health` 回传的构建标识 | 拦住"端口通了但跑的还是上一版" |
| 发布 | `sudo bash deploy/release.sh` | 用户无感，通常 20~40 秒完成 |
| 回滚 | `sudo bash deploy/rollback.sh` | 同样零停机；状态互换，可回滚掉回滚 |
| 证明 | 切流窗口内并发打流 | **用数据证明没断线**，而不是声称没断线 |

一句话概括：**新版本先在旁边跑到确认可用，再把流量挪过去。**

## 1. 为什么不能靠"重启容器"换版本

单容器部署时，最自然的升级方式是：

```bash
docker compose up -d --build     # ← 这一步会先销毁旧容器，再创建新容器
```

这一条命令里，服务不可用的时间 = 旧容器停止 + 新容器启动 + 应用初始化 + 健康检查通过。
实测这个量级在 3~15 秒，而且**取决于新版本启动有多快** —— 版本越重，窗口越长。
更麻烦的是它无法预告：如果新版本启动就崩，你会先失去服务，再收到错误。

零停机的本质要求是：**新版本在承载流量之前就已经被验证过可用**。
这就要求同一时刻存在两个可以互相替换的运行单元 —— 这就是双槽位。

## 2. 架构

```
                         ┌─────────────────────────────┐
   公网 80 / 443 ──────► │  caddy（唯一入口，常驻）      │
                         │  · 自动 HTTPS / 证书续期      │
                         │  · 上游顺序 = 优先级          │
                         │  · 主动健康检查 /api/health   │
                         └──────────────┬──────────────┘
                                        │  lb_policy first
                          ┌─────────────┴─────────────┐
                          ▼                           ▼
                 ┌──────────────────┐        ┌──────────────────┐
                 │  app-blue        │        │  app-green       │
                 │  127.0.0.1:8788  │        │  127.0.0.1:8789  │
                 │  （只绑回环）      │        │  （只绑回环）      │
                 └────────┬─────────┘        └─────────┬────────┘
                          └────────────┬───────────────┘
                                       ▼
                            ┌─────────────────────┐
                            │  gtd-data 卷         │
                            │  gtd4teams.db (WAL)  │
                            └─────────────────────┘
```

三个要点，每一个都对应一处刻意的设计：

1. **槽位端口只绑 `127.0.0.1`**。这个端口是给宿主机上的健康检查与冒烟测试用的，
   不是对外入口。对外入口只有 Caddy 一个 —— 少了第二条入口，也就少了第二个需要
   收紧的暴露面。
2. **两个槽位挂同一个数据卷**。数据只有一份，切换不涉及任何数据搬运，
   所以"切换"这件事本身没有数据风险。（前提见 §2.2。）
3. **上游顺序即优先级**。`lb_policy first` 让流量全部走第一个可用上游；
   发布就是"把新槽位写到第一位"，回滚就是写回去。

### 2.1 为什么切流要用 `caddy reload` 而不是重启 Caddy

`docker compose up -d caddy` 会销毁并重建容器 —— 正在传输的请求全部被切断，
那和重启应用容器没有区别。

`caddy reload` 是**平滑重载**：新配置由新进程组接管新请求，已经在处理的连接由旧配置
继续收尾。HTTP keep-alive 连接不会被重置。

并且 `caddy_reload()` 在重载前会先 `caddy validate`。**校验不通过就原地放弃** ——
线上仍是旧配置，服务完全不受影响。这条纪律让"配置写错"的最坏后果从"服务挂了"
变成"这次发布没做"。

### 2.2 为什么两个进程能共用一个 SQLite 文件（这一条被实测验证过）

SQLite 是单写者模型，直觉上"两个进程写一个库"很危险。它能成立靠三件事：

1. `pyapp/db.py` 的每个连接都开 **WAL**（`journal_mode = WAL`）：读不阻塞写。
2. **`busy_timeout = 15000`**：写与写之间排队等待，而不是立刻失败。
3. 应用层两道额外的兜底（本次为支持蓝绿而补，见 §2.4）。

`tests/test_zerodowntime.py` 把这件事变成了可复跑的断言，而不是推理：

```
两个进程同时读写同一个库文件
  · 并发写入 40 次（两个进程各 20 次）零失败
  · 一边写入的内容，另一边立刻读得到（不是各自缓存了一份）
  · 在 A 上建立的会话在 B 上同样有效（切流不会把用户登出）
  · 两个版本回传的构建标识能区分
  · 服务端日志里没有锁冲突、没有异常栈
```

**发布前请在服务器上跑一次**：

```bash
python3 tests/test_zerodowntime.py
```

它同时验证了 `smoke.sh` / `probe.sh` 这两个发布脚本的行为（放行与拦截都对），
所以它既是一次平台验证，也是一次发布工具的自检。

### 2.3 为什么 Caddy 必须"覆盖"而不是"追加" X-Forwarded-For

`GTD_TRUST_PROXY=1` 时后端会采信 `X-Forwarded-For` 的第一个值作为客户端 IP，
登录限流按这个值计数。而 Caddy 默认行为是**追加**到客户端传来的 XFF 后面：

```
客户端伪造:  X-Forwarded-For: 1.2.3.4        ← 攻击者每次换一个
Caddy 追加后: X-Forwarded-For: 1.2.3.4, <真实IP>
后端取第一个: 1.2.3.4                          ← 限流键被攻击者按需更换 ✗
```

因此 `deploy/Caddyfile.template` 里显式改写：

```
header_up X-Forwarded-For {http.request.remote.host}
header_up X-Forwarded-Proto {http.request.scheme}
```

这样后端拿到的永远是**本次 TCP 连接的真实来源地址**，伪造的头部在入口处被丢弃。
`GTD_TRUST_PROXY=1` 能成立，前提是这一条 + 槽位端口不对外，两条缺一不可。

### 2.4 为支持蓝绿而在代码里补的两处（都是实测发现的真缺陷）

**(1) 启动时不再无条件重跑 DDL —— `pyapp/db.py`**

原实现每次启动都执行整份建表脚本。蓝绿场景下新槽位正是在**旧槽位还在写入时**启动的，
于是两个进程抢写锁，`executescript` 直接失败：

```
sqlite3.OperationalError: attempt to write a readonly database
```

表现是"新槽位起不来"，而原因看起来像是数据库变成只读了 —— 排查方向会被完全带偏。
**这不是理论问题：只要某次发布带了新字段或新表，就必然踩中。**

修法是两条：

- `schema_present()` 先做一次只读检查，结构已建全就直接返回，**完全不产生写入**
  （绝大多数启动都是这种情况）；
- 真正需要建表时带退避重试（约 0.25s 起线性退避，总计数秒）。

**(2) 读路径不再每次都写 —— `pyapp/httpd.py`**

原实现每个已认证请求都会 `UPDATE sessions SET last_seen_at`。也就是说**所有读取操作
都会顺手抢一次写锁**。单进程时只是慢一点；蓝绿切换期间这会让纯读取的流量也卷进写冲突。

修法：活跃时间按 300 秒节流；且刷新失败**只当记账失败**，绝不让请求变成 500。

顺带把写锁争用统一兜住：`_dispatch` 在异常是写锁争用、且响应尚未开始写时，
会回滚连接并重试（指数退避，最多 6 次）。重试之所以安全，是因为每个请求一个连接，
处理器抛异常时连接被关闭，**未提交的事务随之丢弃** —— 要么整体生效，要么完全没发生。

> 反直觉的一点：Linux 上写锁争用报 `SQLITE_BUSY`，`busy_timeout` 会自动等待；
> **Windows 上同样的争用报 `SQLITE_READONLY`，而 busy_timeout 不处理这个错误码**。
> 既然"两个进程共用一个库"是这套方案的地基，就不能把它寄托在操作系统的差异上 ——
> 所以应用层统一兜住，两种平台行为一致。

## 3. 测试门禁：五层，各拦一类问题

发布不是"构建 → 上线"，而是**五道闸门依次通过，任何一道不过就停在原地**。

| 层 | 跑在哪 | 命令 | 拦住什么 |
|---|---|---|---|
| L0 后端接口 | 构建机（需要 python3） | `python3 tests/test_api.py`（49 项） | 权限、越权、字段白名单、类型往返、目录穿越、备份还原 |
| L1 前端冒烟 | 构建机（需要 node） | `.smoke/*.mjs`（80 + 65 + 46 项） | 渲染缺陷、认证流程、真实 index.html 的启动与交互 |
| L2 镜像自检 | **构建过程中** | Dockerfile 里的 `RUN` | 缺文件、模块名写错、循环导入、语法错 —— 让"构建成功"本身等价于一次冒烟 |
| L3 新槽位冒烟 | 服务器，新槽位启动后 | `deploy/smoke.sh` | 构建标识不符、模块图缺失、暴露面泄漏、鉴权边界失守 |
| L4 连续性探测 | 服务器，切流窗口内 | `deploy/probe.sh` | **切换真的断了线**（失败数 > 0 或出现秒级空档） |

L0/L1 在**代码上传到服务器之前**就该跑过。服务器上不一定装 node，所以 `release.sh`
的测试门禁是"能跑就跑"，跑不了会明确告警 —— 判定发布是否合格的依据是 L2/L3/L4
这三道**在服务器上必然执行**的门禁，以及构建机上的 L0/L1。

### L3 冒烟测试检查什么

`deploy/smoke.sh <url> <期望构建标识>` 的五组检查：

1. **服务健康**：`/api/health` 返回 200，且 `build` 等于本次构建标识
2. **前端可加载**：`index.html` 不引用任何外部脚本；**顺着 import 把整张模块图走一遍，
   每个模块都要 200，且所有 `?v=` 版本串一致**（能抓到"引用了没打进镜像的模块"）
3. **暴露面**：19 个受限路径必须 404 —— 含 `/server.py`、`/pyapp/*.py`、`/tests/*`、
   `/data/gtd4teams.db`、`.env`，以及 `/js/../server.py` 这类目录穿越写法
4. **鉴权边界**：未登录读、未登录写、跨站写，全部必须被拒
5. **带认证的端到端**（可选）：给了 `SMOKE_EMAIL` / `SMOKE_PASSWORD` 就真的登录一次并读一遍工作区

> 第 3 组里有一条容易写错的细节：**curl 默认会规范化 URL 路径里的 `..`**。
> 不加 `--path-as-is`，"目录穿越被拦住"这条检查就是假的 —— 请求根本没带着 `..` 发出去。
> 脚本里已显式关掉这个行为。

### L4 用打流证明"不断线"

`deploy/probe.sh` 在切流窗口内持续请求**公网入口**（也就是 Caddy 那条路），
输出三个数：总请求数、失败数、**连续成功之间的最大间隔**。

最后那个数才是"是否断线"的真正度量：

```
总请求 178 次  ·  成功 178  ·  失败 0  ·  用时 34.9 秒
连续成功之间的最大间隔：214 毫秒
[ ok ] 全程 178 次请求零失败，最大空档 214 毫秒：未断线。
```

出现失败请求，或最大间隔到秒级，就说明切换窗口里确实丢了请求 ——
`release.sh` 会以退出码 3 结束并提示可以立刻回滚。

## 4. 发布时序

`sudo bash deploy/release.sh` 依次做这些事（任何一步失败都停在那里）：

| # | 步骤 | 此刻线上是谁在服务 | 失败了会怎样 |
|---|---|---|---|
| 0 | 预检：docker、`.env`、`docker compose config -q` | 旧版本（正常） | 什么都没发生 |
| 1 | 测试门禁 L0/L1（能跑就跑） | 旧版本 | 什么都没发生 |
| 2 | 发布前自动备份 | 旧版本 | 中止（没有退路的发布不值得冒险） |
| 3 | 构建镜像（构建标识 = 镜像标签） | 旧版本 | 中止；构建自检失败通常是代码问题 |
| 4 | 启动**另一个**槽位，等待 healthy | 旧版本 | 新槽位停掉即可，线上没动过 |
| 5 | 校验构建标识 + 冒烟测试（直连新槽位） | 旧版本 | **不切流**，线上没动过 |
| 6 | 开始并发打流 | 旧版本 | — |
| 7 | 重写 Caddy 上游顺序 + `caddy reload` | **切到新版本** | 校验不过则放弃切流，线上没动过 |
| 8 | 引流窗口（默认 20 秒） | 新版本；旧版本仍在跑 | 新版本若挂，Caddy 会自动退回旧槽位 |
| 9 | 停掉旧槽位 | 新版本 | — |
| 10 | 汇总打流结果、写状态、清理旧镜像 | 新版本 | — |

### 关键设计：为什么第 8 步不立刻停旧槽位

引流窗口内旧槽位仍在运行，作用是两件事：

1. **收尾在途请求**。切流那一刻可能还有请求正由旧槽位处理，停掉它会直接切断。
2. **兜底**。Caddy 的上游列表里两个槽位都在，`lb_policy first` 只走第一个；
   万一新版本切过去之后立刻出问题，Caddy 的主动健康检查（3 秒一次）会把它摘除，
   流量自动退回旧槽位 —— **不需要任何人介入**。

### 关于构建标识

镜像标签就是构建标识，形如 `gtd4teams:20260928-153012-a1b2c3d`（时间戳 + 短提交）。
它在构建时通过 `--build-arg GTD_BUILD=...` 写进镜像，运行时由 `/api/health` 回传。

为什么需要它：**容器健康不代表内容正确**。旧容器同样健康、同样占着端口 ——
只看"端口通了"会把"发布成功"变成一句自我感觉良好的话。发布脚本比较的是
"新槽位回传的 build 是否等于本次构建的标识"，对不上就不切流。

## 5. 回滚

```bash
sudo bash deploy/rollback.sh
```

做的是发布流程的后半段，唯一区别是**不重新构建**：直接拿上一次保留下来的镜像标签，
把另一个槽位起起来、冒烟核对（期望的构建标识就是那个旧标签）、切流、引流、停新槽位。
通常十几秒完成，比修 bug 再发一版快得多。

- 回滚前会自动备份（`--no-backup` 可跳过）。
- 回滚后**状态互换**，所以"回滚掉这次回滚"就是再执行一次 `rollback.sh`。
- 回滚目标镜像必须还在本地。`release.sh` 默认保留最近 5 个镜像（且强制最少保留 2 个 =
  当前版 + 上一版），正是为了这一刻；`--keep` 可以调，但别调到 1。
- 想看看本地还留着哪些：`sudo bash deploy/rollback.sh --list`。

## 6. 库结构变更的兼容纪律（重要）

蓝绿切换期间，**新旧两版的代码会同时存在**，它们共用一个库。由此产生一条硬约束：

> **一次发布只能做"加法"（expand），不能做破坏性的结构变更。**

| 变更类型 | 能否直接发 | 说明 |
|---|---|---|
| 新增表 | ✅ | 新版本启动时建出来，旧版本完全不感知 |
| 新增列（可空或带默认值） | ✅ | 旧版本的 `SELECT *` 会多拿到一列，但它不消费它 |
| 新增索引 | ✅ | 对旧版本无影响 |
| 删除列 / 改列名 | ❌ | 旧版本会立刻报错 |
| 改列语义（同名列，含义变了） | ❌ | 最危险：两个版本对同一列的解读不同 |
| `NOT NULL` 且无默认值的新列 | ❌ | 旧版本写入的行会违反约束 |

**破坏性变更要走三步两发布**（expand → migrate → contract）：

1. 第一次发布：加新列/新表，**两版代码都兼容**；
2. 数据迁移（可用 `--export` / `--import` 或直接跑一条 SQL）；
3. 确认新版本稳定后，第二次发布才删掉旧列。

如果确实需要一次性完成破坏性变更，用逃生口：

```bash
sudo bash deploy/release.sh --stop-first
```

它会先停旧槽位再起新槽位 —— 这会带来**一次设计中允许的短暂中断**（几秒），
换来"任何时刻只有一个版本在读写这个库"。这是唯一需要牺牲零停机的场景，
而且是有意识的取舍，不是意外。

## 7. 调度与自愈

单服务器没有编排系统，可用性靠这几层叠加：

| 层 | 手段 | 覆盖什么 |
|---|---|---|
| 进程 | `restart: unless-stopped` | 进程崩溃、OOM、宿主机重启 |
| 容器 | `healthcheck`（15s 一次，探 `/api/health`） | 进程活着但服务不工作 |
| 守护进程 | Docker 的 `live-restore` | **Docker 自身升级/重启时容器不被停掉** |
| 应用 | `deploy/watchdog.sh` + cron | 容器反复不健康、被人手工停掉 |
| 数据 | `deploy/backup.sh` + cron | 误操作、库损坏 |
| 发布 | 引流窗口 + 上游兜底 | 新版本切过去之后立刻出问题 |

### 开启 `live-restore`

单服务器上这一条性价比很高 —— 它让 Docker 守护进程重启（比如升级 docker）时容器继续运行：

```json
// /etc/docker/daemon.json
{
  "live-restore": true,
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" }
}
```

改完 `systemctl restart docker`。

### 看门狗（可选）

```bash
crontab -e
* * * * * cd /opt/gtd4teams && bash deploy/watchdog.sh >> /var/log/gtd4teams-watchdog.log 2>&1
```

处置是逐级的，不会一上来就大动作：

- 连续 3 次不健康 → 重启该槽位；
- 连续 8 次不健康 → 若 `GTD_WATCHDOG_FAILOVER=1` 则切回上一版，**否则只告警**。

默认不自动降级是有意的：自动降级若悄悄发生，第二天没人说得清线上跑的是哪一版。

### 备份调度

```bash
crontab -e
30 3 * * * cd /opt/gtd4teams && bash deploy/backup.sh >> /var/log/gtd4teams-backup.log 2>&1
```

备份用应用自带的 `--export` 走正常读连接，拿到的一定是一致性快照。
**不要直接 `cp` 那个 `.db` 文件** —— WAL 模式下只拷 `.db` 而漏掉 `-wal`，拿到的是旧数据。
默认保留 14 份，落在 `/var/backups/gtd4teams`，权限 600（含口令散列）。

恢复见 [Docker部署方案.md](Docker部署方案.md) 的「备份与恢复」一节，
注意那里写清了 `--import` 是 **INSERT OR REPLACE**（不清空、不合并去重）这个语义陷阱。

## 8. 首次部署

### 8.1 上传代码（在你的本机执行）

```bash
bash deploy/push.sh root@你的服务器IP
```

用 tar 走 ssh 管道，不依赖 rsync。排除清单里最关键的两项是本机 `data/`
（含本机账号与口令散列，不该上去）和 `deploy/run/`（运行期状态，线上要自己长出来）。

### 8.2 服务器上部署

```bash
ssh root@你的服务器IP
cd /opt/gtd4teams
sudo bash deploy/install.sh
```

`install.sh` 会：校验环境 → 生成 `.env`（含随机注册口令）→ 生成并校验 Caddy 配置 →
构建镜像 → 起蓝槽位与 Caddy → 等健康 → 冒烟验证 → 记录状态 → 打印访问地址与安全提示。

### 8.3 部署后必做的两件事

**(1) 在服务器上跑一遍平台验证**（这是本方案唯一"必须在目标平台确认"的事项）：

```bash
cd /opt/gtd4teams
python3 tests/test_zerodowntime.py
```

全绿 → 双槽位共用数据库的前提在你这台机器上成立，`release.sh` 可以放心用。
不绿 → 先用 `release.sh --stop-first` 发布（仍是受控的几秒切换），并把失败信息反馈回来。

**(2) 云厂商安全组只放行 80 与 443**

槽位端口（8788/8789）只绑在回环上，**不需要也不应该**对公网放行。

### 8.4 域名与 HTTPS

`.env` 里填 `GTD_DOMAIN=你的域名`（A 记录先指向本机公网 IP），然后让 Caddy 重新读取配置：

```bash
docker compose up -d caddy     # Caddy 是入口容器，重启它不影响正在服务的槽位
```

Caddy 会自动申请并续期证书。**没有域名时是明文 HTTP**：登录口令会明文过网，
仅建议内网使用 —— 这一点在 `install.sh` 结束时也会提醒。

## 9. 日常运维速查

```bash
sudo bash deploy/release.sh --status          # 现在哪个槽位在跑、镜像是哪个、上一版是什么
docker compose logs -f app-blue caddy         # 跟日志

sudo bash deploy/release.sh --drain 60        # 引流窗口给到 60 秒
sudo bash deploy/rollback.sh                  # 回滚
sudo bash deploy/rollback.sh --list           # 本地保留的镜像

docker compose exec app-blue python server.py --check   # 看库结构与计数
docker compose exec app-blue python server.py --set-password 某人@example.com
```

想排查"到底是哪一层的问题"，可以直接访问槽位端口（只在本机）：

```bash
curl -s http://127.0.0.1:8788/api/health      # 绕开 Caddy，直接问槽位
curl -s http://127.0.0.1:8788/ | head -20
```

## 10. 故障排查

| 现象 | 大概率原因 | 怎么办 |
|---|---|---|
| 发布时"新槽位未在 120 秒内 healthy" | 新版本自身启动失败；或 `data/` 卷权限不对 | `docker compose logs --tail 60 app-green` 看栈；确认卷可写 |
| 发布时"构建标识与本次发布一致"这一项失败 | 槽位被旧容器占着（`up` 没重建） | 删掉该槽位容器再发：`docker compose rm -sf app-green` |
| 发布时"冒烟测试未通过" | 新版本真的有问题，或暴露面检查抓到新增泄漏路径 | 脚本会打印具体是哪几项；**没有切流，线上没动过** |
| 切流报"Caddy 配置校验未通过" | 模板或生成逻辑有问题 | 产物在 `deploy/run/Caddyfile`，对照 `deploy/Caddyfile.template`；旧配置仍在生效 |
| `deploy/run/Caddyfile` 变成了目录 | 首次 `up` 时该文件还不存在，docker 建了同名目录 | `rm -rf deploy/run/Caddyfile` 后重跑 `install.sh` |
| 连续性探测报告有失败请求 | 切流窗口内丢了请求 | `release.sh` 退出码 3；可立即 `rollback.sh`；看 Caddy 是否真热加载成功 |
| 所有人被算成同一个 IP，登录限流误伤 | `GTD_TRUST_PROXY` 被改成了 0 | 改回 1（前提：槽位端口只绑回环） |
| 日志里出现 `attempt to write a readonly database` | 两个进程真的在并发写（不该发生） | `--status` 看是不是两个槽位都起来了；只保留一个 |
| Caddy 起不来但报错看不懂 | 80/443 被占用 | `ss -ltnp | grep -E ':(80|443)'`；或改 `.env` 的 `GTD_HTTP_PORT` |
| 证书申请失败 | 域名未解析到本机 / 80 端口未放行 | 先确认 `curl -I http://你的域名` 能到本机 |

## 11. 已验证 / 尚未验证（如实清单）

**已在开发机验证（可复跑）**

- 后端接口测试 49 项、零停机前提测试 9 项、前端冒烟 80 + 65 + 46 项，全部通过
- 两个进程共用一个 SQLite 文件：并发写入零失败、数据互见、会话跨进程有效、日志无异常
- `smoke.sh` 对正确构建放行、对错误构建拦截；`probe.sh` 报告零失败
- `deploy/Caddyfile.template` 两种模式（有域名 / 无域名）的生成结果与断言全部通过
- `docker-compose.yml` 的结构断言通过（锚点复用、槽位端口只绑回环、Caddy 常驻等）
- Dockerfile 的 `COPY` 源存在性、`HEALTHCHECK` 命令退出码为 0

**尚未验证 —— 第一次在服务器上执行时请留意**

- **镜像构建本身**：开发机上没有 docker，`docker build` 从未实际跑过。
  第 3 步失败的常见原因是拉不到 `python:3.13-slim`（网络），
  可配 `registry.m.daocloud.io` 之类的镜像加速。
- **`docker compose config` 的最终解析**：已作为 `install.sh`/`release.sh` 的预检，
  由 compose 自己校验（本机的结构断言只是辅助）。
- **Caddy 指令的实际行为**：`lb_policy first`、`health_uri` 等为 Caddy 2.x 标准指令，
  但未在本机实跑。`caddy_reload()` 会先 `caddy validate` 再重载，
  所以即便写错也只会**阻止切流**，不会造成停机。
- **Linux 上的写锁争用行为**：预期比 Windows 更宽松（报 `SQLITE_BUSY` 而非
  `SQLITE_READONLY`，`busy_timeout` 会自动等待），且应用层已有统一兜底。
  `tests/test_zerodowntime.py` 就是用来在目标平台上确认这一点的。
