`npm run lint / typecheck / test / build`、`mysql < sql/database.sql`、`执行迁移 SQL 前先在测试库验证`。
**这些命令对本项目不适用（N/A），不得照抄进验收单**：

| 通用模板命令 | 本项目实情 | 替代命令 |
|---|---|---|
| `npm run lint / typecheck / build` | 原生 ESM 前端，**无构建链、无 npm scripts、无 Node 运行时依赖** | `node .smoke/*.mjs`（三套冒烟） |
| `npm run test` | 后端是 Python 3 标准库单体 | `python tests/test_api.py`、`python tests/test_zerodowntime.py` |
| `mysql < sql/database.sql` | 数据库是 **SQLite 单文件**，无 MySQL、无独立 `sql/` 目录 | `python server.py --check`（建库幂等 + 字段规格断言） |
| 「执行迁移 SQL 前先在测试库验证」 | 无独立迁移框架，靠 `pyapp/db.py` 的 `schema_present()` + 退避重试；破坏性变更走 expand/contract 三次发布 | `python tests/test_api.py`（含「字段规格必须等于 `PRAGMA table_info`」「建库幂等」两条防漂移断言）+ `python tests/test_zerodowntime.py` |

### 0.4 勾选与状态约定（各阶段验收单通用）

- 每张验收单**结论列**用 Markdown 复选框：默认 `- [ ] 待办`；判定通过改为 `- [x] 通过`；判定阻塞改为 `- [x] 阻塞` 并在该节「阻塞项登记」写明编号与原因。
- 结论三态：**待办 / 通过 / 阻塞**；另设 **豁免**（仅 G4/G6 可用，必须写理由 + 放行人签字，且不得豁免 G5 安全阻塞项）。
- 判定标准一律写成「可检查、可判通过或不通过」的句式，**禁止**「基本完成」「看起来没问题」。
- 勾选即表示「已核对该项的证据形式」，不是「听说过」。勾选人须在签字位留名。

依据 `docs/零停机发布方案.md` §3，并按总纲 §4 的命名补入 **L0b**（9 项零停机平台前提验证）：

| **L2** 镜像自检 | **构建过程中** | Dockerfile 的 `RUN`：import 全模块 + `server.py --check` | 缺文件、模块名写错、循环导入、语法错 | 构建成功即等价于一次冒烟 | 构建中止；`release.sh` 第 3 步。**【未验证】本机无 docker，`docker build` 从未实跑** |

> L0/L1 在代码上传服务器**之前**跑过。服务器上不一定装 node，故 `release.sh` 的测试门禁是「能跑就跑」，跑不了会明确告警；判定发布是否合格的依据是 **L2/L3/L4（服务器上必然执行）+ 构建机 L0/L1 + 服务器 L0b**。
> 总纲 §4 的 G4 摘要写作「L0 49 项、L0b 9 项、L1 80/65/46 项全绿」，与本节一致。

**v1.1 门禁强度提示（本次治理期实测，详见 §2.2）**：以下四点说明「该层通过」不等于「该类风险已排除」，判定放行时须同时核对 §7 补测任务状态。

| 层 | 既有断言的实际边界 | 已被实证漏掉的问题 |
|---|---|---|
| L0（49 项） | 断言「客户端看到的成功」，**不断言导出范围 / 角色变更范围 / commit 后重试的库内状态** | 3 个后端 P0：导出泄露面、`admin` 改 `role`、重试产生重复行 |
| L0b（9 项） | 验证「两进程共库」地基，**不验证 `_dispatch` 重试的幂等性** | commit 后抛锁 → 客户端 `rows=1` 而库里 2 行；注册部分提交返回 409 `EMAIL_EXISTS`；`/api/logs` 的 `bump_counter` 被放大成 2 |
| L1（191 项） | 断言是**单向**的（有 `case` 就测 `case`、有视图就渲染视图），**缺「视图 `data-action` 集合 ↔ dispatch `case` 集合」双向差集断言** | `submit-password` 断链：后端链路齐全、UI 从不渲染 `#pwd-form`，46 项全绿仍漏掉 |
| L3（`smoke.sh` 第 2 组） | 只把模块 `?v=` **去重为 1**，**未纳入** `js/config.js:170` 与 `pyapp/__init__.py:20` 两个 `APP_VERSION`；正则 `\./[A-Za-z0-9._-]+\.js\?v=` 不含 `/`，按子目录拆分模块会静默漏检 | 版本串四处不同步仍可能放行（IMP-02 / §7） |
| **L3 发布路径（v1.2）** | ~~`install.sh` 冒烟失败只 `warn`，随后仍 `save_state`~~ → **已修复（2026-11-16 核实）**：`install.sh` **第 6 节「冒烟验证」**失败时 `die '未通过冒烟门禁，部署中止。'`（`exit 1`），`save_state` 与「部署完成」横幅都在其后 —— 失败**不会**写 `state.env` | 原漏检：暴露面 / 鉴权检查失败仍被记为成功部署（M1 / §0.2.3）；**现状已被阻断**。残余：`die` 不指明具体 ✗ 项，仍需人工读 `smoke.sh` 的五组明细 |
| **L4（v1.2）** | `probe.sh:101-104` 对 `MAX_GAP_MS > 3000` 只告警并 `exit 0`；`release.sh:311/313/341` 的 `PROBE_OK` 只看退出码 | 「零失败但秒级空档」被判成功（M2 / §0.2.3） |
| **L0/L0b/L1 执行证据（v1.2）** | `release.sh:130/144` 缺工具只 `warn` 跳过；`test_zerodowntime.py:263~285` 四项 `@skipUnless(BASH and CURL)` | 「发布完成」不等于「测试真跑过 / 9 项都跑了」（M3 / M4 / §0.2.3） |

> **共同根因**：现有断言验证的是「**我以为会发生的那一条路径成功了**」，不验证「**不该发生的另外那些路径没发生**」—— 范围、契约、语义、双向集合。**前端与后端是同一类结构性缺口，不是两个孤立 bug**（主理人要求点明）。
> **v1.2 延伸到门禁层**：发布脚本验证的是「**我预期会失败的那种失败**」（`FAILED > 0`、冒烟脚本返回非零），不验证「**另一种不合格但没触发退出码的情形**」（空档超标、冒烟 warn 后继续、用例被 skip、测试被跳过）。因此 **L3/L4 的 `exit 0` 只是必要条件，不是放行充分条件**；补充判据见 §3 的 G4-Sxx / G6-Sxx。

| 层 | 执行者（总纲 §6 RACI） | 触发时机 | 通过标准 | 失败卡点 / 处置 |
|---|---|---|---|---|
| L0 | 测试角色（AI 协作体）+ 开发 | 每次代码改动、每次发布前 | 49 项全绿 | 不上传代码；缺陷进 §5 流程 |

| L1 | 测试角色 | 每次前端改动、每次发布前 | 191 项全绿 | 不上传代码；尤其 `app-boot-test` 失败须先查挂载点/分发 |

> **v1.2 执行证据补充**：L0/L1 是否真跑过，以 `deploy/run/tests.log`（及 `tests.log.<suite>`）**存在且非空**为准；L0b 是否真跑满 9 项，以输出无 `(skipped=` 为准（M3 / M4）。缺 `python3` / `node` / `curl` 的机器上，脚本可能只 `warn` 跳过或跳过用例，**不得据此判门禁通过**；必要时用 `release.sh --strict-tests` 让缺工具直接拒绝发布。

### 1.4 脚本纪律（写验收单/回归命令时必须遵守，来自项目既有约定）

| 纪律 | 原因 | 违反后果 |
|---|---|---|
| 打本机端口一律带 `--noproxy '*'` | 避免 HTTP_PROXY 环境变量把本地请求转走 | 探测结果假阴性/假阳性 |
| 目录穿越检查必须 `--path-as-is` | curl 默认规范化 URL 里的 `..`，不加就是**假检查**（请求根本没带 `..` 发出去） | 「19 个受限路径 404」这一组形同虚设 |
| 「期望无匹配」的 grep 一律追加**短路兜底**（命令写法见下方注） | `pipefail` 下 grep 无匹配返回 1，会让脚本自己崩 | 把「检查通过」误判成「脚本失败」 |
| 版本串四处同步 | `APP_VERSION`(js/config.js) + 所有 `?v=` + `index.html` 引用 + `pyapp/__init__.py`；当前值 `20260917a` | 浏览器命中旧缓存，展示版本与实际代码不一致；`smoke.sh` 第 2 组会抓到 |
| 不直接 `docker compose up -d` | 会把两个槽位同时拉起，破坏「同一时刻一个活跃槽位」不变量 | 双写、状态错乱；用 `install.sh`/`release.sh` |

> 注：Markdown 表格单元格内不能直接出现竖线，故本文表格一律用「短路兜底」指代；**实际 shell 命令写作 `|| true`**（`pipefail` 下用短路兜住「无匹配」的退出码）。表格里若看到带反斜杠的转义竖线，那只是排版转义，**不要带进命令**。

### 2.2 结构性覆盖缺口（本次治理期实测 · 最硬证据）

> 来源：前端工程师端木灵、后端工程师寇豆码的定向实测，经主理人中转。全部【实测·协作复跑】，均有原始输出与代码行号。**这些是已证实的缺陷，不是「可能有问题」**。

### 4.3 修复后回归（`integration_debugging.regression_after_fix`）

按「复现 → 缩小范围 → 假设 → 证据 → 最小修复 → 验证 → 回归」执行，**严禁猜测式乱改**：

1. **复现**：固定复现路径与最小条件，留存请求/响应、日志、代码位置。
2. **定位分层**：按 前端 → 网关(Caddy) → 后端(httpd/policy/store) → 数据库(db.py/SQLite) → 第三方(LLM) → 环境(Windows/Linux) → 部署(双槽位) → 数据 逐层排除，给出 2~3 个可验证假设。
3. **证据**：每条假设用日志 / 网络包 / `PRAGMA` / 配置逐条证实或证伪；**先有根因与证据才动手改**。
4. **最小修复**：只改必要部分，写清影响面（对应 §4.1 哪几行）。
5. **验证**：复现用例转绿 + §4.1 映射的全部必跑项转绿。
6. **防复发**：新增一条断言（写入 `test_api.py` 或对应 `.mjs`，按 G0-03 挂到 `TC-` 编号），否则同类缺陷会再次漏网。
7. **归档**：`BUG-` 单中记录「修复点 / 关联模块 / 回归清单 / 验证结果 / 风险提醒」。

> **代码自己的注释与实现相反**（`// 无论成功与否，私钥都不该继续留在 DOM 里`）—— 属"意图写对了、代码写漏了"。
> **修复**（`frontend-engineer`）：`catch` 分支内**先 `clearKeyInput()` 再分流**，使闸门跳转也带不走私钥；成功路径清两个框；前置校验路径一律不清。新增 `clearKeyInput()` / `clearCertInput()` 两个函数，同时复位文件名标签（避免"标签显示已选、内容却是空"）。
> **验证**：`app-boot-test[15b]` 11 条行为断言（前置失败不清 / 提交失败清私钥留证书 / 标签复位 / 错误提示不回显私钥 / 只重填私钥可重试成功 / 成功后两框皆空）。基线 `app-boot` **149 → 160**。

> ⚠️ **三时机规则仍然有效**（后续改动仍须遵守）：清空必须按**三个时机分开判**，不可把"清空"提前到函数开头 ——
>
> | 时机 | 证书框 | 私钥框 |
> |---|---|---|
> | 提交**成功** | 清 | 清 |
> | 提交**失败**（已提交过） | **保留** | **清** |
> | 未提交（前置校验失败 / 重渲染） | 保留 | 保留 |
>
> 前置那几处 `return showCertError('请选择证书文件…')`（空值 / PEM 格式不对）**本来就该不清**，属第三行。若图省事把清空提到函数开头，会让用户粘贴两段 PEM 后因一个格式错误就全丢 —— 那是用一个大缺陷换一个小缺陷。

> **🟡 遗留 P3（潜在、当前不可观测，2026-11-18 QA 复核发现）**：`clearKeyInput()` 的标签文案是**硬编码**的「未选择文件（**提交失败后**已清空，请重新选择或粘贴）」，但该函数在**成功路径也被调用** → 成功上传后标签一度被写成「提交失败后已清空」，**与事实相反**。
> **当前为何不可见**：成功路径在 `clearKeyInput()` 之后紧接 `render()`，整个面板重建、标签复位为「未选择文件」，文案在同一个同步块内被覆盖，**不会绘制到屏幕**。
> **为何仍要登记**：① 它与 N-01 属同一类病（**说了与事实不符的话**，违背 BR-028 结果诚实纪律），只是这次在文案层；② 一旦将来有人把成功路径的 `render()` 挪走或加上条件，这句假话会立刻暴露。
> **最小修法**：`clearKeyInput(msg = '未选择文件')` 参数化，失败路径传「提交失败后已清空…」，成功路径用默认值。**成本 1 行。**

> **闸门分支无断言（2026-11-18 更正：风险不是"低"，是"被调用顺序护着"）**
> `catch` 内的闸门分支（`isPasswordGateError` → `handleGateError`）目前**无断言**。
> ⚠️ **本节初版把理由写成"闸门会切走整个 DOM、私钥自然消失，故风险低"—— 这是错的**（`frontend-engineer` 纠正，QA 已回源码复核）：`handleGateError` → `enterPasswordGate()` → `showScreen('password')` **只切 `#auth-root` / `#app-root` 的 `hidden`，不重建 `#main`**。因此 `#cert-key-pem` 元素**连同 value 一起留在隐藏 DOM 里**。
> **正确结论**：私钥之所以消失，**完全是因为我们调了 `clearKeyInput()`**，不是因为 DOM 被换掉。当前实现靠"清空在闸门判断之前"这个**调用顺序**护着；一旦有人把清空挪到 `render()` 之后、或给成功路径加条件，隐藏 DOM 里的私钥就会一直留着（切账号、恢复显示时可能被重新展示）。
> **可测且便宜**：桩里已有 `gateForbidden` 开关 → 打开 → 填证书/私钥 → 点上传 → 403 → 断言"跳到改密页 **且** `#cert-key-pem.value === ''`。约 8 行，**不需要新桩**。

> **🔴 N-02 未修（P2，会冲掉草稿）**：`loadCert()` 在开头与结尾**各调一次 `render()`**，而 `certUploadCard()` 的两个 `<textarea>`（`#cert-crt-pem` / `#cert-key-pem`）**没有 value 绑定**，内容只存在于 DOM。→ 用户"粘贴 PEM → 点刷新状态"时，草稿**被整套重建冲掉**。
> **旁证（这条最说明问题）**：`showCertError()` 的注释明写「**不重渲染，保住用户已经粘贴的文本**」—— 说明作者**知道**重渲染会冲掉粘贴内容，但 `loadCert()` 没有遵守同一条纪律。
> **定级 P2 而非 P1 的理由**（按本文件 §5.1 级别定义）：P1 是"核心功能不可用 / 权限边界失守 / 发布门禁失效 / 备份不可用"；本条**有可用绕行方案（重新粘贴）**，符合 P2 的"非核心功能异常、有可用绕行方案"。
> **用例（🔴 预期红）**：`boot:cert-draft-survives-render` —— 填入证书+私钥 → 触发 `load-cert`（刷新状态）→ 断言两个 textarea 的值**仍在**。

> **🟡 N-12 未修（P3，文案与实现不符）**：`certUploadCard()` 的 hint 仍写「私钥只在本次请求体里提交，**提交成功后**页面上的输入会被立刻清空」。现状是**提交失败也会清私钥** → 文案把"失败也清"这件对用户有影响的事隐去了，用户上传失败后回头发现私钥框空了，会以为页面出错。
> 与 N-01 恰好相反：N-01 是「注释承诺了、实现没做到」，N-12 是「实现做到了、文案没跟上」——**两类都要防，第二类更隐蔽**，因为没人会去核对"文案是否还成立"。

### 8.3 回滚方案（测试失败时如何回退）

| 失败发生点 | 回退动作 | 依据 | 数据影响 |
|---|---|---|---|
| L0/L1/L0b 失败（代码未上传 / 服务器预检） | **不发版**：中止，代码不上传服务器，缺陷进 §5 流程 | `release.sh` 第 1 步「什么都没发生」 | 无 |
| L2 构建自检失败 | 中止构建，线上旧版本不动 | `release.sh` 第 3 步 | 无 |
| L3 冒烟 / 构建标识不符 | **不切流**：新槽位停掉即可，线上旧版本没动过 | `release.sh` 第 5 步 | 无 |
| **首次部署 `install.sh` 冒烟失败 → 部署中止**（v1.2 / D1；2026-11-16 核实脚本已 `die`） | **不对外公布地址**。脚本已 `exit 1`、不写 `deploy/run/state.env`、不打印「部署完成」，**不会**再产生「假成功」，无需人工清状态文件。按 `smoke.sh` 五组 `✗` 明细定位（`die` 只报「未通过冒烟门禁」，**不指出哪一项坏**）；**服务此时仍在运行**（冒烟在 `docker compose up` 之后、`save_state` 之前），数据未被改动。修好后直接重跑 `install.sh`（幂等）：因无 `state.env`，仍走首次部署路径、**会重新冒烟**；再按 `09` §2 V5~V7 核对暴露面与鉴权 | `install.sh` 第 6 节「冒烟验证」+ `lib.sh` 的 `die()`（M1）、G4-S01 / G6-S01、`09` §2 | 业务数据**未被改动**；**不会**再出现「状态文件与事实不符」。注意：容器仍在跑 —— 若不打算修，须手工 `docker compose down`，否则暴露面风险仍在 |
| Caddy 配置校验不通过 | `caddy_reload()` 先 `caddy validate`，校验不过**原地放弃**，旧配置仍生效 | 发布方案 §2.1 | 无 |
| L4 探测失败（exit 3） | 立即 `sudo bash deploy/rollback.sh`（零停机，切回旧槽位）；或引流窗口内 Caddy 上游兜底自动退回 | 发布方案 §5 / §4 第 8 步 | 无数据搬运（共用同一卷） |
| 切流后新版本异常 | 引流窗口（默认 20s）内旧槽位仍在跑，Caddy 主动健康检查 3s 一次自动摘除新槽位、流量退回旧槽位 | 发布方案 §4 | 无 |
| **数据库结构变更需回退** | 遵守 expand/contract：**一次发布只做加法**；破坏性变更拆三次发布（加新列 → 迁数据 → 第二次发布删旧列）；或 `release.sh --stop-first` 接受一次受控短停 | 发布方案 §6 + 总纲 §7.3 | 需迁移 + 回滚 SQL + 兼容性分析 |
| 数据需要精确拉回某时刻 | 灾备：停服务 → 删 `data/gtd4teams.db*` → `server.py --import 备份.json` → 起服务（**不能直接 `--import` 到非空库**，它是 `INSERT OR REPLACE`） | `Docker部署方案.md` §6 + 总纲 §7.4 | 会话表不在备份范围，全员需重新登录（正常） |
| 回滚后再回退 | `rollback.sh` 状态互换，再执行一次即可「回滚掉这次回滚」 | 发布方案 §5 | 无 |

### 8.4 验收标准（汇总）

- **阶段门禁**：G0~G6 七张验收单，每张所有验收项勾选「通过」或有书面豁免（G5 无豁免通道），且签字位齐全 → 该阶段通过。
- **发布门禁**：L0(49) + L0b(9) + L1(80/65/46) 全绿 → L2 构建成功 → L3 五组全过且 `build` 一致 → L4 失败数 0 且最大间隔 ≤ 3000ms。
- **缺陷阈值**：§5.3 七条任一命中即禁止进入 G6。
- **回归**：§4.1 改动类型对应的必跑项无漏跑；长耗时用例单独跑（§4.2）；结构性缺陷修复后按 §4.4 定向回归。
- **证据**：每条结论都能指向「命令输出（含 EXIT 码）/ 文件路径 / 截图 / git diff」之一；【未验证】项不得记为通过。
- **v1.1 覆盖充分性**：L0 / L0b / L1「全绿」**不等于覆盖充分**（§2.2）。判定 G4 / G6 放行时须同时核对 §7 的 **IMP-13 / IMP-16 / IMP-17（P0）**状态；未补齐前不得单凭套数全绿放行，相关验收项结论留为**待办**。
- **v1.2 门禁判定正确性**：L3 / L4 / L0b 的**脚本 `exit 0` 不等于放行充分条件**（§0.2.3 / §2.4）。G4 放行须 **G4-01~G4-11 全部通过 + G4-S01~S05 全部通过**；G6 放行须 **G6-01~G6-13 全部通过 + G6-S01~S03 全部通过**。§5.3 第 8 条任一命中即禁止进入 G6；`deploy/run/tests.log`、探测三数人工判定、L0b 无 `skipped`、目标 Linux 复跑四项证据缺一不可。
