### 1.1 计数口径与分发行为（易错点，如实记录）

- **20 条 ≠ 20 个路径**：`/api/llm/config` 有 GET+POST 两条（`:832`、`:833`）；`/api/auth/me`（`:819`）与 `/api/auth/profile`（`:818`）是两个不同路径但指向**同一个 `h_profile`**（`:523`）。故唯一路径 **19 条**。此为本文的登记口径，见 `04_TDS` §14 O-3。
- **方法映射**：`do_GET`/`do_HEAD` → `_dispatch('GET')`；`do_POST`/`do_PUT`/`do_DELETE` → `_dispatch('POST')`（`httpd.py:317-330`）。**后果【代码·已核】**：`PUT/DELETE` 到任一已注册的 POST 路径会被当作 POST 命中同一 handler（如 `PUT /api/rows` 会执行一次插入）；`OPTIONS` 一律 405（`httpd.py:332-334`）。这是现状而非设计意图，列入 §8 开放问题。
- **路径规范化**：`path = parsed.path.rstrip('/') or '/'`，故 `/api/health/` 与 `/api/health` 等价（`httpd.py:338`）。
- **未命中**：`ROUTES.get()` 返回 None → 404 `NOT_FOUND`（`httpd.py:350-353`）；非 `/api/` 前缀走静态三关白名单（`httpd.py:343-348,420-484`），非 GET → 405。
- **写请求三关前置**（对所有 POST 生效）：`_check_origin()` → `Content-Type` 必须 `application/json` → `_read_body()`（`httpd.py:357-371`）。故**任何 POST 都先可能返回 403/415/400/413**，与各端点自身错误码叠加。
- **静态资源不属于 `/api/*`**：`/`、`/js/*`、`/css/*`、`/assets/*`、`/img/*`、`/favicon.ico` 由 `PUBLIC_ENTRIES` 白名单托管（`pyapp/config.py:22`），非本文端点，但属 G3「真实 index.html 启动」的验证对象。
- **v1.1 端点增删（CR-2026-001）**【代码·已核】：移除 `POST /api/auth/register` 与 `GET /api/auth/check-email`（命中 `ROUTES.get()` 返回 None → 404 `NOT_FOUND`，`httpd.py:406-409`）；新增 `POST`/`GET /api/admin/accounts`。故 §1 的「20 条条目 / 19 条唯一路径」在 v1.1 **计数不变、成员变了**（−2 端点、+2 端点，其中 `check-email` 是 GET 单条、`accounts` 是 GET+POST 一对）。详见 §10.2。

> **判据（v1.3 固定，以后加 code 都按这条决定要不要写进 `MAP`）**：
> - **`code` 的含义随调用者/场景变化** → **`msg` 优先 + 兜底**（`MAP` 里只留一句最短的通用兜底，服务端文案必须能到达界面）。典型：`EMAIL_EXISTS`（管理员建号 vs 用户自登不是一回事）、`ROLE_NOT_ALLOWED`（对系统管理员与团队管理员是两句不同的话）、`FORBIDDEN`（通用码，今天在建号、明天可能在别处）。
> - **含义唯一** → 可以硬编码（`UNAUTHENTICATED`、`INVALID_CREDENTIALS`、`PASSWORD_CHANGE_REQUIRED` 这类）。
> - **无论哪种，服务端文案与前端文案不得分叉**：两处各写一份，同一个错误在"管理员入口"与"用户入口"下会有两种说法，排障时无法对账。
> - 实现约束：`friendlyError` 是 `if (MAP[code]) return MAP[code]`，**`MAP` 优先**（`api.js:358-382`）。所以"想用服务端文案"就必须**把那条从 `MAP` 里删掉或改成 `msg || 兜底`**，否则服务端写多好都到不了用户眼前。

> **纪律**：`.smoke/auth-flow-test.mjs:371-388` 是表驱动断言（7 个 code + 2 个 kind + 1 个回落）。改服务端 `message` 或前端 `MAP` 必须同步改这张表，否则 G4 的 65 项会挂【测试·有名】。`auth-flow-test.mjs:280,307,317` 还分别用 `EMAIL_EXISTS`(409)、`INVALID_CREDENTIALS`(401)、`RATE_LIMITED`(429) 打桩验证内联提示。

## 4. 关键契约详述（10 个高频/高风险端点）

> 约定：凡标 **【服务端注入】** 的字段，客户端提交的值**一律丢弃**；凡标 **【客户端禁止提交】** 的字段，提交即被静默忽略（`db.split_payload`，`db.py:565-591`）。

### 4.1 ① `POST /api/auth/login`（`:822` / `:579`）

请求：
```json
{"email": "alice@example.com", "password": "correct-horse"}
```
响应 `200` + `Set-Cookie: gtd_session=<token>; Path=/; HttpOnly; SameSite=Lax; Max-Age=2592000`：
```json
{"user": {"id": "u_1a2b3c4d", "email": "alice@example.com", "name": "Alice"}}
```

| 字段 | 说明 |
|---|---|
| `email` | 必填；大小写不敏感查库（`lower(email)`，`httpd.py:590`） |
| `password` | 必填；缺任一 → 400 `MISSING_CREDENTIALS` |
| `user.id` | TEXT 形态 `u_<hex>`（`security.py:92-95`） |

- 限速键 `email.lower()|client_ip`，15 分钟 10 次（`httpd.py:585-587`；`security.py:118-119`）。
- 邮箱不存在与口令错**返回同一 `INVALID_CREDENTIALS`**，防账号枚举（`httpd.py:592-595`）。
- 登录成功若 `needs_rehash` 则顺手升级散列（`httpd.py:598-601`）。
- **【客户端禁止提交】** `owner_id`/`id`/`password_hash` 等：本端点根本不读这些字段。
- 用例：`test_06_login_wrong_password_then_success`（`test_api.py:190`）、`test_08_login_is_rate_limited`（`:209`）、`test_40`（`:659`）【测试·有名】。

响应 `200`：

| `payload` | 必须是 JSON 对象，否则 400 `BAD_PAYLOAD` |

| **`id` / `created_at` / `updated_at`** | **【客户端禁止提交】**（`pk`/`stamp` 被丢弃，`db.py:578-586`）；时间戳服务端维护（`store.py:116-119,137-138`）。`test_22_unknown_fields_are_dropped`（`test_api.py:429`） |
| 未知字段 | 静默丢弃，不报错（`db.py:577-579`） |
| 类型归一化 | `int/real/bool/json/jsonarr/text/date/ts` 按 `COLUMNS` 收敛（`db.py:516-562`）；`test_23` 断言 `tags` 数组、`recurrence` 对象、`flagged` 布尔往返 |

**三种 op 的权限差异（刻意保留，改动前先读 `04_TDS` §5.3）**：

| op | 权限通过 | 权限被拦 | 证据 |
|---|---|---|---|
| `insert` | 返回新行 `rows:[{...}]` | `raise Denied` → **403 `PERMISSION_DENIED`**（`test_16`，`test_api.py:341`） | `store.py:122-127` |
| `update` | 返回更新后行 | **200 + `rows:[]`** | `store.py:141-142` |
| `delete` | 返回 `rows:[{id}]`（`store.py:159`） | **200 + `rows:[]`** | `store.py:155-156` |

## 5. 契约变更规则

### 5.1 什么算破坏性变更（必须走 `CR-` + G1）

| 类别 | 例子 |
|---|---|
| 端点 | 新增/删除 `/api/*`；改方法或路径；改认证要求（免鉴权 ↔ 需登录） |

#### 10.2.2 决策：`/api/auth/register` 是「移除（404）」还是「保留（403）」？

**结论：从 `ROUTES` 移除（404）。同时移除 `/api/auth/check-email`。**

理由（按重要性排序）：

1. **403 会把"已删除的能力"表述成"此刻暂不可用"**。`h_register` 的 403 依据是 `cfg.allow_signup`（`httpd.py:655-657`），而 `allow_signup` 是一个**运行期可改的开关**（`config.py:92-95`，来自 `GTD_ALLOW_SIGNUP`）。只要路由还在、开关还在，"把开关打开就恢复自助注册"就是一条**一行配置改动即可复活**的路径 —— 而本期要消灭的正是这条路径。404 表达的是"没有这个能力"，403 表达的是"你暂时没被允许"，这两件事在产品上完全不同。
2. **保留路由就必须留一个空壳 handler**。`h_register`（`httpd.py:653-691`，39 行）的价值几乎全在建号逻辑（邮箱/口令校验 + `INSERT users` + 建会话 + 下发 Cookie）；一旦恒 403，这些全要删，剩下的 `raise ApiError(403, ...)` 没有任何被调用的正当理由。死代码在安全评审里是最容易被"顺手恢复"的东西。
3. **配置连坐必须一次清干净**：`allow_signup`/`signup_code`（`config.py:92-95`）、`describe()` 的 `allowSignup`/`signupCodeRequired`（`config.py:166-167`）、CLI 三个参数（`server.py:44-50`）、`h_check_email` 的 `signupAllowed/signupCodeRequired`（`httpd.py:646-650`）、`cmd_set_password` 里对 `cfg.allow_signup` 的提示分支（`server.py:146-149`）、`deploy/env.example:35-40`、`README.md:42-43,147-148`。**保留 403 就必须把这些全部保留**，于是"自助注册"这个概念会继续存在于配置、文档、运维手册里，只是不生效 —— 比删掉更容易误判。
4. **攻击面**：净减少一个"免鉴权 + 可写库（`INSERT users`）+ 可建会话（`Set-Cookie`）"的端点，以及一个"免鉴权 + 可批量探测邮箱是否注册"的枚举端点。`h_check_email` 虽有限速（`httpd.py:635-638`），但限速键是 `check-email|<IP>`（不是按邮箱），换 IP 即可绕过 —— 而它现在已经没有任何正当调用方。
5. **路由表即能力清单**。`ROUTES`（`httpd.py:1048-1069`）是本文 §1、`04` §2.2 与 G1 评审的共同事实来源。让路由表与"真实可用能力"一致，比让路由表多一条永远 403 的条目更可信。

**必须承认的代价**：

- 旧页面（浏览器里已加载的旧 `api.js`、或发布窗口期仍开着的旧标签页）调用会得到 `404 NOT_FOUND`，`message` 为 `接口 /api/auth/register 不存在`（`httpd.py:408`）。**新版 `friendlyError` 会把 404 统一换成可读文案**（§10.7 注记 3：「该功能已下线，请刷新页面；账号由管理员创建。」）；但**旧 `api.js` 里没有这条兜底**，会回落成服务端原文案（`api.js:382-384`）。**可接受**：这句话不会让人误以为"稍后重试就好"，也不会造成任何安全后果；刷新页面即消失（`.html` 为 `no-store`、静态资源为 `no-cache`，`httpd.py:575`）。产品侧担心的"用户以为系统坏了去重启服务"，只影响**未刷新**的旧标签页，且发布说明里会写明"账号改由管理员创建"。
- `tests/test_api.py` 的通用建号夹具、`.smoke/auth-flow-test.mjs` 的 fetch 打桩必须同步改造（§10.9.4）。**注意：换成 403 也躲不掉这项成本**（夹具一样要改），只是错误码不同。所以"省测试改造"不能作为选 403 的理由。

**已被否决的替代方案（留档，防止以后再被提出来）**：曾考虑"从 `ROUTES` 移除、但保留一张已下线端点表，统一返回 `410 Gone` + `SIGNUP_REMOVED`"。**主理人 2026-11-14 裁决定稿：不保留，就是 404。** 三条理由：

1. 留一个 `SIGNUP_REMOVED` 错误码，等于让"自助注册"这个概念在代码里续命 —— 本期要做的是**连同概念一起删掉**（配置项、CLI 开关、`describe()` 字段、`env.example`、README 全清）。
2. **`410` 是一个永久性承诺**：它告诉所有客户端"这个路径永远不会再存在"。一旦发出去，以后想复用 `/api/auth/register` 这个路径就变成破坏性变更 —— 而我们没有任何理由把未来的选择权提前交出去。
3. 受益窗口只有"发布后几分钟内仍开着旧标签页的用户"，代价却是长期死代码 + 一个新错误码。**不划算。**

因此：**不新增 `SIGNUP_REMOVED` 错误码**，错误码表维持 §10.8 的 39 个（其中不含 `SIGNUP_REMOVED`）。代价（旧标签页拿到 `404 NOT_FOUND`，文案「接口 /api/auth/register 不存在」）接受，发布说明里写一句"账号改由管理员创建"；前端用 `friendlyError` 的 404 兜底把这条文案换成可读提示（§10.7 注记 3），**不需要新错误码**。

### 10.3 新增 `POST /api/admin/accounts`

> ⚠️ **命名陷阱，先读**：`/api/admin/*` 这个前缀在本项目里**不表示"仅系统管理员"**，它表示"**账号管理**"。本端点的调用者有两级（系统管理员 / 团队管理员），具体权限在 handler 内按身份分流。**不要**在 `_dispatch` 或将来任何地方给 `/api/admin/*` 加一个统一的"必须是系统管理员"门槛 —— 那会把团队管理员这条主路径直接堵死。

#### 10.3.1 请求契约

| 字段 | 类型 | 必填 | 系统管理员 | 团队管理员 | 规则 |
|---|---|---|---|---|---|
| `email` | string | **是** | ✔ | ✔ | 必须匹配 `EMAIL_RE`（`httpd.py:41`，与 `h_register` 同一正则）；大小写不敏感查重（同 `httpd.py:672`） |
| `name` | string | 否 | ✔ | ✔ | 缺省取 `email.split('@')[0]`（与 `httpd.py:677` 一致）；服务端截断 64 字符 |
| `teamId` | int | **团队管理员必填** | 可选 | **必填** | 系统管理员省略 = 只建号、不加入任何团队（此时 `role` 也必须省略）；给定则必须存在且 `archived=0`，**入队角色默认 `admin`** |
| `role` | string | 否 | **给了 `teamId` 时只接受 `admin`（省略即 `admin`）；没给 `teamId` 时必须省略** | 必须省略 / `null` / `'member'`（省略即 `member`） | **v1.3 收紧**：系统管理员传 `member`/`owner` 一律 `ROLE_NOT_ALLOWED` 400（委派链，见 §10.3.3）；团队管理员传 `admin`/`owner` 一律 403。**`owner` 对任何人、任何情况都拒绝**（与 `policy.py:182-183`「owner 行的 role 不可被修改」同源） |
| `isSystemAdmin` | — | **禁止** | — | — | **不读**。请求体里出现即忽略；`is_system_admin` 恒为 0（唯一的系统管理员创建入口是 CLI，§10.6） |
| `mustChangePassword` | — | **禁止** | — | — | **不读**。恒为 1 |
| `password` / `passwordHash` / `id` | — | **禁止** | — | — | **不读**。明文口令由服务端 `secrets` 生成（§10.6.5） |

请求示例：

```json
{"email": "bob@example.com", "name": "Bob", "teamId": 12, "role": "member"}
```

**`null` 与"字段缺失"等价**（`body.get('role')` 返回 `None`）：前端传 `{teamId: null, role: null}` 与传 `{email:...}` 的攻击面完全一样，服务端不做区分。

#### 10.3.2 响应契约

`201 Created`（**不设 `Set-Cookie`** —— 建号不切换调用者会话，这与 `h_register` 相反，见 `httpd.py:690-691`）：

```json
{
  "user": {"id": "u_9f3a1c7d2e4b8a60", "email": "bob@example.com", "name": "Bob",
           "isSystemAdmin": false, "mustChangePassword": true},
  "teamId": 12,
  "role": "member",
  "password": "Xk7pQ2mRt9vWb4Ns"
}
```

| 字段 | 语义 | 备注 |
|---|---|---|
| `user.id` | `u_` + 16 hex（`security.new_user_id()`，`security.py:92-95`） | 与既有账号同形态 |
| `user.isSystemAdmin` | 恒 `false` | 见 §10.3.1 |
| `user.mustChangePassword` | 恒 `true` | 首次登录即被闸门拦住（§10.5） |
| `teamId` | 加入的团队 id；**未加入时为 `null`**（不是 `0`/`''`） | 前端按 `=== null` 判定 |
| `role` | 在该团队的角色；未加入时为 `null` | 取值只可能是 `admin` / `member` |
| `password` | **明文初始口令，只出现这一次** | 服务端不存明文、不回显、不写日志、无"再次获取"接口 |

**响应头要求**：`Cache-Control: no-store`（响应体含明文口令，不能被任何中间层缓存）。实现：`handler._json(payload, status=201, extra_headers={'Cache-Control': 'no-store'})`。注意现有 `_send` 默认不设 `Cache-Control`（`httpd.py:243-257`），必须显式加。

**建号后目标账号没有任何会话**：需其本人用该口令登录，登录后立即被闸门要求改密（§10.5）。

#### 10.3.3 权限判定矩阵（本期最关键的越权面）

> 判定顺序即表中顺序：**先判身份，再判参数**。不要先查"邮箱是否已存在"—— 那会把"某邮箱是否存在"暴露给一个本来无权建号的人（账号枚举）。

|---:|---|---|---|---|---|

| 2 | 任意，但 `must_change_password=1` | 任意 | 任意 | **拒绝（闸门先于本端点）** | `PASSWORD_CHANGE_REQUIRED` 403 |
| 3 | 系统管理员 | 省略 | 省略 / `null` | **允许**：只建号，不加入任何团队（"建一个待分配的团队管理员"） | 201，`teamId=null`,`role=null` |
| 4 | 系统管理员 | 省略 | **显式传任意值**（`admin`/`member`/`owner`） | **拒绝**：没有团队就没有团队角色，传了就是错的 | `ROLE_NOT_ALLOWED` 400 |
| 5 | 系统管理员 | 存在的 T | 省略 / `null` | **允许**：建号 + 入队，**默认按 `admin`** | 201，`role='admin'` |

| 16 | 该团队 `status != 'active'` 的"前管理员" | 任意 | 任意 | **拒绝**（停用即失去管理权，与 `policy.load_context` 口径一致，`policy.py:344-349`） | 同上，403 |

> **#3/#4/#5 的一个实现要点**：`role` 与 `teamId` **必须同现同缺**（对系统管理员而言）。省略 `teamId` 却传了 `role`（哪怕是 `member`）一律 400 —— 否则会出现"传了 `member` 但没入队"这种自相矛盾的请求被静默接受，前端会以为人已经进团队了。

**「委派链」—— 为什么系统管理员不能建 `member`（v1.3 收紧，主理人 2026-11-14 裁决）**

| 项 | 内容 |
|---|---|
| 变更 | 系统管理员的建号角色集合由 `{'admin','member'}` 收成 **`{'admin'}`**；`teamId` 省略时 `role` 必须也省略 |
| 理由①（用户原话） | 需求原句是"系统管理员创建**团队管理员**账号，并可指定归属团队"。给 `member` 等于让"团队管理员管成员"这条委派链变成可绕过的装饰 |
| 理由②（我原先的反对意见已作废） | 我曾主张"不给 `member` 则新团队产生不了第一个管理员"。**这条不成立**：系统管理员建**无团队账号**（#3）→ 对方登录、改密、**自己建团队成为 owner**（`store.create_team_with_owner`，`store.py:233-237` 把创建者写成 `role='owner'`）→ 再由他建成员。整条路径不需要系统管理员碰 `member` |
| 理由③ | 净减一个越权面：系统管理员不再能"往任何团队里塞人"，只剩"授团队管理员"这一件事 |
| 实现落点 | `store.create_account` 步骤 3：`team_id` 给定时 `role` 缺省取 `'admin'`，且**只接受 `'admin'`**；`team_id` 缺省时 `role` 必须为 `None`（显式给任何值都 400）。见 §10.3.4 |

**已知取舍（第 10 行，必须在 `08` 记录并接受）**：系统管理员可以对**任意**团队授出 `admin`，即使他不是该团队成员。这等价于"系统管理员可对任意团队提权"。之所以接受：

① 本期已把系统管理员限制在"建号 + 授团队管理员"两件事上，他看不到任何团队的业务数据（`load_context` 只认 `team_members`，`policy.py:335-350`；系统管理员若不加入团队，`memberships` 为空 → 所有业务表 `can_select` 全 False）；
② 若不给出这条能力，新团队将无法产生第一个团队管理员（系统管理员必须先自己用邀请码加入团队才能授权，成本更高且更容易做错）；
③ 能力的规模是"能创建账号 / 能授权"，不是"能读数据"，`08` 定级时应据此评估。
④ **产品侧补充的一条更硬的理由（采纳）**：`team_members` 里 `owner` 行的 `role` **谁都改不了**（`policy.py:182-183`：`old_role == 'owner' and new_role != 'owner' → False`）。所以当某团队 owner 离职、失联或长期不可用时，**"系统管理员给另一个人授 `admin`"是唯一能在不碰任何业务数据的前提下恢复"这个团队有人能管"的通道**。没有这条能力，该团队只能靠人工改库。这条请写进 `08` 的审计表，作为该能力的正当用途依据。

**必须写死的四条禁止**（任何一条被放松都等于越权）：
1. 团队管理员**永远**不能创建系统管理员（请求体里根本没有这个字段，且 store 里 `is_system_admin` 恒 0）。
2. 团队管理员**永远**不能授 `admin`（否则他能无限复制同级管理员，团队所有权/管理权失控 —— 与 `policy.update_keep` ② 对"自提 owner"的封堵同源，`policy.py:184-189`）。
3. 任何人**永远**不能通过本端点授 `owner`（所有权转让需要二次确认 + 审计，本期不做）。
4. **系统管理员永远不能经本端点建 `member`**（v1.3）。这条不只是收敛权限：它保证"团队成员的来源只有团队管理员或本人建团队"这一条可审计的因果链。若将来要放开，必须能回答"这个成员是谁塞进来的"，而现有审计只有 `account.created` 一条（`06` §10.3.6），回答不了。

#### 10.3.4 写入路径：`store.create_account()` 契约（**唯一**写入路径）

**为什么不能用 `policy.can_insert('team_members', ...)` 近似**：`team_members` 的 insert 策略是 `is_admin(tid) or is_owner(tid)`（`policy.py:161-164`），它只覆盖"团队管理员"这一层；而系统管理员若是该团队成员（或根本不是成员），这条策略会**误拒**或**误放**。更根本的是：`policy` 的输入是"一行数据 + `AuthzContext`"，`AuthzContext` 里根本没有"系统管理员"这个概念（`policy.py:50-67`）—— 硬塞进去会让策略层承担它不该承担的实例级概念。所以这一层必须是**显式的、独立的、有名字的**。

**签名**（`pyapp/store.py` 新增；类型注解保持在 Python 3.8 可用范围内，与 `security.session_expiry` 的写法一致）：

```python
def create_account(conn, actor, *, email, name=None, team_id=None, role=None,
                   password_hash, is_system_admin=False, must_change_password=True):
    """三级建号的唯一写入路径。返回 {'user': {...}, 'teamId': int|None, 'role': str|None}。

    actor —— 由调用方从**会话/CLI**组装，**绝不来自请求体**：
        {'uid': str,                          # 调用者账号 id
         'is_system_admin': bool,             # users.is_system_admin
         'admin_team_ids': tuple,             # 调用者 role in ('owner','admin') 且 status='active' 的 team_id
         'via': 'http' | 'cli'}               # 只用于审计，不参与授权

    password_hash —— 已散列的口令。**明文永不进入 store**（明文只存在于 httpd 的局部变量与响应体）。
    is_system_admin —— **仅 CLI 传 True**；HTTP 路径恒定不传。本项目里创建系统管理员的入口只有 CLI。
    """
```

**职责边界（写清 in / out，避免下一个人往里加东西）**：

| 属于本函数 | 不属于本函数 |
|---|---|
| 归一化 `email`/`name`/`role` 的缺省与截断 | 生成明文口令（`security.generate_temp_password()`）与散列（`security.hash_password`） |
| 授权判定（`actor` × `team_id` × `role`，矩阵 §10.3.3） | 解析 HTTP 请求体 / 组装 `actor` |
| 入参校验（邮箱格式、角色枚举、团队存在且未归档） | 限流、`Origin` 校验、Cookie 无关 |
| 唯一性检查 + 捕获 `IntegrityError` 兜并发 | 拼响应（含 `Cache-Control` 头） |
| 单事务写 `users` + 可选 `team_members` + 审计 `app_logs`，**一次提交** | 下发 Cookie / 建会话（本流程不建会话） |
| 取回新行（**提交之前**）并返回 dict | 打印到终端（CLI 负责） |

**内部校验顺序（必须照此顺序，顺序本身就是安全设计）**：

1. `email = str(email or '').strip()`；`name` 缺省 `email.split('@')[0]`、截断 64；`role = (str(role).strip() if role not in (None, '') else None)` —— **先归一成 `None | 'admin' | 'member' | 'owner'`，不要在这里填默认值**：默认值**取决于是哪个分支**（系统管理员 + 有团队 → `admin`；团队管理员 → `member`），在步骤 3/4 里填空。
2. **授权闸①（有无建号权）**：`actor['is_system_admin']` 为真 → 走系统管理员分支；否则 `actor['admin_team_ids']` 非空 → 走团队管理员分支；两者都不满足时**再分两种**：
   - 实例**零系统管理员**（`SELECT 1 FROM users WHERE is_system_admin = 1 LIMIT 1` 为空）→ `StoreError('NO_SYSTEM_ADMIN', '本实例还没有系统管理员。请先在服务器执行 python server.py --create-admin <邮箱> 完成引导', 403)`；
   - 否则 → `StoreError('FORBIDDEN', '只有系统管理员或团队管理员可以创建账号', 403)`。
   **为什么要分**：两种情况调用者的处境完全不同 —— 前者是"实例没初始化，你要跑 CLI"，后者是"你没权限"。混成一个码，运维看到 403 会去查权限、排查越权，而真正该做的是跑一条命令。这个判断只在**失败路径**上多一次只读查询，成本可忽略。
3. **系统管理员分支**（角色集合 = `{'admin'}`，v1.3）：
   - `team_id` 缺失时：`role is not None` → `ROLE_NOT_ALLOWED` 400（矩阵 #4，"没有团队就没有团队角色"）；`role` 保持 `None`，`team_id` 保持 `None`。
   - `team_id` 给定时：`role` 缺省填 `'admin'`；`role != 'admin'`（即 `member` / `owner`）→ `ROLE_NOT_ALLOWED` 400（矩阵 #7/#8）；再校验 `team_id` 存在且 `archived = 0` → 否则 `TEAM_NOT_FOUND` 404。
4. **团队管理员分支**：`team_id` 缺失 → `TEAM_REQUIRED` 400；`int(team_id) not in actor['admin_team_ids']` → `NOT_TEAM_ADMIN` 403（**先判越权，再判 role**：不然会向一个越权调用者透露"role 该填什么"）；`role` 缺省填 `'member'`，`role != 'member'` → `ROLE_NOT_ALLOWED` 403。
5. **参数闸**：`EMAIL_RE.match(email)` 失败 → `StoreError('INVALID_EMAIL', '请输入有效的邮箱地址', 400)`。
6. **唯一性**：`SELECT 1 FROM users WHERE lower(email) = lower(?)` 命中 → `EMAIL_EXISTS` 409，文案**必须是**：
   「该邮箱已有账号。请把本团队邀请码发给对方，由**对方登录后自行加入**；若对方无法登录，请联系运维重置密码。」
   **为什么这么写**：管理员**没有**"把人加入团队"的能力 —— `join_team_by_code` 用的是**当前会话身份**（`store.py:252-295`），邀请码只能由账号本人登录后使用。原本文案（"请用邀请码把它加入团队"）会让管理员拿着邀请码找不到出口。**错误文案必须指向一条调用者真的能执行的路径**，否则它只是把死路说得好听一点。
7. **写入（同一事务，未提交）**：
   - `INSERT INTO users (id, email, name, password_hash, created_at, updated_at, is_system_admin, must_change_password)`
     —— `is_system_admin` = `1 if (is_system_admin and actor['via'] == 'cli') else 0`，**双重保险**：即使有人给 HTTP 路径传了 `True`，`via` 不是 `'cli'` 也会被抹成 0。
   - `if team_id:` `INSERT INTO team_members (team_id, user_id, email, display_name, role, status, capacity, created_at, updated_at)` —— `role` 取步骤 3/4 填好的值（`admin` 或 `member`）、`status='active'`、`capacity=6`、`email`/`display_name` 冗余写入（与 `create_team_with_owner` 同一风格，`store.py:233-237`、`join_team_by_code` `store.py:287-293`）。
   - **审计行（见 §10.3.6）**：`INSERT INTO app_logs (...)`，与上面两条**同一事务**。
8. **异常映射**：`except sqlite3.IntegrityError` → `conn.rollback()` →
   - 撞 `users_email_uniq`（`db.py:44`）→ `EMAIL_EXISTS` 409（步骤 6 与 INSERT 之间有并发窗口，这条是兜底）；
   - 其它 → `StoreError('ACCOUNT_CREATE_FAILED', '账号创建失败，请重试', 500)`（沿用 `TEAM_CREATE_FAILED` 的风格，`store.py:238-242`）；
   - `except Exception` → `conn.rollback()` 后原样抛出。
9. **取回在提交之前**：`SELECT id, email, name, is_system_admin, must_change_password FROM users WHERE id = ?` → 组 dict → `conn.commit()` → **return**。
   提交之后**不允许**再做任何 `execute` / 取回 / 二次提交 —— 否则 `TrackedConnection.commit_attempted` 会置位（`db.py:478-481`），本次请求失去写锁争用重试资格（`httpd.py:475-485`），并进入"已提交但后续失败、不可重放"的窗口。这条纪律在 `insert_row`（`store.py:161-166`）与 `create_team_with_owner`（`store.py:246-248`）里已经收敛过一次，**不要在新代码里退回去**。

**httpd 侧的 handler 只做四件事**（`h_admin_accounts_create`）：

```python
user  = handler._require_user(conn)                 # ① 认证 + 改密闸门（自动）
ctx   = load_context(conn, user['id'])              # ② 只为了拿团队管理员身份
actor = {'uid': user['id'],
         'is_system_admin': bool(user.get('isSystemAdmin')),
         'admin_team_ids': tuple(t for t, r in ctx.memberships.items() if r in ('owner', 'admin')),
         'via': 'http'}
password = security.generate_temp_password()        # ③ 明文只在这里
result = store.create_account(conn, actor, email=..., name=..., team_id=..., role=...,
                              password_hash=security.hash_password(password))
result['password'] = password                       # ④ 只塞进响应，不落库、不打日志
handler._json(result, status=201, extra_headers={'Cache-Control': 'no-store'})
```

> 注意 ②：`ctx.memberships` 只含 `status='active'` 的行（`policy.py:344-349`），所以"被停用的前管理员"自动不在 `admin_team_ids` 里 —— 矩阵 #16 由这一行代码保证，不需要额外判断。

#### 10.3.8 结构性保障：`users` 不在 `db.COLUMNS`，所以新列**天生**不可被客户端篡改

主理人要求把"新列不可被客户端篡改"写成**结构性保障**，而不是"我们在代码里校验了"。这两者的强度差一个量级，逐条给证据链：

| 环节 | 事实 | 证据 |
|---|---|---|
| ① `COLUMNS` 只登记 **11 张业务表** | `teams`/`team_members`/`work_items`/`projects`/`areas`/`contexts`/`resources`/`progress_logs`/`reviews`/`on_call`/`app_logs` —— **`users`、`sessions`、`settings` 不在其中** | `db.py:300-375` |
| ② 通用 CRUD 的可写表白名单由它派生 | `WRITABLE_TABLES = tuple(COLUMNS.keys())`（`db.py:378`）—— 不存在第二份手工维护的表名清单 | `db.py:378` |
| ③ 任何越界的 `table` 在**取数之前**就被拒 | `store._assert_table()` 抛 `UNKNOWN_TABLE` / 404；`insert_row`/`update_row`/`delete_row` 第一行都调它 | `store.py:33-35`、`:140-141`、`:169-170`、`:192-193` |
| ④ 已有一条测试把这件事钉死 | `test_35_unsupported_table_is_rejected` 断言 `insert('users', {...})` → **404 `UNKNOWN_TABLE`** | `test_api.py:690-694`【测试·有名】 |
| ⑤ 第二层：即便将来有人误把 `users` 加进 `COLUMNS` | `split_payload` 仍会丢弃 `owner`/`stamp`/未知字段（`db.py:641-667`），且 `password_hash` 这类未登记字段一样写不进去 | `db.py:641-667` |

**结论**：`is_system_admin` / `must_change_password` 这两个新列，**不存在任何一条客户端可达的写入路径** —— 不是"我们记得过滤"，而是"通用 CRUD 的表白名单里根本没有 `users` 这张表"。唯一能改它们的入口是：

1. `store.create_account` / `grant_system_admin` / `reset_password`（服务端受控函数，见 §10.3.4）；
2. `h_change_password` 的 `UPDATE ... must_change_password = 0`（§10.5.4）。

**补充要求（采纳 data-modeler 的建议）**：在 `db.COLUMNS` 上方补一段注释说明"`users`/`sessions`/`settings` 是系统表，永不进 `COLUMNS`"，并加一条护栏测试 `test_users_table_is_not_client_writable`（对 `insert`/`update`/`delete` 三种 op 都断言 404 `UNKNOWN_TABLE`）。这条测试的价值在于：**把"结构性保障"从设计事实变成可执行断言** —— 结构性保障一旦被人无意破坏（比如某天把 `users` 加进 `COLUMNS` 以便"管理界面能改名字"），现有测试只有 `insert` 一条会红，`update`/`delete` 不一定。

### 10.5 强制改密闸门（`403 PASSWORD_CHANGE_REQUIRED`）

#### 10.5.1 错误契约

| 项 | 值 |
|---|---|
| code / status | `PASSWORD_CHANGE_REQUIRED` / **403** |
| `message` | 「初始密码尚未修改，请先设置新密码后再继续（当前操作已锁定）」—— 服务端文案即最终展示文案，前端 `friendlyError` 的 `MAP` 里给同一句，避免两处漂移 |
| 触发条件 | 会话有效 **且** `users.must_change_password = 1` **且** 请求路径不在放行白名单内 |
| 不触发的边界 | 无会话（那是 401 `UNAUTHENTICATED`，闸门不改变 401 的优先级） |

**优先级写死**：`401 UNAUTHENTICATED` > `403 PASSWORD_CHANGE_REQUIRED` > 端点自身的授权错误（`FORBIDDEN` 等）。理由：不能让人用"我还在改密阶段"来解释"我为什么没有建号权"。

#### 10.5.2 位置：为什么在 `_require_user` 内，而不是 `_dispatch` 的某一步

**结论**：闸门实现在 `_require_user`（`httpd.py:328-332`）内部，`_current_user` 之后、返回 `user` 之前：

```python
def _require_user(self, conn):
    user = self._current_user(conn)
    if not user:
        raise ApiError(401, 'UNAUTHENTICATED', '登录状态已失效，请重新登录')
    if user.get('mustChangePassword') and not self._password_change_exempt():
        raise ApiError(403, 'PASSWORD_CHANGE_REQUIRED',
                       '初始密码尚未修改，请先设置新密码后再继续（当前操作已锁定）')
    return user
```

它**仍然发生在 `_dispatch` 的重试循环内**（`httpd.py:440-445`），因此继承全部既有纪律：每请求一个新连接、异常时未提交事务随连接关闭丢弃（`httpd.py:471-473`）、响应未开始写才可重放（`httpd.py:475-485`）。闸门在任何写之前抛出，重放安全性不受影响。

四条理由：

1. **唯一必经点，天然 fail-closed**。现有 **12 个**需要登录的 handler，第一个动作全是 `_require_user`（`h_profile:623`、`h_change_password:736`、`h_workspace:759`、`h_rows:770`、`h_team_create:791`、`h_team_join:807`、`h_review_save:818`、`h_export:852`、`h_llm_config_get:858`、`h_llm_config_set:947`、`h_llm_models:986`、`h_llm_chat:996`；其中 `profile`/`me` 共用一个 handler）。**新增端点只要按既有写法调 `_require_user`，就自动被闸门覆盖** —— 不需要任何人记得去改一个白名单。这是"默认拒绝"和"默认允许 + 记得加黑名单"之间的区别，而后者一定会漏。
2. **不需要二次查会话**。`_current_user` 本来就 JOIN 了 `users`（`httpd.py:289-294`），把 `must_change_password`、`is_system_admin` 加进 SELECT 列表即可，零额外查询。若把闸门放 `_dispatch`，那里没有 user 对象（认证在各 handler 内完成），要么再查一次会话，要么让 `_dispatch` 缓存 user —— 两者都比改一行 SELECT 重。
3. **不误伤匿名/可选鉴权端点**。`h_session`（`httpd.py:617-619`）、`h_log`（`:827-839`）走的是 `_current_user`；`h_health`（`:597-614`）、`h_logout`（`:725-732`）根本不鉴权；静态资源走 `_dispatch` 的前置分支（`:399-404`）。这些本来就不受闸门影响 —— 但白名单仍**显式登记** `health`/`session`/`logout`（§10.5.3 共 5 逻辑项 / 6 条路径），理由是多 3 行常量的成本可忽略，而"将来有人把 `h_session` 改成 `_require_user`"时不会突然把会话探测打死。
4. **不放 `_dispatch` 的额外理由**：路径白名单写在路由层，等于把授权规则散到两个地方（`ROUTES` 附近 + `policy.py`），这与本项目"授权集中在 `policy.py` + 少量显式 store 函数"的整体设计相反（`04` §2.2、`policy.py:5-7`）。

#### 10.5.3 放行白名单（精确清单，主理人裁决定稿）

> **计数口径（彻底钉死，避免 3/5/8 三种说法并存）**：
> **白名单 = 5 个逻辑项 = 6 条路径**（`profile` 与 `me` 是同一 handler 的两条路径）。这是**唯一**需要记的数字。
> 常量里**统一登记这 6 条路径**，即使其中 `health`/`session`/`logout` 当前天然不经过 `_require_user` —— 多登记 3 行常量的成本可以忽略，收益是：将来某人把 `h_session` 改成 `_require_user`（很自然的重构）时，不会突然把"会话探测"打死，也不会让改密页白屏。
> 另外两类不参与判定、也不需要登记：**`/api/logs`**（走 `_current_user`，天然放行）与**全部静态资源**（`_dispatch` 前置分支）。**因此 QA 的断言口径是**：除"白名单 6 条路径 + `POST /api/logs` + 非 `/api/` 静态路径"之外，`must_change_password=1` 的会话对**每一张** `ROUTES` 条目都必须 403。

| # | 路径 | 当前机制 | 为什么必须放行 |
|---:|---|---|---|
| 1 | `POST /api/auth/password` | 该 handler 用 `_require_user`（`httpd.py:736`） | **生死线**。漏掉这条 = 用户为了改密必须访问改密接口 → 被自己的闸门拦住 → **密码永远改不了、账号永久锁死**。`data-modeler` 在 `05` §13.8 B4a 也独立标出了同一风险 |
| 2 | `GET /api/auth/profile` | `_require_user`（`:623`） | 前端渲染"强制改密"页需要权威身份（`api.js:103-105`、`app.js:171-176`） |
| 3 | `GET /api/auth/me` | 同一个 handler（`ROUTES` `:1052` → `h_profile` `:622`） | 别名路径必须与 profile **同放行**，否则两个等价路径行为不一致 —— 最容易漏的一条 |
| 4 | `GET /api/auth/session` | `_current_user`（`:617-619`） | 现在是天然放行；但它是**前端唯一的启动门禁来源**（`api.js:83-90`），必须显式保护，不能依赖"它碰巧不调 `_require_user`" |
| 5 | `POST /api/auth/logout` | 不鉴权（`:725-732`） | 被强制改密的人必须能退出（换账号）。同样显式保护 |
| 6 | `GET /api/health` | 不鉴权（`:597-614`） | 发布/容器探针不能因为"有人没改密码"而失败，否则蓝绿会把正常判成不健康（`deploy/smoke.sh`、`Dockerfile` HEALTHCHECK 都打它） |

**不参与判定、也不登记的两类**：

| 类 | 路径 | 机制 |
|---|---|---|
| 运行日志 | `POST /api/logs` | 走 `_current_user`（`httpd.py:837`），允许匿名 → **天然放行**。刻意保留：改密失败/闸门拦截正是最需要留证的场景（`httpd.py:828-832` 的注释就是为此写的），且它不是业务数据 |
| 静态资源 | `/`、`/js/*`、`/css/*`、`/assets/*`、`/img/*`、`/favicon.ico` | `_dispatch` 前置分支（`:399-404`）+ `PUBLIC_ENTRIES`（`config.py:22`）→ 连 `/api/` 前缀都不进。若拦了，页面本身打不开，改密表单也加载不出来 |

**形式**：

```python
# httpd.py —— 归一化路径（见 §10.5.6），不是 self.path
PASSWORD_CHANGE_EXEMPT = frozenset({
    '/api/health',
    '/api/auth/session',
    '/api/auth/profile',
    '/api/auth/me',
    '/api/auth/password',
    '/api/auth/logout',
})
```

**准入判据（以后想往里加一条，先过这三问）**：
① 它是"改密必须走的"（password）？② 它是"渲染改密页必须读的"（profile/me，严格说只有 session 必需，profile 是为兼容既有 `hydrateIdentity()`）？③ 它是"健康/探针/退出"这类**与业务数据无关**的基础设施？
三问全否 → **不许加**。特别是"让他先看一眼工作区""让他导出自己的数据""让他先建个团队"这类"业务上方便"的请求，一律拒绝 —— 闸门的价值就在于它是**没有商量余地的边界**。

#### 10.5.4 清零与事务纪律

改密成功后必须**在同一事务、同一次提交**里做三件事（顺序无关，原子性有关）：

1. `UPDATE users SET password_hash = ?, must_change_password = 0, updated_at = ? WHERE id = ?`
2. `DELETE FROM sessions WHERE user_id = ? AND token_hash <> ?`（踢其它会话，保留当前 —— 既有行为，`httpd.py:751-753`）
3. `conn.commit()`

风险点：若第 1 步只写了 `password_hash` 而忘了清零标记，用户改完密码仍被 403 拦住 —— **且再改一次也没用**（因为每次都会走同一段代码），表现为"改密成功但永远用不了"，是本期最容易被漏测的故障。建议 QA 补一条断言：改密成功后，**同一个会话**立刻 `GET /api/workspace` 必须 200（而不是 403）。

#### 10.5.5 前端如何知道"我该去改密"

**唯一权威来源是 `user` 对象上的两个新字段**（加法式扩展，非破坏性）：

| 字段 | 类型 | 出现位置 |
|---|---|---|
| `mustChangePassword` | bool | `GET /api/auth/session` 的 `user`、`GET /api/auth/profile`/`me` 的 `user` 与展平层、`POST /api/auth/login` 的 `user`、`POST /api/admin/accounts` 的 `user` |
| `isSystemAdmin` | bool | 同上 |

实现要点（一处改、四处生效）：
- `_current_user` 的 SELECT 加 `u.is_system_admin, u.must_change_password`（`httpd.py:289-294`），返回 dict 加两个 `bool(...)` 键（`:309`）；
- `_user_public`（`:593-594`）加入这两个键 → `h_session`（`:619`）与 `h_profile`（`:624`）自动获得；
- `h_login` 自己组 dict（`:720`），需单独加这两个键；
- **`bool()` 要加 `.get(...)` 兜底**，否则任何漏改的 dict 会把 500 抛在渲染路径上。

前端行为约定（交前端）：
- 启动时 `getSession()` 返回 `user.mustChangePassword === true` → 直接渲染"设置新密码"页，**不渲染业务界面**（服务端已经拒绝，前端只是不要让人白撞）。
- 收到 `403 PASSWORD_CHANGE_REQUIRED`（例如另一个标签页已经改过、或界面状态陈旧）→ 也跳该页，**不要**当成普通错误弹 toast。
- 该页只有两个出口：`POST /api/auth/password` 成功 → 重新 `getSession()` 再进业务；`signOut()` → 回登录页。

#### 10.5.6 一处真实会踩的实现陷阱：路径归一化

`_dispatch` 归一化路径用的是**局部变量**：

```python
path = parsed.path.rstrip('/') or '/'      # httpd.py:389 —— 局部变量！
```

而 `self.path` 是原始值。若 `_require_user` 里比对 `self.path`，那么 `POST /api/auth/password/`（带尾斜杠）会**不在白名单**里 → 403 → **用户永远改不了密码**。而 §1.1 已明确"`/api/health/` 与 `/api/health` 等价"是既有行为（`httpd.py:389`），所以尾斜杠请求是真实会发生的。

**修法（最小改动）**：在 `_dispatch` 里 `self._path = path`（`:389` 之后），`_require_user` 读 `self._path`。不要用 `self.path.rstrip('/')` 各自算一遍 —— 两处算法一旦分叉，就是上面那个故障。

#### 10.5.7 临时口令的时效：**裁决定稿 = 不做有效期、不加第三列**

`10_CR-2026-001` 的 EX-029/O-6 曾提出「临时口令 72 小时有效期」，并给了"加 `temp_password_expires_at` 列"与"用 `users.updated_at` 推算"两个备选。**主理人 2026-11-14 裁决：都不采纳。本期只加 `is_system_admin`、`must_change_password` 两列。**

| 结论 | 内容 |
|---|---|
| 列 | **不加** `temp_password_expires_at`；`_MIGRATIONS` 只有 v1（`is_system_admin`）、v2（`must_change_password`），`schema_version` 终值 = 2（`05` §13） |
| 时效保证 | 由**"首登必须改密"这道闸门**保证，不由时间保证。语义差别是刻意接受的：临时口令的风险窗口是"从签发到首次登录"，而不是"从签发到 72 小时" |
| 一次性口令三不 | **不落库**（库里只有 PBKDF2 散列，明文只存在于 httpd 局部变量与响应体）、**不落日志**（不写 `app_logs`、不进 `_log_access`、前端不进 `log()`）、**不可再次获取**（没有"查看初始口令"接口，也没"重置他人密码"端点） |
| 丢失怎么办 | 只能由管理员**重新创建**（`POST /api/admin/accounts`，不触碰已有账号）或运维 `--set-password` 重置（会置 `must_change_password=1`） |
| 错误码 | **不新增**。既不做过期，就没有"过期"这一错误态 |

**必须留档的反例（为什么"用 `updated_at` 推算"是错的）**：`h_login` 在 `needs_rehash` 时会执行 `UPDATE users SET password_hash = ?, updated_at = ?`（`httpd.py:716-718`）——**每次登录都可能刷新 `updated_at`**。于是"72 小时"会变成"最后一次登录后 72 小时"，对活跃用户**永不过期**：文档写着有期限、代码永远不触发，排障时没人查得出来。这类"看起来有、实际自我续期的假机制"比"明确不做"危险得多 —— 记在这里，防止下一期有人重新捡起这个点子。

#### 10.5.8 判定顺序（与 `10_CR` EX-030 对齐）

`h_change_password` 里，`must_change_password` 的清零**必须发生在原密码校验通过之后**：`INVALID_OLD_PASSWORD`（`httpd.py:744-746`）分支不得改动标记，否则一次错误尝试就把用户"放行"出去了。实现时照既有顺序：校验原密码 → `UPDATE`（`password_hash` + 清零）→ 删其它会话 → 单次 `commit`（`httpd.py:744-754`）。

### 10.6 CLI 契约

#### 10.6.1 命令总览（三个命令**正交**，各管一件事）

| 命令 | 建号 | 设口令 | 授系统管理员 | 清必须改密 | 幂等 |
|---|---|---|---|---|---|
| `--create-admin <email>` | 不存在则建 | 新号生成随机口令；**已存在则不动口令** | ✔ | **✔ 一律置 1** | ✔ |
| `--grant-admin <email>` | ✘（不存在就报错退出） | ✘（不动口令） | ✔ | **✔ 一律置 1（裁决）** | ✔ |
| `--set-password <email>`（既有） | 不存在则建（**不授予管理员**） | ✔ 交互输入 | ✘ | **✔ 一律置 1（裁决）** | 可重复执行（每次重置） |

> **裁决定稿（主理人 2026-11-14）**：三个命令**一律**把 `must_change_password` 置 1。判据不是"有没有产生新口令"，而是"**口令这一环是否经过运维之手**"。`--grant-admin` 看似不动口令，但一次提权之后，那个账号的旧口令很可能已经被共享/记录在某个聊天窗口里 —— 强制重设是唯一能保证"提权后的口令一定由本人设定"的办法。这是一次性摩擦，换一条不变量。

设计意图：**一个命令只做一件事**，组合出运维需要的动作，而不是做一个"万能 admin 命令"（万能命令的每一次扩展都在扩大误操作半径）。

#### 10.6.2 `--create-admin <email>`

参数：`<email>` 必填，必须过 `EMAIL_RE`（`httpd.py:41`；建议把邮箱正则下沉到 `security.validate_email()`，让 CLI 与 HTTP 共用同一规则，避免两处分叉 —— 目前 `server.py` 已 `from pyapp.httpd import ...`，`:29`）。

行为矩阵：

| 前置 | 行为 | 输出 | 退出码 |
|---|---|---|---|
| 邮箱不存在 | 建号（`is_system_admin=1`、`must_change_password=1`）+ 生成随机口令 | 打印口令**一次** | 0 |
| 邮箱已存在、`is_system_admin=0` | **不改口令**，只置 `is_system_admin=1` | 「已存在该账号 → 已授予系统管理员（口令未改动；如需重置请用 `--set-password`）」 | 0 |
| 邮箱已存在、`is_system_admin=1` | 无变化 | 「该账号已是系统管理员（幂等，无改动）」 | 0 |
| 邮箱格式不合法 | 不写库 | 错误提示 | 2 |

**幂等性要求的原因**：引导流程会被写进部署脚本与运维手册（`09`），脚本可能被重复执行。若第二次执行就重置了口令，运维会在"我以为它只是检查一下"的时候把刚发给用户的口令改掉。

输出格式（**逐字建议**，便于运维脚本 grep）：

```
已创建系统管理员：admin@example.com
  初始密码（只显示这一次，请立即保存）：Xk7pQ2mRt9vWb4Ns
  首次登录后必须立即修改密码；该账号目前不属于任何团队。
```

已存在分支：

```
账号已存在：admin@example.com → 已授予系统管理员
  口令未改动。如需重置：python server.py --set-password admin@example.com
```

**纪律**：口令只出现在 stdout 这一处；**不得**写进 `app_logs`、不得写进 `.env`、不得出现在 `--check` 输出里（`cmd_check` 只报计数，见 §10.6.6）。

#### 10.6.3 `--grant-admin <email>`

| 前置 | 行为 | 输出 | 退出码 |
|---|---|---|---|
| 账号存在、非管理员 | `UPDATE users SET is_system_admin=1, must_change_password=1, updated_at=?` + `commit()`（**一次提交**） | 「已授予系统管理员；该账号下次登录必须先改密码」 | 0 |
| 账号存在、已是管理员（且 `must_change_password` 已是 1） | 无写入 | 「已是系统管理员（无改动）」 | 0 |
| 账号存在、已是管理员（但 `must_change_password=0`） | 只补置 `must_change_password=1` | 「已是系统管理员；已要求其下次登录改密」 | 0 |
| 账号不存在 | **不建号** | 「账号 x 不存在。请先用 `--create-admin` 创建」 | 2 |

为什么不存在时不自动建号：`--grant-admin` 的用途是"给一个**已知存在**的人授权"。若它顺手建号，一次邮箱打错（`admn@` vs `admin@`）就会**静默创建一个带随机口令的管理员账号**并打印口令 —— 而真正的那个人依然进不来。把"建号"与"授权"分开，是这个错误表现为"命令报错"而不是"线上多一个管理员"的唯一办法。

#### 10.6.4 `--set-password <email>`（既有命令，语义修订）

保留既有行为（`server.py:136-174`），修订四点：

| 项 | v1.0 行为 | v1.2 要求（含裁决定稿） |
|---|---|---|
| 建号时的身份 | 不涉及 | **明确不授予系统管理员**（`is_system_admin=0`），输出里加一句「该账号不是系统管理员」 |
| `must_change_password` | 不涉及（落 `0`，等于免改密） | **置 1（主理人裁决）**。理由：这是破窗通道，若它绕开闸门，就会留下一批"永久免改密、且密码经运维之手"的账号 —— 正是本次变更要消灭的状态 |
| 踢会话 | 已做，但**只在重置分支**（`server.py:170`：`DELETE FROM sessions WHERE user_id = ?`） | **保留，且与置 1 在同一次 `commit()` 里**。"踢掉旧会话 + 强制改密"是同一件事的两半：只踢不置 1，旧口令仍可再次登录；只置 1 不踢，已登录的会话不受影响。**只做一半等于没做** |
| 实现位置 | `server.py:160-170` 直接拼 SQL（建号分支 `:161-166`、重置分支 `:167-169`） | **收敛到 `store.reset_password(...)`**，与 HTTP 建号共用事务与散列纪律；否则本项目会出现**第三处**建号逻辑（`h_register` 已删、CLI 一处、store 一处）。见 `04` R-15 |

**对既有运维习惯的影响（必须写进 `09` 的手册与话术）**：

1. 运维重置口令后，**必须明确告知用户"登录后会被要求立即改密"**，否则用户会以为系统出错（"我密码没错，怎么进不去业务界面"）。这一句要写进重置话术模板。
2. 重置后**不能**再把该口令当作"长期凭据"分发（旧习惯是"给他设个密码，让他用"）。本期语义是**临时凭据**：发出去、对方登录、对方改掉、回执确认。
3. **`--set-password` 是 break-glass，不是日常开通账号的手段**。日常建号走 `POST /api/admin/accounts`（系统管理员/团队管理员自助完成，运维不参与）。这条职责划分要写清，否则运维会继续当"人工账号机"。

建议的 store 侧函数（三个函数都遵循"单事务、单提交、取回在提交前"）：

```python
def create_account(conn, actor, *, email, name=None, team_id=None, role=None,
                   password_hash, is_system_admin=False, must_change_password=True)
def grant_system_admin(conn, email)   # -> dict|None（不存在返回 None，不建号）；置 is_system_admin=1 + must_change_password=1
def reset_password(conn, email, password_hash, *, create_if_missing=True,
                   must_change_password=True)   # -> {'created': bool, 'user': {...}}；同一事务内删该用户全部会话
```

#### 10.6.5 随机初始口令生成规范（标准库，零依赖）

| 项 | 建议 | 理由 |
|---|---|---|
| 模块 | `secrets`（已在用，`security.py:3`） | `random` 是 Mersenne Twister，**不是**密码学安全随机源，绝不可用于生成凭据 |
| 函数 | `security.generate_temp_password(length=16)` | 与 `new_token()` / `new_user_id()` 放在一起，有名字、可单测 |
| 长度 | **16** | 熵 ≈ 16 × log₂57 ≈ **93 bit**；远高于 `validate_password` 的 8 位下限（`security.py:29,69-75`），也短到能一次复制 |
| 字符集 | `A-Z` 去掉 `I/O` + `a-z` 去掉 `l` + `2-9`（共 57 个） | 去掉 `0/O`、`1/l/I` 三对视觉混淆字符（口令是要靠人**手抄/口述**传递的）；不含空格、引号、反斜杠、`$`、`-`，避免 shell 粘贴与 `.env`/存储串（PBKDF2 存储串用 `$` 分隔，`security.py:39`）产生歧义 |
| 组成保证 | 前 3 位分别取大写/小写/数字各一，其余 13 位取全集，再用 `secrets.SystemRandom().shuffle()` 打乱 | 保证任何"必须含大小写+数字"的策略都能过；避免"全是字母"这种看起来不像口令的极端（概率上极小，但被人看见一次就会被质疑） |
| 交付 | 只在 CLI stdout / 建号响应体出现**一次** | 无"查看初始口令"接口；丢了只能 `--set-password` 或由管理员重置 |

#### 10.6.6 引导流程（首次部署的唯一路径，交 `09` 落 SOP）

```text
1. python server.py --check                       # 建库 + 打印配置（含 systemAdminCount 建议新增，见下）
2. python server.py --create-admin admin@example.com   # 打印一次性初始口令
3. 浏览器打开 → 用该邮箱 + 初始口令登录 → 被强制改密 → 设置新密码
4. 系统管理员登录后建团队管理员账号（POST /api/admin/accounts，指定 teamId + role=admin）
5. 团队管理员登录（强制改密）→ 为本团队建成员 / 或用邀请码让已有账号加入
```

**`--check` 的建议增强**：`cmd_check`（`server.py:86-105`）目前报 `counts.{users,teams,workItems}`。建议加 `systemAdmins`（`SELECT COUNT(*) FROM users WHERE is_system_admin = 1`）与 `pendingPasswordChanges`（`must_change_password = 1` 的数量）—— 这两个数字是"引导做了没有""还有谁没改初始口令"的唯一自检依据；`config.describe()` 是纯配置（无 DB），不要把 DB 计数塞进去。

**计数核对**：v1.0 共 **27** 个 `export`（`grep -c '^export ' js/api.js` = 27）。增 2 删 2 ⇒ **仍 27**。

两条实现注记：

1. **`request()` 不新增 `kind`**。`PASSWORD_CHANGE_REQUIRED` 是 403，而 `request()` 只在 401 时打 `kind:'unauthenticated'`（`api.js:74`）。前端应按 `err.code === 'PASSWORD_CHANGE_REQUIRED'` 判定，而不是改传输层去加 `kind` —— 改传输层会影响 `.smoke/auth-flow-test.mjs` 的表驱动断言（`:371-388`），收益不抵风险。若确实想要 `kind`，属另一条变更，需单独登记。
2. **`createAccount` 返回的 `password` 绝不能进 `log()`**。`SENSITIVE_KEYS` 已精确匹配 `password` 并在 `sanitize()` 里脱敏（`api.js:230-231,241-244`），但那只是**兜底**；正确做法是根本不传。也**不要**写进 `localStorage`/`sessionStorage`/`state`（刷新即失，正是"只显示一次"的语义）。
3. **404 要给一条可读兜底（按 `status` 判，不是按 `code`）**。已下线端点（`register`/`check-email`）返回 `404 NOT_FOUND`，`message` 是「接口 /api/auth/register 不存在」—— 旧标签页的用户看到这句会以为是系统故障，**会去重启服务**（产品侧的真实担忧）。所以在 `friendlyError` 的最前面加一条：

   ```js
   if (error?.status === 404) return '该功能已下线，请刷新页面；账号由管理员创建。'
   ```

   **必须按 `status` 而不是按 `code` 判**：静态资源的 404 由 `_serve_static` 返回 `text/plain "not found"`（`httpd.py:585-586`，不是 JSON 错误体），`request()` 解析出 `payload=null` → `detail={}` → `err.code` 是 `null`、只有 `err.status` 是 404。按 `code` 判会漏掉这一类。这条**不新增错误码**，只是 `friendlyError` 多一个分支，与 §10.2 的"404 定稿"完全兼容。

   **代价（写下来免得以后当 bug 查）**：`api.js` 内部**路径写错**也会得到这句文案（开发期表现为"打开某个页面提示功能已下线"）。所以排障时**不要看界面文案**，看 DevTools 的 Network 里那条请求的实际 URL —— 这是唯一能区分"端点真的下线了"与"前端路径拼错"的地方。接受这个代价的理由：面向用户的收益（不再误以为系统故障）大于开发期的这点不便，而开发期本来就在看 Network。

**`--import` 的终版口径（主理人 2026-11-14 二次改判，与 `05` §13.6 R3 / §13.9 裁决 2 一致）**

口径经过两轮：先想"给 `users` 加导入列白名单"→ data-modeler 反证"能拿到备份的人已经能伪造登录态，白名单没意义"→ **撤销列裁剪**；但撤销的是裁剪，**不是"改代码"**。

| 项 | 终版要求 |
|---|---|
| 列裁剪 | **不做**。不裁剪任何列集合，`password_hash` 的导入行为不变，`import_all` 的 `INSERT OR REPLACE` 语义不变 |
| **必须做的** | 在 `store.import_all` 捕获 `sqlite3.OperationalError` 中的 `no such column` / `no such table`，翻译成 `StoreError('IMPORT_SCHEMA_MISMATCH', '备份文件的结构与当前库不一致：请先运行 --check 让数据库升级到最新结构，再导入', 400)`；**其余 `OperationalError` 原样上抛，不吞** |
| 配套 | `09` 的灾难恢复流程强制"**导入前先 `--check`**"（与"`--import` 前先删库文件"并列） |
| 保留 | "备份文件按凭据级敏感文件管理"（`chmod 600` / 不进版本库）—— 这半不变 |

**为什么不做列裁剪（这条比结论重要，留档）**：白名单会让"新备份 → 旧结构库"变成**静默成功** —— `is_system_admin` 被悄悄丢掉，还原后实例**零管理员**、没人能建号，而操作者看到的是"导入成功"，于是不会去查为什么建号按钮没了。**一个明确的失败 + 一句"先 `--check` 升级结构"，比一次成功的静默降级安全得多。**

**由此新增一个错误码**：`IMPORT_SCHEMA_MISMATCH`（400，CLI 路径）。它不出现在 HTTP 侧 —— `import_all` 只被 `server.py --import` 调用（`store.py:455-478`）。错误码总数因此 **38 → 39**（见 §10.8 与 §2.2 的合计口径修正说明）。

**同时补一条护栏（data-modeler 核查发现的缺口）**：`test_api.py:808` 只断言 `password_hash` 不出现在 `GET /api/export` 里，**没有断言 `is_system_admin` / `must_change_password` 不出现**。`export_visible` 今天用显式 5 列 `SELECT`（`EXPORT_USER_COLUMNS`，`store.py:399`）所以不漏，但这条纪律**没有护栏** —— 哪天有人把它改成 `SELECT *`，两个权限列就会跟着进导出响应，而测试全绿。要求：在同一用例补 `assertNotIn('is_system_admin', body)` 与 `assertNotIn('must_change_password', body)`。
