## 1. 运维角色与日常节奏

### 1.1 角色与值班

本项目为「1 人 + AI 协作」的极小团队，**运维角色由用户（李鹏 / Leo）本人承担**，无独立 SRE。
因此手册的设计目标是：**命令可复制、判定可勾选、异常可一个人处理完**，不引入需专职维护的组件。

| 职责 | 承担人 | 说明 |
|---|---|---|
| 服务器 / SSH / 云安全组 | 用户本人 | 阿里云控制台 + SSH 密钥 |
| `.env` 与 AI 密钥保管 | 用户本人 | 见 §7 台账 |
| 发布 / 回滚执行与 G6 放行 | 用户本人 | 唯一放行权 |
| 告警接收与处置 | 用户本人 | 告警渠道未定，见 §10 开放问题 Q5 |
| 备份与演练记录签字 | 用户本人 | §6.5 记录表 |

> **残余风险**：单人有值守空窗（夜间/假期）。`GTD_WATCHDOG_FAILOVER` 默认 0 只告警不自动降级（该开关的 `.env` 读取已修好 —— 一旦在 `.env` 里取消注释即**真的**启用自动降级，见 §7.2），
> 意味着**无人看告警时不会自动恢复**。上线前必须明确告警渠道与响应时限，否则自愈能力等于零。

### 1.2 每日 / 每周 / 每月 / 每次发布

以下命令均在项目根目录 `/opt/gtd4teams` 执行；`--noproxy '*'` 是既有纪律（防环境代理把本机探测带偏）。

#### 每日（1~2 分钟）

```bash
cd /opt/gtd4teams
sudo bash deploy/release.sh --status                          # 活跃槽位 / 镜像 / 上一版 / 公网入口
ACTIVE=$(sed -n "s/^ACTIVE_COLOR='\(.*\)'/\1/p" deploy/run/state.env)
PORT=$(bash -c "source deploy/lib.sh; color_port '$ACTIVE'")   # 从 .env 读端口，不硬编码
curl -s --noproxy '*' "http://127.0.0.1:$PORT/api/health"; echo   # 直连活跃槽位，看 build
curl -s --noproxy '*' http://127.0.0.1:80/api/health; echo         # 走 Caddy 入口
cat deploy/run/state.env                                       # build 是否与 ACTIVE_IMAGE 对应
tail -20 /var/log/gtd4teams-backup.log 2>/dev/null || true    # 昨夜备份结果
tail -20 /var/log/gtd4teams-watchdog.log 2>/dev/null || true  # 看门狗异常计数
df -Pm / | awk 'NR==2{print "磁盘可用(MB):",$4}'             # < 2048 需处理（见 SOP-06）
```

每日必看三项：**活跃槽位是否只有一个、`/api/health` 的 `build` 是否等于 `state.env` 的 `ACTIVE_IMAGE` 去掉 `gtd4teams:` 前缀、备份日志是否有新文件**。

#### 每周（5~10 分钟）

```bash
cd /opt/gtd4teams
sudo bash deploy/rollback.sh --list             # 本地镜像清单，确认 >= 2 个可回滚版本
docker images gtd4teams --format '{{.Tag}} {{.CreatedAt}} {{.Size}}'
cat deploy/run/state.env                        # ACTIVE_*/PREVIOUS_*/LAST_RELEASE_AT
ls -lh /var/backups/gtd4teams/ | tail -20      # 备份份数、大小、时间；权限应为 -rw-------
docker system df                               # 镜像/卷/构建缓存占用
docker compose logs --since 7d app-blue 2>&1 | grep -c -- '  ! ' || true   # 一周 4xx/5xx 计数
docker compose logs --since 7d caddy 2>&1 | grep -iE 'error|warn' | tail -30 || true
```

**每周业务健康抽查**（零依赖，标准库只读查询；时间串写法见 E7，务必用 `strftime` 版）：

```bash
docker compose exec -T app-blue python -c "
import sqlite3
c=sqlite3.connect('file:/data/gtd4teams.db?mode=ro',uri=True)
q=\"select count(*) from app_logs where created_at >= strftime('%Y-%m-%dT%H:%M:%SZ','now','-7 days') and level in ('error','warn')\"
print('近7天 error/warn:',c.execute(q).fetchone()[0])
print('团队数:',c.execute('select count(*) from teams').fetchone()[0])
print('事项数:',c.execute('select count(*) from work_items').fetchone()[0])
"
```

#### 每月（30 分钟，建议月初低峰）

1. **备份恢复演练**（§6，在临时卷上做，不碰生产数据）——必做，记录进 §6.5 表。
2. **告警通道演练**：手工触发一条测试告警，确认能收到（渠道未定则补记入 §10 Q5）。
3. **账号与权限复核**：`users` 表账号清单、离职/临时账号清理（§7）。注册口令已随 CR-2026-001 废弃，**无需轮换**。
4. **TLS 证书有效期**（有域名时）：`echo | openssl s_client -connect 域名:443 -servername 域名 2>/dev/null | openssl x509 -noout -dates`。
5. **Docker / 系统更新评估**：`systemctl status docker`、`live-restore` 是否仍开启（[零停机发布方案.md](../零停机发布方案.md) §7）。
6. **旧文档与配置一致性抽查**：`deploy/env.example` 与 `docker-compose.yml` 的变量是否仍对得上（本次已发现失配，见 §9）。

#### 每次发布（严格按 §5 两张清单）

```bash
# 发布前：清空单、备份、构建标识基线
sudo bash deploy/release.sh --status
bash deploy/backup.sh                              # 或由 release.sh 自动备份（默认开启）
# 发布：不带 --no-probe / --no-backup / --skip-tests
sudo bash deploy/release.sh
# 发布后：切流窗口探测输出人工复核（不只是看 exit code，见 §9 R4）
cat deploy/run/state.env
curl -s --noproxy '*' http://127.0.0.1:<活跃槽位端口>/api/health   # build 必须 == 本次 TAG 去掉前缀
bash deploy/smoke.sh http://127.0.0.1:<活跃槽位端口> <本次构建标识>
```

**发布后守候 30 分钟**：盯 §3 应用层指标（4xx/5xx、写锁关键字、`app_logs` error 速率）。

## 2. 首次上服务器验证清单【最高优先级】

> **规则**：按 V1→V10 顺序执行，**任何一项「未验证/失败」都不得跳过**。每项给出「已验证 / 未验证」勾选位与失败分支。
> 全部通过后由用户签字，作为 G6 放行证据归档。
> 勾选位含义：**「服务器已验证」**（与 §0.3 的「本机实跑」分开记，二者不能互相替代）。

### 2.1 顺序总表

| 序 | 验证项 | 服务器验证 | 失败时处理分支 | 阻塞级别 |
|---:|---|:---:|---|---|
| V1 | 环境与工具链（docker / compose / python3 / curl / openssl / 磁盘） | ☐ 已验证 ☐ 未验证 | 缺件则安装；磁盘 < 2GB 先清理 | ⛔ |
| V2 | 脚本语法 + 零停机前提测试 **在 Linux 上复跑** | ☐ 已验证 ☐ 未验证 | **不绿 → 所有发布强制 `--stop-first`**，并回报失败用例 | ⛔ |
| V3 | `docker compose config -q` 编排最终解析 | ☐ 已验证 ☐ 未验证 | 对照锚点/缩进排查，禁止手工绕过 | ⛔ |
| V4 | `python3 server.py --check` + 容器内 `--check` | ☐ 已验证 ☐ 未验证 | 看 `ok` / `tables` / `counts` | ⛔ |
| V5 | 首次部署 `install.sh`：**成功路径 + 注入失败路径各跑一次**，并对五组输出**人工逐行复核**（三条判据见下方「V5 判定」；**前置条件不满足，本条判据即为假测试**） | ☐ 已验证 ☐ 未验证 | 三条判据任一不满足 → **本项不通过**；脚本已在「第 6 节 冒烟验证」`die`（`exit 1`，在 `save_state` 之前，现 `install.sh:135~143`），不写 `state.env`、不打横幅，**无需人工清状态文件**；按 `smoke.sh` 五组 `✗` 定位后重跑（幂等）。⚠️ 此时容器**仍在运行**，不打算当场修须 `docker compose down` | ⛔ |
| V6 | `caddy validate`（一次性容器 / 运行中 exec） | ☐ 已验证 ☐ 未验证 | 对照 `deploy/run/Caddyfile` 与模板；旧配置仍在生效 | ⛔ |
| V7 | 槽位端口绑定 + 单活跃不变量 + `state.env` | ☐ 已验证 ☐ 未验证 | 见 SOP-10；绑定必须是 `127.0.0.1` | ⛔ |
| V8 | TLS / 域名 / 证书与安全组 | ☐ 已验证 ☐ 未验证 | 见 [零停机发布方案.md](../零停机发布方案.md) §8.4、SOP-10 | ⛔（有域名时） |
| V9 | **19 个受限路径的公网复核**（走 Caddy，非槽位直连） | ☐ 已验证 ☐ 未验证 | 任一非 404 → 停发布、查白名单 | ⛔ |
| V10 | 备份 + **隔离卷恢复演练** + cron/watchdog/live-restore | ☐ 已验证 ☐ 未验证 | 见 §6；演练失败不得放行 | ⛔ |

> **V5 判定（首次部署 · 冒烟门禁）**
>
> **前置①（不满足则下面三条是假测试）**：必须是**没有 `deploy/run/state.env`** 的首次部署。
> 已部署过的机器会走 `install.sh` 的「4. 已经部署过」分支**直接 `exit 0`，根本到不了冒烟**，
> 测试会"通过"而实际什么都没测到。做法：先备份 `deploy/run/state.env` 再移走（确认 `--status` 已无可用状态），跑完还原。
>
> **前置②**：判据 2 的「md5 相同」在首次部署下**不可执行**（文件本来就不存在，`md5sum` 会直接报错），
> 故写作「md5 相同 **或** 运行前后均不存在」。
>
> **三条判据（全中才算「已验证」）**：
> 1. 失败路径 `install.sh` 退出码 **≠ 0**；
> 2. `deploy/run/state.env` 运行前后 **md5 相同**（**或**运行前后均不存在）；
> 3. 控制台**不含**「部署完成」。
>
> **失败时**：脚本在「第 6 节 冒烟验证」里 `die '未通过冒烟门禁，部署中止。'` → 不写 `state.env`、不打横幅，
> **不会假成功**，因此无需人工清状态文件；按 `smoke.sh` 五组 `✗` 定位、修好后重跑（幂等）。
> **仍必须人工判定** —— `die` 只报"未通过"，不指出是哪一项 `✗`：
> **门禁替你判断，日志替你定位，两件事不能互相替代。**
> ⚠️ 此时**容器仍在运行**。若不打算当场修，须手工 `docker compose down`，否则暴露面风险仍在。

**门禁判定**：V1~V10 全勾「已验证」+ V2 全绿 + **§0.4 的 G5 七项阻塞全部关闭 / G4 L0b 通过 / G-01 实测通过** → 方可执行第一次 `release.sh`。
**V2 不绿的退路**：`sudo bash deploy/release.sh --stop-first`（受控的几秒中断，换"任何时刻只有一个写者"），并把失败输出回报主理人。

### 2.6 V9：19 个受限路径的**公网**复核（走 Caddy 入口）

`deploy/smoke.sh` 在发布流程里是**直连槽位端口**的（绕开 Caddy 便于定位）。但上线验收必须额外证明
**公网入口（Caddy → 槽位）这一整条链路**没有把源码/数据暴露出去。以下是独立复核命令：

```bash
BASE=https://你的域名          # 无域名时用 http://127.0.0.1:80
EXTRA=(); [[ "$BASE" == https://* ]] && EXTRA=(-k --resolve "你的域名:443:127.0.0.1")
PATHS=(
  '/server.py' '/pyapp/db.py' '/pyapp/policy.py' '/pyapp/config.py' '/pyapp/httpd.py'
  '/tests/test_api.py' '/README.md' '/Dockerfile' '/docker-compose.yml'
  '/.env' '/data/gtd4teams.db' '/deploy/run/state.env'
  '/js/../server.py' '/js/%2e%2e/server.py' '/js/..%2Fserver.py'
  '/js/../pyapp/db.py' '/css/../pyapp/db.py' '//server.py' '/js//api.js'
)
for p in "${PATHS[@]}"; do
  code=$(curl -s --noproxy '*' --path-as-is "${EXTRA[@]}" -o /dev/null -w '%{http_code}' --max-time 6 "$BASE$p")
  printf '%-30s -> %s\n' "$p" "$code"
done
# 判定：19 行必须【全部 404】。任一 200/403/301 都算失败。
# 反向确认白名单没被误伤：curl -s --noproxy '*' "${EXTRA[@]}" -o /dev/null -w '%{http_code}\n' "$BASE/"  → 200
```

> `--path-as-is` 不可省：curl 默认会规范化 `..`，那样"目录穿越被拦住"是假测试（请求根本没带 `..` 发出去）。
> 清单与 `deploy/smoke.sh` 的 `_LEAK_PATHS` 逐字一致（E6 精确计数 19 条）。

## 3. 监控指标与告警阈值

### 3.1 采集能力盘点（零依赖，不引入 Prometheus / ELK）

现有可观测面只有四样，全部用得上，**不新增任何组件**：

| 来源 | 位置 | 能拿到什么 | 注意事项 |
|---|---|---|---|
| `/api/health` | 免鉴权 HTTP | `ok` / `version` / **`build`** / `storage` / `llmConfigured` | 槽位直连与公网入口都打，用于定位哪一层坏 |
| `app_logs` 表 | SQLite（`/data/gtd4teams.db`） | 前端上报的 `level`(info/warn/error)、`scope`、`event`、`message`、`created_at` | **不是服务端访问日志**；`POST /api/logs` 允许匿名写入、按 IP 限流 10 次/15 分钟（🔍 源码核实） |
| `docker compose logs` | json-file，`10MB×3` 轮转 | `_log_access` 只在 `status>=400` 时打印 `  ! {method} {path} -> {status}`；异常栈 `Traceback` | 用 `grep -c -- '  ! '` 统计 4xx/5xx；无匹配时 `grep -c` 返回 1，脚本里要 `\|\| true` |
| 主机 / Docker | `df` `free` `docker system df` `docker inspect` `cron` | 磁盘、内存、卷/镜像占用、容器健康与重启次数、备份新鲜度 | 系统自带命令，零依赖 |

> **时间串陷阱（E7 实测）**：`db.now_iso()` 产出 `2026-11-13T03:44:10Z`，
> 而 SQLite `datetime('now','-1 hour')` 产出 `2026-11-13 02:44:10`（空格）。
> 字符串比较时 `'T' > ' '`，导致**恒真**、把历史数据全算进窗口。
> 所有 `app_logs` 时间窗 SQL 必须写 `strftime('%Y-%m-%dT%H:%M:%SZ','now','-1 hour')`。

**告警渠道（最小可行版，全部用现有工具）**：`cron` 定时跑一段 bash（内联命令，不新增脚本文件）
→ 结果追加 `/var/log/gtd4teams-monitor.log` → 超阈值时用一条 `curl` 推企业微信/钉钉群机器人 webhook。
Webhook URL 属敏感项，**放 `/etc/gtd4teams/alert.env`（`chmod 600`），不写入 `.env`、不进版本库**。
后续增强版可接阿里云云监控自定义脚本，但那属于新增依赖，本次不引入、也不建议先上。

> webhook 推送待渠道确认后，在 `ALERT` 分支补一条
> `curl -s --noproxy '*' -X POST -H 'Content-Type: application/json' -d '{"msgtype":"text","text":{"content":"GTD4Teams 告警"}}' "$ALERT_WEBHOOK"`；
> `$ALERT_WEBHOOK` 从 `/etc/gtd4teams/alert.env` 读取，**不写死、不入库**。

### 3.4 日志与监控点清单（严格模式必填）

| 日志/信号 | 位置 | 保留 | 监控点 | 失败时可见性 |
|---|---|---|---|---|
| 应用 4xx/5xx 与异常栈 | `docker compose logs app-blue/app-green` | json-file `10MB×3` | `  ! ` 行、`Traceback`、锁错误 | 容器销毁即丢，需及时 grep |
| 前端运行日志 | `app_logs` 表（共享卷） | 随库；`LOG_LIMIT=400` 只影响工作区读取 | error/warn 速率、异常 event | 持久，但匿名可写、可被灌水 |
| Caddy 访问日志 | `caddy-data` 卷 `/data/access.log` | `10MB×3` | 5xx、证书/ACME 报错 | `docker compose exec -T caddy` 或挂卷读 |
| 发布/回滚决策 | `deploy/run/state.env` + 各脚本 stdout | 不入版本库 | `ACTIVE_*` / `PREVIOUS_*` / `LAST_RELEASE_AT` | 建议每次发布 `tee` 留档 |
| 发布期测试门禁 | `deploy/run/tests.log` | 运行期 | L0/L1 是否真跑（防"跳过测试还以为跑了"） | `release.sh` 在缺 python3/node 时只 warn |
| 备份/看门狗 | `/var/log/gtd4teams-{backup,watchdog}.log` | 自行 logrotate | 备份成败、streak 计数 | cron 日志停更本身即告警项 H6 |

## 4. 故障处理 SOP

> 统一六段：**现象 → 快速判断（命令）→ 止血 → 根因 → 恢复 → 复盘**。
> 通用第一原则：**先止血、再根因、后补测试与复盘**（Hotfix 纪律）。
> 通用第二原则：任何"看起来成功"的发布/恢复，都要用 `build` 标识或数据计数**实证**，不能只看"端口通了"。

### SOP-01 新槽位起不来（`wait_healthy` 120s 超时）

- **现象**：`release.sh` 报「新槽位未能在 120 秒内变为 healthy —— 未做任何切流，线上仍是旧版本」。
- **快速判断**：
  ```bash
  sudo bash deploy/release.sh --status
  docker compose ps -a --format '{{.Name}} {{.Status}}'
  docker compose logs --tail 60 app-green            # 换成目标槽位
  docker inspect -f '{{json .State}}' gtd4teams-green | python3 -m json.tool
  docker compose exec -T app-green python server.py --check 2>&1 | head -30
  ```
- **止血**：**什么都不用做，线上未受影响**（脚本明确不切流）。不要为了"让它起来"去手动改 Caddy 或停旧槽位。
  若用了 `--stop-first`，旧槽位已被停 → 立即拉回：`docker compose up -d --no-build app-blue`（按实际活跃色）。
- **根因**：① 新版启动就崩（构建自检应已拦住，仍崩说明是运行期数据相关）；② 数据卷权限/只读根文件系统；
  ③ 两个进程同时建表抢写锁（`attempt to write a readonly database`，见 [零停机发布方案.md](../零停机发布方案.md) §2.4）；
  ④ 端口被占用；⑤ 镜像与实际代码不一致。
- **恢复**：修代码 → 重新 `release.sh`（会换回同一目标槽位，先 `docker compose rm -sf app-green` 清残留再发）。
  若判断是平台写锁前提不成立 → 全量改用 `--stop-first`。
- **复盘**：记录目标槽位日志全文、`tests/test_zerodowntime.py` 是否仍在服务器上全绿、是否属于库结构不兼容变更（expand/contract 纪律）。

### SOP-02 切流后 5xx

- **现象**：切流后用户报错；`probe.sh` 出现失败请求；`release.sh` 可能以 **exit 3** 结束并提示可回滚。
- **快速判断**（分层定位，30 秒内）：
  ```bash
  curl -s --noproxy '*' -o /dev/null -w '%{http_code}\n' http://127.0.0.1:<新槽位端口>/api/health   # 槽位本身
  curl -s --noproxy '*' -o /dev/null -w '%{http_code}\n' http://127.0.0.1:80/api/health            # Caddy 入口
  docker compose logs --since 3m app-green 2>&1 | tail -60
  grep -n 'reverse_proxy' deploy/run/Caddyfile                                                     # 上游顺序是否真的换了
  ```
  - 槽位 200 / 入口 5xx → Caddy 层（配置未生效、上游被健康检查摘除、reload 未落地）。
  - 槽位也 5xx → 应用/数据层（新版代码 bug、库结构不兼容、写锁）。
- **止血**：**立即 `sudo bash deploy/rollback.sh`**。引流窗口（默认 20s）内旧槽位还在跑，
  Caddy 的 `health_uri /api/health` + `health_interval 3s` 会自动把坏上游摘除、退回旧槽位——但**不要指望它，人工回滚更快**。
- **根因**：新版本代码缺陷 / 破坏性库结构变更（删列、改列语义、`NOT NULL` 无默认值）/ Caddy 热加载失败但脚本误判。
- **恢复**：回滚后确认 `build` 回到上一版、`state.env` 已互换；再用 `smoke.sh` 对回滚目标槽位复验。修 bug 后按 Hotfix 流程重发。
- **复盘**：保存 `probe.sh` 输出（失败数、最大连续成功间隔）、Caddy 日志、切流前后 `state.env` 快照；核对是否违反「一次发布只做加法」。

### SOP-03 构建标识对不上（**最隐蔽、最危险**）

- **现象**：`smoke.sh` 的「构建标识与本次发布一致」出现 ✗；或上线后 `/api/health` 的 `build` 还是上一版时间戳。
- **快速判断**：
  ```bash
  cat deploy/run/state.env
  curl -s --noproxy '*' http://127.0.0.1:8788/api/health ; echo
  curl -s --noproxy '*' http://127.0.0.1:8789/api/health ; echo      # 两个槽位都问一遍
  docker compose ps -a --format '{{.Name}} {{.Image}}'
  bash deploy/smoke.sh http://127.0.0.1:<目标端口> <本次构建标识>     # 脚本会明确给出期望/实际
  ```
- **止血**：**不要切流**。旧容器同样 healthy、同样占着端口，"端口通即发布成功"会让线上跑上一版。
  已切流的按 SOP-02 回滚。
- **根因**：目标槽位被旧容器占着，`compose up` 没重建（`image` 变了但容器没换）/ `GTD_BUILD` 未通过 `--build-arg` 注入 /
  手工 `docker run` 起了个游离容器占端口 / `GTD_IMAGE` 环境变量串了。
- **恢复**：`docker compose rm -sf app-green`（换成目标槽位）清掉旧容器后重新 `release.sh`；
  核对 `docker inspect -f '{{.Config.Env}}' <cid> | tr ',' '\n' | grep GTD_BUILD` 与镜像标签一致。
- **复盘**：把「`/api/health` 的 `build` == `state.env` 的 `ACTIVE_IMAGE` 去前缀」加入每次发布后的固定检查（§5 与指标 A2）。

### SOP-04 `caddy validate` 失败

- **现象**：`release.sh` 报「生成的配置未通过校验 … 已放弃切流」。
- **快速判断**：
  ```bash
  docker compose exec -T caddy caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile
  cat -n deploy/run/Caddyfile
  diff -u deploy/Caddyfile.template deploy/run/Caddyfile || true
  ```
- **止血**：**同样什么都不用做**——`caddy_reload()` 先 validate 后 reload，校验不过就原地放弃，
  线上仍是旧配置、服务完全不受影响（这是设计中最值得信赖的一条纪律）。
- **根因**：模板 `__UPSTREAMS__` 被替换成多行（Caddyfile 换行终结指令）/ 注释里的占位符被误替换（生成器已做保护）/
  手工编辑了 `deploy/run/Caddyfile`（下次发布会被整份覆盖）/ `deploy/run/Caddyfile` 变成了目录（首次 up 时文件不存在被 docker 建了同名目录）。
- **恢复**：改 `deploy/Caddyfile.template`（不要改 `run/Caddyfile`）；若是目录：`rm -rf deploy/run/Caddyfile` 后重跑 `install.sh` / `release.sh`。
  改完先独立 validate 再发布。
- **复盘**：确认 `caddyfile_generate` 只替换非注释行、两个上游写在同一行；把产物留档。

### SOP-05 SQLite 写锁争用

- **现象**：日志出现 `database is locked` / `attempt to write a readonly database` / `SQLITE_BUSY`；新槽位起不来或请求 500。
- **快速判断**：
  ```bash
  sudo bash deploy/release.sh --status                     # 是否两个槽位同时 Up？
  docker compose ps -a --format '{{.Name}} {{.Status}}'
  docker compose logs --since 15m app-blue 2>&1 | grep -iE 'locked|readonly|SQLITE_BUSY|Traceback' | tail -30 || true
  python3 tests/test_zerodowntime.py                      # 平台前提是否仍成立
  ```
- **止血**：停掉多余槽位，恢复「同一时刻只有一个活跃槽位」：`docker compose stop app-green`（按实际）。
  若是 `--stop-first` 场景之外的意外双写，优先停**非活跃**那个。
- **根因**：两个进程同时写（WAL + `busy_timeout=15s` 本应排队）；某次发布带了新字段/新表，新槽位启动重跑 DDL 抢锁；
  读路径 `UPDATE sessions SET last_seen_at` 曾让纯读也抢写锁（已按 300s 节流修复）；**Linux 上写锁行为至今未实跑**。
- **恢复**：确认单活跃后重试；若平台前提不成立 → 后续发布一律 `--stop-first`。
  库结构变更遵守 expand/contract：破坏性变更拆三次发布，或一次性用 `--stop-first`。
- **复盘**：记录 `test_zerodowntime.py` 在**这台服务器**的结果；Windows 报 `SQLITE_READONLY`、Linux 报 `SQLITE_BUSY` 的差异要写进交接记录。

### SOP-06 磁盘满

- **现象**：构建失败、`backup.sh` 失败、容器起不来；`df` 可用 < 2GB（`release.sh` 会提前 warn）。
- **快速判断**：
  ```bash
  df -Pm / | awk 'NR==2{print $4}'
  docker system df
  du -sh /var/lib/docker/containers /var/backups/gtd4teams 2>/dev/null
  ls -lhS /var/log/gtd4teams-*.log | head
  ```
- **止血**：**先别删数据卷**。按安全顺序释放：
  `docker image prune -f`（清悬空镜像，注意 `prune_images` 会保留最近 5 个 `gtd4teams:` 镜像）→
  清旧的 `/var/log/gtd4teams-*.log`（先 `tail` 留证）→ 再考虑 `docker builder prune`。
  **禁止** `docker compose down -v`（会删 `gtd-data` 数据卷）。
- **根因**：镜像累积 / 日志轮转失效 / 备份份数超预期（`KEEP=14`）/ `app_logs` 表被匿名灌水增长。
- **恢复**：可用 > 2GB 后重跑发布；`app_logs` 异常增长时可评估清理历史行（**先备份、先在演练卷验证**）。
- **复盘**：把 H1/H4 纳入日常巡检；确认容器日志 `10MB×3` 与 Caddy 日志 `10MB×3` 轮转真的生效（未验证项）。

### SOP-07 备份文件损坏 / 误导入

- **现象**：`--import` 后数据不对；或恢复时 JSON 解析报错；或**误把备份导进非空生产库**造成数据污染。
- **快速判断**：
  ```bash
  python3 -c "import json,sys; d=json.load(open(sys.argv[1])); print(d.get('format'), d.get('version'), {k:len(v) for k,v in d['tables'].items()})" /var/backups/gtd4teams/<文件>.json
  docker compose exec -T app-blue python server.py --check     # 当前生产库计数
  ```
- **止血**：**立刻停止一切写入**。`--import` 是 `INSERT OR REPLACE`（按主键覆盖，不清空、不去重），
  误导入不会自动消失。若尚未切流/停服，先 `docker compose stop app-blue app-green`。
  **不要反复试导入**——每次都会再覆盖一遍。
- **根因**：`store.import_all` 语义是覆盖合并；非空库里"备份里没有的行"会继续留着，得到的是**混合状态**而非还原。
  另外 `export_all` 的 `BACKUP_TABLES` = `COLUMNS.keys() + ('users','settings')`，**不含 `sessions`**（🔍 源码核实），
  所以恢复后所有人需重新登录是**预期行为**，不是故障。
  ⚠️ 同一份备份还**含 `settings` 表内 LLM 密钥明文**（见 [08](08_安全审计与上线门禁.md) R-10），
  一旦备份文件外泄，处置不止于"恢复数据"：
  ```bash
  # 1) 轮换 LLM 密钥：改 .env 的 GTD_LLM_API_KEY（或界面 POST /api/llm/config）后让容器重建
  docker compose exec -T app-blue python server.py --check     # 确认配置确实变了
  # 2) 逐账号改密（--set-password 会同时 DELETE FROM sessions，令该账号其它会话失效）
  docker compose exec -T app-blue python server.py --set-password <邮箱>   # 交互式，对 users 表每个账号执行
  # 3) 确认注册端点确实已移除（CR-2026-001）、并排查 /api/export 是否被滥用（G5 的 R-01/R-03）
  curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/auth/register   # 期望 404（端点已不存在）
  ```
  注：`--set-password` 需逐账号交互执行，仓库内没有批量改密命令；账号清单可从 `users` 表只读查询取得。
- **恢复**：走 §6.3 的**正确顺序**：停服 → 先 `rm -f /data/gtd4teams.db*` 删库文件 → 再 `--import` → 起服 → 计数校验。
  若误导入已发生且无干净备份，取最近一次完好备份按上述顺序重做；期间所有新增数据会丢失，须如实告知用户。
- **复盘**：把「恢复前先确认目标库是空库/已删库文件」列为演练必勾项；备份文件校验（JSON 可解析 + `format` 字段）纳入每月演练。

### SOP-08 回滚后数据不一致

- **现象**：`rollback.sh` 成功、旧版跑起来了，但用户看到数据缺失/多出/字段异常。
- **快速判断**：
  ```bash
  cat deploy/run/state.env
  curl -s --noproxy '*' http://127.0.0.1:<活跃端口>/api/health      # build 是否为上一版
  docker compose exec -T app-blue python server.py --check           # counts
  bash deploy/smoke.sh http://127.0.0.1:<活跃端口> <上一版构建标识>
  ```
- **止血**：先确认是**代码回滚**还是**数据回滚**问题。`rollback.sh` **不重新构建、也不动数据库**，它只换镜像；
  数据用的是同一个 `gtd-data` 卷。若数据本身被新版本写坏，回滚代码**不会修复数据**。
  必要时停服，按 SOP-07 用发布前备份恢复。
- **根因**：① 新版本带了破坏性库结构变更（违反 expand/contract），旧版读不懂新列/新表；
  ② 新版本已写入旧版不认识的数据；③ 误以为"回滚=数据也回去了"。
- **恢复**：库结构不兼容 → 只能**前滚**修数据兼容（或按三步两发布补迁移），不要反复来回切；
  数据被写坏 → 用最近备份按「先删库再导入」恢复，并接受备份点之后的数据丢失。
- **复盘**：核对本次发布是否含库结构变更；把「回滚只回滚代码，不回滚数据」写进发布说明与交接文档。

### SOP-09 账号被批量创建或滥用

- **现象**：`users` 表短时间暴增、陌生邮箱账号；`app_logs` 里大量与账号相关的事件；磁盘/库体积异常增长。
- **快速判断**：
  ```bash
  docker compose exec -T app-blue python -c "
  import sqlite3; c=sqlite3.connect('file:/data/gtd4teams.db?mode=ro',uri=True)
  print(c.execute(\"select count(*) from users where created_at >= strftime('%Y-%m-%dT%H:%M:%SZ','now','-1 hour')\").fetchone()[0])
  print(c.execute('select email,created_at,is_system_admin from users order by created_at desc limit 20').fetchall())"
  # 注册端点已移除，批量建号只可能来自"管理操作"。查是谁、什么时候执行的：
  grep -ho 'create-admin\|grant-admin\|set-password' /root/.bash_history /home/*/.bash_history 2>/dev/null | sort | uniq -c
  ```
  ⚠️ **本节原有的"限速"讨论已不适用于注册**（端点已不存在）。仍适用的一条：登录与 `POST /api/logs` 的限速是
  **进程内内存字典**（key=`邮箱|IP` / `log|IP`），不持久化、不跨槽位、容器重启即清零（🔍 源码核实）。
- **止血**：
  - ⚠️ **`GTD_ALLOW_SIGNUP` / `GTD_SIGNUP_CODE` 已失效**（CR-2026-001 移除注册端点）。**改 `.env` 不会关掉任何东西**，
    改完重建容器也不会有变化 —— 这一条原来写的是"二选一收紧注册"，现在这样操作只会浪费一次停机。
    （`.env` 里若还留着这两个键，启动横幅与 `--check` 会打印一行"已忽略"提醒，见 `pyapp/config.py`。）
  - 现在该做的：① 保留现场（先 `backup.sh`，再对 `users` 做只读导出留存证据）；② 用 `is_system_admin` 与 `created_at`
    定位批量建号的来源账号与时间窗；③ 停用/删除异常账号（**先备份**、在演练库验证 SQL）；④ 若怀疑凭据泄露，
    对该管理员账号 `--set-password` 重置并核查 `sessions` 表里的活跃会话。
- **根因**（CR-2026-001 之后）：**注册端点已从代码移除**，所以"口令泄露/为空"不再是建号入口。现在只可能是：
  管理员凭据泄露、管理操作被滥用（`--create-admin` / `--grant-admin` / 建号接口），或有人在宿主上直接改库。
  （历史根因保留在此以免误读旧记录：`GTD_SIGNUP_CODE` 为空 / 口令泄露 / `GET /api/auth/check-email` 会回传 `signupAllowed`。）
- **恢复**：异常账号清理后复核 `users` 增量归零；通知合法用户；必要时重置管理员口令（`--set-password` 会同时失效其全部会话）。
- **复盘**：确认注册端点仍为 404（`curl -o /dev/null -w '%{http_code}' http://127.0.0.1:8080/api/auth/register`）；
  把"谁有权建号、建号记录在哪查"写进交接文档。

### SOP-10 槽位端口误绑 `0.0.0.0`（**安全事件**）

- **现象**：`ss -ltnp` 显示 `0.0.0.0:8788`；或从外部 `curl http://公网IP:8788/api/health` 竟然通了。
- **快速判断**：
  ```bash
  ss -ltnp | grep -E ':(8788|8789)'
  docker compose config | grep -E 'host_ip|published|127\.0\.0\.1' | head -20
  grep -n 'GTD_TRUST_PROXY' .env docker-compose.yml
  curl -s --noproxy '*' -H 'X-Forwarded-For: 1.2.3.4' http://127.0.0.1:8788/api/health   # 观察是否可绕过入口
  curl -s -o /dev/null -w '%{http_code}\n' http://<公网IP>:8788/api/health              # 从外部机器执行
  ```
- **止血**：① 云安全组立刻封 8788/8789；② 把 `docker-compose.yml` 的 `ports` 前缀改回 `127.0.0.1:`，
  `docker compose up -d --force-recreate --no-build app-blue app-green`（或直接重新 `install.sh`）；
  ③ 若期间 `GTD_TRUST_PROXY=1`，伪造 XFF 可换掉登录限流键 → 临时把 `GTD_TRUST_PROXY` 改 0 并重建容器
  （副作用：所有请求被算成 Caddy 容器 IP，正常用户也可能被限流误伤，属**两害相权**，须尽快恢复正确绑定后改回 1）。
- **根因**：有人为排障把 `ports` 前缀从 `127.0.0.1:` 改成空/`0.0.0.0:`，破坏了
  「槽位不对外 + `GTD_TRUST_PROXY=1` + Caddy **覆盖** XFF」这个三件套前提。
  ⚠️ **更正一处上下文口径（E8）**：当前实现中**不存在 `GTD_BIND` 变量**；绑定地址硬编码在 `docker-compose.yml` 的
  `ports` 条目里。所谓「`GTD_BIND` 与 `GTD_TRUST_PROXY` 配对」来自旧版单容器文档，对当前编排不成立——
  正确的配对是 **`ports` 的 `127.0.0.1:` 前缀 ↔ `GTD_TRUST_PROXY=1` ↔ `header_up X-Forwarded-For {http.request.remote.host}`**，三者缺一不可。
- **恢复**：绑定恢复后，从外部再测一次 8788/8789 必须不通；确认 `/api/health` 只能经 80/443 到达；
  复核 `Caddyfile` 的 XFF 是**覆盖**不是追加。
- **复盘**：把 `ss -ltnp` 与 `docker compose config` 绑定检查加入 §2 V7 与每周巡检；登记为安全事件（同步安全工程师）。

### SOP-11 切流配置未真正生效（**与 SOP-03 同级隐蔽，2026-11-15 实测**）

- **现象**：`release.sh` 全程报「已平滑重载上游」，但
  ① 每次发布都丢 1~4 个 502（有时又恰好 0 个，看起来像"偶发"）；
  ② 502 的 `dial` 目标是**已经被停掉的旧槽位**（看 caddy 日志的 `dial tcp <旧槽位IP>:8787: i/o timeout`）；
  ③ 或者根本没人察觉，只是"切流好像没起作用"。

- **快速判断（三条，按顺序）**：
  ```bash
  # ① 容器内配置的 mtime 是否等于本次发布生成的时间？不等 = 挂载没更新
  docker compose exec -T caddy ls -l --time-style=full-iso /etc/caddy/Caddyfile
  ls -l --time-style=full-iso deploy/run/Caddyfile

  # ② caddy 日志里有没有 "config is unchanged"？有 = 这次 reload 是 no-op
  docker compose logs --since 10m caddy | grep -E "config is unchanged|load complete"

  # ③ admin API 的上游**顺序**是否符合预期？顺序错也等于没切流
  docker compose exec -T caddy sh -c 'wget -qO- http://127.0.0.1:2019/config/' \
    | grep -o '"dial":"[^"]*"'
  ```
  ⚠️ **第 ③ 条必须看顺序，不能只看"两个都在"**。`lb_policy first` 只走**第一个**可用上游，
  「期望 `app-green app-blue`、实际 `app-blue app-green`」意味着流量根本没切过去 —— 集合比较会误判为通过。

- **止血**：**不要再发第二次版本试图"覆盖"它**。先按 ① 判断是挂载问题还是 reload 问题，再决定动作。
  若线上仍有 502，按 SOP-02 回滚。

- **根因（2026-11-15 实测确认）**：`caddyfile_generate` 曾用
  `mv "${CADDY_CONFIG}.new" "$CADDY_CONFIG"` 落盘。**单文件 bind mount 绑定的是 inode，不是路径** ——
  `mv` 会产生**新 inode**，而容器内 `/etc/caddy/Caddyfile` 仍指向旧 inode（3 天前的旧内容）。
  于是 `caddy validate` 与 `caddy reload` 读到的永远是旧配置，Caddy 返回 `config is unchanged`（no-op），
  而脚本因为退出码是 0，照样打印「已平滑重载上游」。
  **该缺陷从 2026-11-13 持续到 11-15，期间所有发布的"切流"均未生效；11-14 的 4 个 502 与 11-15 的 1 个 502 是同一根因。**

- **恢复**：
  1. 写入方式必须是**原地覆盖**（保持 inode）：`cat "${CADDY_CONFIG}.new" > "$CADDY_CONFIG"`，**不要 `mv`**
  2. 若容器已绑在旧 inode 上，需一次性重建让它重新绑定：
     ```bash
     docker compose up -d --force-recreate caddy
     ```
     实测代价：**命令 2.1 秒、入口恢复 2.7 秒、期间丢 3 个请求**（开发期可接受；生产环境需评估）
  3. 重建后必须确认 `docker compose exec caddy ls -l /etc/caddy/Caddyfile` 的 mtime 与宿主机一致

- **防复发（已落地）**：`deploy/lib.sh` 新增
  - `CADDY_EXPECTED_UPSTREAMS`（由生成侧写入期望值，避免调用点各传一份而漂移）
  - `caddy_runtime_upstreams()`：从 admin API 取真实上游并归一化
  - `caddy_assert_upstreams()`：**顺序敏感**比较，不符即 `die`，文案直指 inode 根因
  - `caddy_reload` 成功文案改为「已平滑重载上游（**运行时上游已核实**）」

- **复盘（一条纪律，务必写进习惯）**：
  > **`reload` 返回 0 不等于生效，`"load complete"` 也不等于上游变了。**
  > 任何"平滑重载成功"的日志，都必须附带**运行时状态断言**（查 admin API 的实际上游），
  > 否则它只是一句打印，而不是一道门禁。这是本项目第三次遇到"门禁自己被软化"的同类问题
  > （前两次是 `install.sh` 冒烟失败静默放行、`probe.sh` 空档超阈值只告警）。

**探测退出码（`probe.sh`，2026-11-15 起）**：

| 退出码 | 含义 | 上层怎么用 |
|:---:|---|---|
| `0` | 无失败请求，且最大空档 ≤ 3000 ms；或带了 `--allow-gap` 且确实无失败请求 | 连续性达标（后者**不构成**零停机证明） |

**前端跨文件一致性（Q11）：与 md5 是两个不同的问题**

本项目前端是 6 个 ESM 模块，靠 `?v=` 各自缓存、随镜像整体替换。因此「一致性」有两个**互不等价**的问题，别用一个去回答另一个：

| 问题 | 判据 | 什么时候会误导你 |
|---|---|---|
| 线上文件 **== 工作区文件**？ | md5 逐文件比对（§5.2） | 工作区有**未发布**改动时（例如只改了 `app.js`），md5 必然不同 —— 此时它说明不了线上是否自洽 |
| 线上这一对文件**彼此匹配**？ | 跨文件**语义标记** grep（本节 Q11） | — |

检查命令（只读，发布**后**跑）：

```bash
# 线上产物里这两个标记必须同时为 0（或同时非 0）。当前标记对：建号表单的角色选择器
curl -s http://127.0.0.1:8080/js/views.js | grep -c 'id="a-role"'   # 0 = 建号表单已按 v1.3 收窄（不渲染角色选择器）
curl -s http://127.0.0.1:8080/js/app.js   | grep -c 'a-role'        # 0 = app.js 也不再读这个元素
```

判读：

| views | app | 含义 | 处置 |
|:---:|:---:|---|---|
| `0` | `0` | **自洽**（2026-11-17 实测即此状态） | 通过 |
| `0` | `≥1` | **新 views + 旧 app**：`app.js` 读不到 `#a-role`，会把角色**回填成 `member`**；而 v1.3 后端对系统管理员传 `member` 返回 `400 ROLE_NOT_ALLOWED` | 不通过 → 补齐 `app.js` 重新发布（或 `rollback.sh` 回上一版） |
| `≥1` | `0` | 反向不匹配：用户**能选角色但选择无效**（静默失效） | 同上 |

**为什么必须单独查**：这类混版的形状是「**不报错、不白屏、只是某个按钮行为错**」——没有 500、探测全绿、冒烟也可能全过（冒烟只保证"不该开的没开"，不保证"该开的能开"）。等到用户报"建号报错"时，已经错过发布窗口。

**为什么不能用 mtime / 版本号代替**：
- 镜像内文件 mtime 在构建时被压成同一时刻（实测三个文件同刻），比出来的是**构建时刻**，不是改动时刻；
- 版本串 `?v=` 是**缓存键**，整批文件共用同一个值，天然无法表达"这一对是否匹配"；
- 本项目已两次因"用间接指标回答直接问题"得出相反结论：① 拿 `08` 记的旧构建号回答"证书页是否上线"（实际已上线两天）；② 拿 mtime 推断"`app.js` 旧 → 可能与新 `views.js` 不匹配"（实测 `0/0` 自洽）。

**新增跨文件契约时请顺带登记标记**：只要某次改动让"A 文件不再产出某个元素/字段，而 B 文件仍依赖它"，就在**两侧**各留一个可 `grep` 的语义标记（如 `id="a-role"` 的出现与消失），并把命令补进 Q11。标记是人工维护的，**但它是当前唯一能直接回答"线上这对文件是否自洽"的判据**。

### 5.2 回滚验收清单

> **本项目工作区不是 git 仓库 —— 没有 commit 可 `revert`。**
> 回滚的唯一途径是 `rollback.sh` 切回上一个镜像（`ACTIVE_IMAGE` → `PREVIOUS_IMAGE`），
> **代码级回退不存在**。因此发布前必须确认 `PREVIOUS_IMAGE` 是好的 —— **这是你唯一的安全网**。
> 核实（本项目及其上层目录均无 `.git`）：
> ```bash
> git -C /opt/gtd4teams rev-parse --show-toplevel   # → fatal: not a git repository
> ```

> **「这个功能上线了吗」没有单一答案 —— 必须逐文件比内容，不能用版本号回答。**
> 本项目前端是多文件、按 `?v=` 各自缓存的：同一次发布之后，**同一个页面里可能 `views.js`/`api.js` 是新的、`app.js` 是旧的**。
> 实测例子（2026-11-17 那次发布后）：`views.js`/`api.js`/`index.html` 与线上镜像一致，`app.js` 不一致 ——
> 即"证书页已上线，但 `app.js` 的修复没进去"。用版本号或 `08` 记的构建号去回答，会得出相反结论。
>
> 注：**md5 回答「线上 == 工作区？」；「线上这一对文件彼此匹配吗」是另一个问题**，见 §5.1 的 Q11「前端跨文件一致性」。
> 工作区存在未发布改动时（例如只改了 `app.js`），md5 必然不同 —— 此时只能用语义标记判断线上是否自洽。
>
> 判定方法（只读，实测可用）——**把工作区文件与线上镜像里的同名文件做 md5 对比**：
> ```bash
> cd /opt/gtd4teams
> IMG="$(sed -n "s/^ACTIVE_IMAGE='\(.*\)'$/\1/p" deploy/run/state.env)"; echo "线上镜像=$IMG"
> docker run --rm --entrypoint sh "$IMG" -c 'md5sum /app/js/app.js /app/js/views.js /app/js/api.js /app/index.html'
> md5sum js/app.js js/views.js js/api.js index.html      # 工作区（或已同步的部署目录）侧
> curl -s http://127.0.0.1:8080/ | grep -o '?v=[0-9a-z]*' | sort -u   # 线上实际在跑的前端版本串
> ```
> 两侧 md5 相同 = 该文件**已在线上**；不同 = **未上线**。逐个文件判，不要合并成一个"版本"。
>
> ⚠️ **不要用 mtime 判**：镜像内文件的 mtime 在建镜像时被统一压成构建时间（实测三个文件全是同一时刻），
> 所以"容器内 mtime vs 工作区 mtime"比出来的是构建时刻、不是改动时刻。**内容哈希才是可靠判据。**
>
> ⚠️ 另外注意：`release.sh` 构建的是**部署目录**（`/opt/gtd4teams`），不是 Windows 工作区。
> 工作区改了但没同步到部署目录 = 不会进镜像。**每次发布前先确认部署目录与工作区一致**（本项目的实际踩点：漏同步过一次模板文件）。

### 6.1 频率与责任

### 6.2 `--import` 语义陷阱（务必先读）

🔍 **源码核实**（`pyapp/store.py` `import_all`）：`--import` 是 **`INSERT OR REPLACE` 按主键覆盖**，
**既不清空现有数据，也不做增量去重**。

| 恢复到 | 结果 |
|---|---|
| **空库 / 已删库文件** | 备份内容被精确还原 ✅ |
| **非空库** | 与现有数据按 id 覆盖合并；备份里没有的行**继续留在库里** → 混合状态 ❌ |

因此**灾难恢复的正确做法只有一种**：停服 → **先删库文件** `rm -f /data/gtd4teams.db*` → 再 `--import` → 起服 → 校验。
另外 `export_all` 的 `BACKUP_TABLES` 不含 `sessions`，**恢复后所有人必须重新登录，这是预期行为**。

⚠️ **`docs/Docker部署方案.md` 的恢复命令不可直接照抄**：其中 `docker compose run --rm … app sh -c …`、
`docker compose cp … app:…` 用的服务名 `app` 在**当前双槽位编排中不存在**（现为 `app-blue` / `app-green` / `caddy`），
且该文档引用的 `--profile tls`、`GTD_BIND`、`GTD_HTTP_PORT=8787`、`GTD_TRUST_PROXY=0` 均与当前实现不符（E8）。
照抄会直接 `no such service: app`。**以下 §6.3 为按当前编排重写的命令。**

> `caddyfile_generate()` 从 `deploy/Caddyfile.template` 生成到 `deploy/run/Caddyfile`，再以**单文件
> bind mount** 挂进容器（见 `docker-compose.yml`）。改模板**不会自动生效**，必须重新生成并 `caddy_reload`；
> 生成时最后一步必须**原地覆盖**（`cp`/`cat >`），**不能用 `mv`** —— `mv` 换了 inode，容器内仍指向旧 inode。

> **手工 `rm /certs/tls.crt` 不会触发重载** —— Caddy 会继续用内存里的旧证书，而页面/文件看起来都"已经删了"（实测：
> 移走 `tls.crt` 后 `https://localhost:8443` 仍返回 200，因为配置引用的是 `tls-<指纹>` 副本）。这是最容易制造
> "以为改了其实没改"的操作，写在这里是为了不让下一个人踩。
> 它还有一个**自相矛盾的用户可见面**：手工 `rm` 之后 `GET /api/admin/cert` 立刻变成 `configured: false`（它按文件判断），
> 而浏览器实际仍在用那张证书 —— 于是"页面说没证书、HTTPS 还在服务"。看到这种不一致，先查有没有人绕过接口动过 `/certs`。
