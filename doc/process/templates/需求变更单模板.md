# 模板 · 需求变更单

> 维护人：质量保障 ｜ 上位文档：`00_开发流程总纲.md` §5.2 编号 / §7 变更纪律、`07_测试体系与各阶段验收标准.md` §4.1 回归映射、`docs/零停机发布方案.md` §6 库结构兼容纪律
> **用法**：任何改动先开 `CR-` 变更单（总纲 §7.1），写清影响的需求 / 文档 / 代码 / 测试 / 数据库 / 安全边界 / 回归范围，再走追溯链。
> **核心目的**：改一处之前先能回答「影响面是什么、要重跑哪些测试、能不能零停机发」。

---

## 1. 编号规则

| 项 | 规则 |
|---|---|
| 格式 | `CR-<YYYY>-NNN`（年份 + 三位序号） |
| 示例 | `CR-2026-0007` |
| 关联编号 | `REQ-xxx`（必需）、`TC-xxx`、`ACC-Gn-xxx`、`BUG-xxx`、`GTD_BUILD` |
| 一变更一单 | 一次发布涉及多个变更时，各自开单，在发布结论表（`07` §6）汇总 |
| 顺序 | **先开 CR → 再改代码 → 再跑回归 → 再填验收单**；不允许「先改了再补单」 |

## 2. 字段表与状态枚举

| 字段 | 必填 | 说明 |
|---|---|---|
| 变更编号 / 标题 | ✅ | 标题写「对象 + 动作」，不写「优化一下」 |
| 提出人 / 日期 / 来源 | ✅ | 来源：评审 / Bug / 线上问题 / 合规 / 用户反馈 |
| 关联需求 / 缺陷 | ✅ | `REQ-xxx` / `BUG-xxx`，或「存量补课」 |
| 变更类型 | ✅ | 新增 / 修改 / 删除 / 修复 |
| 原描述 / 变更后描述 | ✅ | 逐字对照，不留模糊空间 |
| 变更理由 | ✅ | 为什么改；不写「更好」 |
| **影响范围** | ✅ | 功能域 / 接口 / 数据模型 / 权限 / 测试 / 部署 / 文档 / 版本串（见 §5 清单） |
| **破坏性判定** | ✅ | 是否涉及表结构；命中 §6 expand/contract 哪一类 |
| 受影响测试用例 / 验收单 | ✅ | `TC-xxx` / `ACC-Gn-xxx` 清单 |
| **回归范围** | ✅ | 按 `07` §4.1 改动类型映射，逐条列命令 |
| 风险评估 | ✅ | 影响范围 / 触发条件 / 严重程度 / 缓解（对齐 `07` §8.1 风险表） |
| 安全边界核对 | ✅ | 是否触及权限 / 认证 / 归属 / XFF / 密钥 / 暴露面；若是，**G5 必须重跑** |
| 裁决结论 | ✅ | 批准 / 拒绝 / 延期；批准须写目标版本与构建标识 |
| 签字位 | ✅ | 提出人 / 评估人(QA) / 放行人 / 日期 |

**状态枚举**：`提出 / 评估中 / 批准 / 拒绝 / 延期 / 已实施 / 已验证 / 已关闭`。
**变更类型枚举**：`新增 / 修改 / 删除 / 修复`。
**破坏性枚举**：`非破坏性（加法） / 破坏性（需 expand-contract） / 不涉及数据`。

## 6. 库结构变更兼容性判定表（来自 `docs/零停机发布方案.md` §6）

> 蓝绿切换期间**新旧两版代码同时存在、共用一个库**，因此硬约束是：**一次发布只能做「加法」（expand），不能做破坏性结构变更**。

| 变更类型 | 能否直接发 | 说明 |
|---|---|---|
| 新增表 | ✅ | 新版本启动时建出来，旧版本完全不感知 |
| 新增列（可空或带默认值） | ✅ | 旧版本 `SELECT *` 多拿一列，但不消费 |
| 新增索引 | ✅ | 对旧版本无影响 |
| 删除列 / 改列名 | ❌ | 旧版本会立刻报错 |
| 改列语义（同名列，含义变了） | ❌ | **最危险**：两个版本对同一列解读不同 |
| `NOT NULL` 且无默认值的新列 | ❌ | 旧版本写入的行会违反约束 |

**破坏性变更三步两发布**：① 第一次发布加新列/新表（两版兼容）→ ② 数据迁移（`--export`/`--import` 或一条 SQL）→ ③ 确认稳定后第二次发布才删旧列。
逃生口：`sudo bash deploy/release.sh --stop-first`（先停旧槽位再起新槽位，接受一次受控短停）。

> 补充纪律（总纲 §7.4）：`--import` 是 **`INSERT OR REPLACE`**，既不清空也不去重；灾难恢复必须**先删库文件再导入**，否则残留行与新数据叠加。

## 7. 使用纪律

- [ ] **先开单再改代码**；单未批准不得进入 G2。
- [ ] 描述对照逐字写，不留「优化」「调整」这类模糊词。
- [ ] 影响范围勾了哪一项，回归范围就要有对应命令；**漏一项即 G4-08 不通过**。
- [ ] 涉及表结构必填 §6 判定；破坏性变更未走 expand/contract 或 `--stop-first` → G1-05 / G6-11 阻塞。
- [ ] 涉及权限 / 认证 / 归属 / XFF / 密钥 / 暴露面 → **G5 必须重签**（独立阻塞权，不可豁免）。
- [ ] 涉及 `index.html` 或 `dispatch` → `app-boot-test.mjs`(46) 必跑（唯一能抓挂载点/视图分发的测试）。
- [ ] 版本串四处同步是硬门禁（G2-05）；改动前端必须同步递增。
- [ ] 长耗时用例单独跑（113.7s / 190.3s），不与其它起服务用例并行（`07` §4.2）。
- [ ] 裁决为「批准」时写明目标版本；发布后在 `07` §6 结论表回填 `GTD_BUILD`。
- [ ] 证据状态按 `07` §0.1 四态标注，【未验证】不得写成通过。
