# 模板 · Bug 报告

> 维护人：质量保障 ｜ 上位文档：`07_测试体系与各阶段验收标准.md` §5 缺陷管理 / §4.3 修复后回归、§8.2 用例清单；编号规则 `00_开发流程总纲.md` §5.2
> **目标**：把发现的问题整理为**可复现、可定位、可修复、可回归**的报告。任何「失败」结论都必须有 `BUG-` 编号。
> **纪律**：先有根因与证据，再有最小修复；**严禁猜测式乱改代码**（`integration_debugging.systematic_debugging` / `regression_after_fix`）。

---

## 1. 编号规则

| 项 | 规则 |
|---|---|
| 格式 | `BUG-<YYYY>-NNNN`（年份 + 四位序号，跨年不复用） |
| 示例 | `BUG-2026-0031` |
| 关联编号 | 必填关联 `TC-xxx`（失败用例）；可关联 `REQ-xxx` / `CR-xxx` / `ACC-Gn-xxx` / `GTD_BUILD` |
| 一缺陷一单 | 不把多个问题塞进一张单；同源多问题用「关联缺陷」互相引用 |

## 2. 字段表与状态枚举

| 字段 | 必填 | 说明 |
|---|---|---|
| Bug 编号 / 标题 | ✅ | 标题写「现象 + 条件」，不写「有个问题」 |
| 严重级别 / 优先级 | ✅ | P0~P3（定义见 §4） |
| 状态 | ✅ | 生命周期状态（见 §5） |
| 所属模块 / 功能域 | ✅ | 对应 `07` §2 覆盖矩阵的功能域 |
| 关联用例 / 需求 | ✅ | `TC-xxx` / `REQ-xxx`，或「探索性测试发现」 |
| 环境 | ✅ | OS、Python、Node、浏览器、版本号 `APP_VERSION`、构建标识 `GTD_BUILD`、相关开关（`GTD_TRUST_PROXY` 等） |
| 复现步骤 / 复现率 | ✅ | 编号步骤；复现率写「N/N 次」 |
| 期望 / 实际结果 | ✅ | 都要可判定；实际结果照录，不修饰 |
| **根因分层** | ✅ | 前端 / 网关(Caddy) / 后端(httpd/policy/store) / 数据库(SQLite) / 第三方(LLM) / 环境 / 部署 / 数据 —— **先判定层，再动手** |
| 假设与证据 | ✅ | 2~3 个可验证假设，逐条证实或证伪（日志 / 网络包 / `PRAGMA` / 配置） |
| 证据 | ✅ | 日志片段、命令输出（含 EXIT 码）、截图、网络包、文件路径 |
| 影响范围 | ✅ | 受影响功能、用户、数据、发布门禁 |
| 责任方 / 发现人 / 日期 | ✅ | |
| 修复方案（最小） | 修复时填 | 只改必要部分 + 影响面 |
| 回归清单 / 防复发断言 | 修复时填 | 对应 `07` §4.1 改动类型 + 新增 `TC-` 断言 |
| 关闭结论 | ✅ | 通过 / 拒绝（须注明「刻意取舍」出处）/ 延期 |

**状态枚举**：`新建 / 待分派 / 修复中 / 待验证 / 关闭 / 重开 / 拒绝 / 延期`。
**严重级别**：`P0 致命 / P1 严重 / P2 一般 / P3 轻微`（完整定义见 `07` §5.1）。

## 4. 严重级别定义（`07` §5.1 摘要）

| 级别 | 判定标准 | 本项目示例 |
|---|---|---|
| **P0** | 数据丢失/损坏、服务整体不可用、认证被绕过、越权可读写他人数据、发布后必须回滚 | 「蓝绿切换后所有人被登出」「静态托管泄露 `data/gtd4teams.db`」 |
| **P1** | 核心功能不可用、权限边界失守、发布门禁失效、备份不可用 | 「版本串不同步导致浏览器命中旧代码」「`smoke.sh` 少了 `--path-as-is` 使穿越检查为假」 |
| **P2** | 非核心功能异常、有绕行方案、边界值处理不当 | 「资源台账 `credential` 类型文案错误」 |
| **P3** | 文案、排版、提示语，不影响功能 | 「错误提示措辞不统一」 |

### 阻塞发布判定阈值（`07` §5.3，任一命中即禁止进入 G6）

- [ ] 存在任一未关闭 **P0**
- [ ] 存在 P1 且涉及 **权限 / 数据丢失 / 越权 / 认证 / 上传 / 并发与重复请求**
- [ ] **越权用例任一失败**（G5-02）
- [ ] L0/L0b/L1/L2/L3/L4 **任一门禁失败**
- [ ] **G5 存在任一阻塞项**（独立阻塞权，无豁免通道）
- [ ] 回归范围漏跑，或 P0/P1 的防复发断言未新增
- [ ] 缺陷收敛不达标：P1 未关闭且无放行人书面豁免

## 5. Bug 生命周期

```
新建 → 待分派 → 修复中 → 待验证 ─┬─→ 关闭
                                 ├─→ 重开 ─┐（回到修复中）
                                 ├─→ 拒绝  │
                                 └─→ 延期  │
                                          ↑
                         关闭后回归失败 ────┘
```

> 「拒绝」必须写明依据：例如 `README.md` §权限语义中标注的 6 处**刻意取舍**（双域共用 `work_items`、写入不带 `owner_id`、被拦返回空数组、`work_items` 更新不含 owner 条件、`contexts` 更新含 owner 条件、`status != active` 视为非成员）。**避免后来者把这些取舍当 bug「顺手修好」** —— 本项目历史上已因此丢过改动（总纲 §2）。

## 6. 填写示例（真实历史缺陷，展示「证据 → 根因 → 最小修复 → 防复发」全链）

> 本例取自 `docs/零停机发布方案.md` §2.4 记录的**真实缺陷**（为支持蓝绿而补的两处之一）。用于演示填写颗粒度；其中修复内容已是项目现状。

```markdown
# BUG-2026-0008 · 蓝绿发布时新槽位启动失败，报 "attempt to write a readonly database"

| 字段 | 内容 |
|---|---|
| 严重级别 | ☑ P0（新版本无法承载流量，发布整体不可用） |
| 状态 | ☑ 关闭（已修复并有回归断言） |
| 所属模块 / 功能域 | 发布零停机 / `pyapp/db.py` |
| 关联用例 | TC-CON-001（`tests/test_zerodowntime.py`） |
| 发现场景 | 新槽位在**旧槽位仍在写入时**启动 |

## 环境
| 项 | 值 |
|---|---|
| OS | Windows（开发机）／Linux（目标服务器，行为预期不同） |
| 部署形态 | ☑ 双槽位蓝绿，两进程共用同一 SQLite 文件（WAL + busy_timeout=15000） |

## 复现步骤
1. 启动旧槽位并持续写入。
2. 带新增字段/新表的版本启动新槽位（触发整份建表脚本重跑）。
3. 观察新槽位启动日志。

**复现率**：必现（只要发布带新字段或新表就必然踩中）

## 期望结果
新槽位正常启动并 healthy，不影响旧槽位写入。

## 实际结果
```
sqlite3.OperationalError: attempt to write a readonly database
```
表现是「新槽位起不来」，原因看起来像数据库变成只读 —— **排查方向被完全带偏**。

## 根因定位
| 项 | 内容 |
|---|---|
| 问题边界 | ☑ 数据库层（DDL 写锁） + 部署层（双进程共库） |
| 假设 1：库文件权限不对 | 证伪：单进程启动正常，权限无误 |
| 假设 2：磁盘只读 / 卷挂载问题 | 证伪：旧槽位同期写入成功 |
| 假设 3：启动时无条件重跑 DDL，与旧槽位写锁冲突 | **证实**：原实现每次启动都 `executescript` 整份建表脚本；新槽位恰在旧槽位写入时启动，两个进程抢写锁 |
| 根因 | 绝大多数启动**结构已建全却仍产生写入**，在蓝绿共库场景下必然与另一进程的写事务冲突 |
| 证据 | 启动异常栈；`db.py` 原实现；两进程并发写日志 |

> 附带根因（同一批修复）：`pyapp/httpd.py` 每个已认证请求都 `UPDATE sessions SET last_seen_at`，**所有读操作都顺手抢一次写锁**，蓝绿切换期间把纯读流量也卷进写冲突。

## 影响范围
| 项 | 内容 |
|---|---|
| 受影响功能 | 全部带 DDL 变更的发布；切流窗口的读请求 |
| 是否命中阻塞阈值 | ☑ 是，第 1 条（P0 未关闭）与第 4 条（L0b/L3 门禁） |
| 影响门禁 | L0b、L3 |

## 最小修复（只改必要部分）
| 项 | 内容 |
|---|---|
| 改动 1 `pyapp/db.py` | `schema_present()` 先做**只读检查**，结构已建全就直接返回、完全不产生写入；真需建表时带退避重试（约 0.25s 起线性退避，总计数秒） |
| 改动 2 `pyapp/httpd.py` | 活跃时间按 300s 节流；刷新失败**只当记账失败**，绝不让请求变成 500 |
| 改动 3 `pyapp/httpd.py` | `_dispatch` 在异常为写锁争用、响应尚未开始写时回滚连接并重试（指数退避，最多 6 次）；因每请求一连接、异常时连接关闭、未提交事务丢弃 → 要么整体生效要么完全没发生 |
| 影响面 | `db.py` 表结构/`server.py --check`、全套接口测试、零停机前提测试（对应 `07` §4.1「改 db.py COLUMNS」「改 httpd.py」两行） |

> 平台差异（如实记录）：Linux 写锁争用报 `SQLITE_BUSY`，`busy_timeout` 会自动等待；**Windows 报 `SQLITE_READONLY`，busy_timeout 不处理这个错误码**。既然「两进程共用一个库」是地基，就不能寄托在 OS 差异上，故应用层统一兜底，两平台行为一致。**Linux 侧行为【未验证】，首次上服务器须跑 `test_zerodowntime.py` 确认。**

## 修复后回归
- [x] 原复现用例转绿
- [x] `python tests/test_api.py` 49 项全绿（含字段规格 == `PRAGMA table_info`、建库幂等不丢数据）
- [x] `python tests/test_zerodowntime.py` 9 项全绿：并发写 40 次零失败、数据互见、会话跨进程、日志无锁冲突
- [x] 相邻功能验证：纯读请求不再产生写锁；`last_seen_at` 刷新失败不影响 200
- [x] 防复发断言：`TC-CON-001` 常驻 `tests/test_zerodowntime.py`
- [x] 190.3s 用例单独跑

## 关闭结论
☑ 关闭
```

## 7. 使用纪律

- [ ] 一张单只写一个缺陷；复现步骤任何人照着做都能得到同样结果。
- [ ] **实际结果照录**，不写「报错了」，要贴原始错误串与 EXIT 码。
- [ ] 根因必须落在 §3 的某一层，且有 ≥1 条证据；**没有证据不得写「应该是…」**。
- [ ] 修复方案写「只改必要部分 + 影响面」，对应 `07` §4.1 的改动类型。
- [ ] P0/P1 **必须**有防复发断言与 `TC-` 编号，否则不得关闭。
- [ ] 「拒绝」要注明「刻意取舍」出处，防止误改（总纲 §2）。
- [ ] P0/P1 关闭需放行人签字；命中 §4 阻塞阈值时禁止进入 G6。
- [ ] 证据状态按 `07` §0.1 四态标注，【未验证】不得写成通过。
