# 模板 · 阶段验收单

> 维护人：质量保障 ｜ 上位文档：`00_开发流程总纲.md` §4 门禁矩阵 / §5.2 编号、`07_测试体系与各阶段验收标准.md` §3
> **用法**：每个阶段（G0~G6）复制 §3 生成一张单，编号 `ACC-Gn-YYYYMMDD`；完整判定标准查 `07` §3 对应小节。
> **核心纪律**（总纲 §3）：门禁不是会议，是一张可勾选的表；判定标准必须能回答「通过 / 不通过」，不允许写「基本完成」「看起来没问题」。

---

## 1. 编号规则

| 项 | 规则 |
|---|---|
| 验收单编号 | `ACC-G<n>-YYYYMMDD`，如 `ACC-G4-20261113`；同一天同阶段重开单追加 `-2`（`ACC-G4-20261113-2`） |
| 单内条目编号 | `Gn-NN`，如 `G4-01`；与 `07` §3 的条目号一致，**不要自造条目号** |
| 示例 | 验收单 `ACC-G6-20261113` 里的第 6 项 = `G6-06 L4 连续性探测` |
| 关联编号 | 每条判定证据可挂 `TC-xxx` / `BUG-xxx` / `CR-xxx` / `GTD_BUILD` |
| 归档 | 每次发布至少归档 `ACC-G4` / `ACC-G5` / `ACC-G6` 三张（总纲 §8） |

## 2. 字段表与状态枚举

| 字段 | 必填 | 说明 |
|---|---|---|
| 验收单编号 | ✅ | `ACC-Gn-YYYYMMDD` |
| 阶段 / 门禁 | ✅ | G0~G6 之一 |
| 准入条件 | ✅ | 上一门禁通过（G0 为「调研记录齐全」） |
| 退出条件 | ✅ | 进入下一阶段 |
| 必交产出 | ✅ | 见 §6 速查表 / 总纲 §4 |
| 放行权 | ✅ | G0/G1/G6 用户；G2 开发自审；G3/G4 测试；**G5 安全独立阻塞权** |
| 验收项 | ✅ | 编号 `Gn-NN` + 名称 |
| 判定标准 | ✅ | **可检查、可判通过/不通过** |
| 证据形式 | ✅ | 命令输出（含 EXIT 码）/ 文件路径 / 截图 / git diff |
| 责任人 | ✅ | 按总纲 §6 RACI |
| 结论 | ✅ | 默认 `- [ ] 待办` |

**结论状态枚举**：

| 状态 | 写法 | 含义 |
|---|---|---|
| 待办 | `- [ ] 待办` | 未核对证据 |
| 通过 | `- [x] 通过` | 已核对证据且符合判定标准 |
| 阻塞 | `- [x] 阻塞` | 不符合，须在「阻塞项登记」写明编号与原因 |
| 豁免 | `- [x] 豁免` | **仅 G4/G6 可用**；必须写理由 + 放行人签字；**G5 无豁免通道** |

> **勾选即表示「已核对该项的证据形式」**，不是「听说过」。勾选人须在签字位留名。

## 4. 填写示例（照此颗粒度写）

> 示例取自 `07` §3.7 G6 的第 6 项。**示例中的数值仅演示填写格式，不是本次发布实测值。**

```markdown
# ACC-G6-20261113 · 上线验收单（节选示例）

| 项 | 内容 |
|---|---|
| 验收单编号 | ACC-G6-20261113 |
| 阶段 / 门禁 | G6 上线验收 |
| 准入条件 | G5 安全门禁已签字放行 |
| 退出条件 | 发布完成，进入运维/迭代 |
| 必交产出 | 发布结论表（`07` §6）+ 备份 + 回滚预案 |
| 放行权 | ☑ 用户（运维） |
| 版本串 / 构建标识 | APP_VERSION `20260917a` ｜ GTD_BUILD `20261113-153012-a1b2c3d` |
| 执行日期 / 环境 | 2026-11-13 ｜ Ubuntu 22.04 / Docker 24.x（现场填） |

| 验收项 | 判定标准（可判通过 / 不通过） | 证据形式 | 责任人 | 结论 |
|---|---|---|---|---|
| G6-06 L4 连续性探测 | `deploy/probe.sh` **失败数 = 0** 且最大连续成功间隔 **≤ 3000ms**；出现秒级空档即不通过，`release.sh` 以 exit 3 结束 | 探测报告三数：总请求 / 失败数 / 最大间隔；`release.sh` EXIT 码 | 运维 | - [x] 通过 |

## 阶段结论
- [ ] **通过**　- [x] **阻塞**（G6-12 未现场确认，按 `07` §3.7 判定纪律不得默认通过）

## 阻塞项登记
| 编号 | 原因 | 处置 | 责任方 | 预计解决 |
|---|---|---|---|---|
| G6-12 | 开发机无 Docker，Caddy `lb_policy first` / `health_uri` 实际行为【未验证】 | 首次发布现场执行 `caddy validate` + 切流观察，补录证据后重开单 | 运维 | 首次发布当日 |

## 门禁评审四项
| 项 | 内容 |
|---|---|
| 通过 / 不通过结论 | 不通过（条件未满足） |
| 必须补齐项 | - [x] G6-12 四项现场确认 |
| 建议优化项 | - [ ] 把版本串四处同步做成自动化断言（`07` IMP-02） |
| 下一阶段准入条件 | - [ ] 全部 G6 项通过或有放行人书面豁免，且 `07` §6 发布结论表已签字 |

## 签字位
| 角色 | 姓名 | 日期 |
|---|---|---|
| 执行人 | （待填） | |
| 复核人（QA） | （待填） | |
| 放行人（用户） | （待填） | |
```

**这个示例想说明两件事**：
1. 「通过」必须带证据（探测三数 + EXIT 码），不能只勾；
2. **【未验证】项不得默认通过** —— 正确做法是标「阻塞」或「条件通过 + 遗留风险 + 放行人签字」，这正是 `07` §0.1 的证据原则。

## 5. 门禁速查表（G0 ~ G6，对齐总纲 §4）

| 门禁 | 阶段 | 准入 | 必交产出 | 放行权 | 阻塞条件（摘要，完整见 `07` §3） |
|---|---|---|---|---|---|
| **G0** | 需求 | 调研记录齐全 | `02` REQ/BR/EX + 权限矩阵 + 验收标准 | 用户（产品） | 存在无验收标准的需求；权限矩阵与代码不一致且未标注「刻意取舍」 |
| **G1** | 设计 | G0 通过 | `03 FDS`+`04 TDS`+`05 数据模型`+`06 接口契约` | 用户（架构） | 数据库变更缺回滚 SQL；接口契约与现有 `/api/*` 冲突未说明 |
| **G2** | 开发 | G1 通过 | 代码 + 版本串 + 自测记录 | 开发自审 | 版本串不同步；新增交互未注册 `dispatch`；新增视图未改三处 |
| **G3** | 联调 | G2 通过 | 联调验收单 | 测试 | 挂载点缺失 / 视图未分发 |
| **G4** | 测试 | G3 通过 | 测试报告 + 回归结论 | 测试 | 任一断言失败；回归范围漏跑 |
| **G5** | 安全 | G4 通过 | `08` 安全放行结论 + 越权用例结果 | **安全（独立阻塞权）** | 存在任一阻塞项 → **禁止进入部署** |
| **G6** | 上线 | G5 放行 | 发布结论表 + 备份 + 回滚预案 | 用户（运维） | 构建标识对不上；探测失败（exit 3）；未验证项未现场确认 |

## 6. 使用纪律

- [ ] 每张单只对应**一个阶段**，不合并、不跨阶段勾选。
- [ ] 五栏表头固定为「验收项 / 判定标准 / 证据形式 / 责任人 / 结论」，不增删列。
- [ ] 判定标准逐条从 `07` §3 照搬，不临场重写、不放宽。
- [ ] 结论列的复选框语法保持 `- [ ]` / `- [x]`，便于直接当清单用。
- [ ] **G5 的任何一项不得豁免**，也不得以「赶进度」为由覆盖。
- [ ] 阻塞项必须有编号、原因、处置、责任方；「口头说好了」不算闭合。
- [ ] 签字位三项（执行人 / QA 复核 / 放行人）齐全才算有效单；G5 另加安全工程师签字。
- [ ] 每次发布至少归档 `ACC-G4` / `ACC-G5` / `ACC-G6`（总纲 §8）。
- [ ] 证据状态按 `07` §0.1 四态标注：【实测·引用】/【未验证】/【文档示例】/【待裁决】。
