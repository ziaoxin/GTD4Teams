## 0. 这个目录解决什么

项目原有 `docs/` 下 4 份文档全是**专题技术设计**（AI 能力、Docker 部署、桌面客户端、零停机发布），
没有任何需求、设计规格、阶段验收的过程文档。结果是：代码写得不错、测试 249 项全绿，
但**回答不了「这个功能对应哪条需求 / 哪条规则 / 哪条验收标准」**。

本目录补的是这条链，不是功能：

```
REQ-xxx → BR/EX-xxx → FDS 页面·流程 → TDS 模块 → 接口契约 / 数据表
        → TC-xxx → ACC-Gn-xxx → GTD_BUILD → 线上验证
```

**使用原则**：这是「1 人 + AI 协作」的极小团队流程，每阶段只留 1 份主文档 + 1 张验收单。
不要把流程变成负担；自动化能判定的一律交给脚本（见 `00` §6、§10）。

## 4. 一致性说明（避免把不同口径误读成矛盾）

| 容易混淆 | 正确理解 |
|---|---|
| 版本串「三处」vs「四处」 | 前端三处（`js/config.js` APP_VERSION + 各模块 `?v=` + `index.html` 引用）**加**服务端一处（`pyapp/__init__.py`）= 共四处同版本。README 的「三者」指前端三处 |
| 服务端错误码 **46 个** vs 前端映射 **22 个** | 两个不同集合：46 = 服务端全量错误码（`06` 口径）；22 = `js/api.js:358-381` 的 `friendlyError` MAP 条目（需本地化文案的 code）。现有表驱动只覆盖 **7 / 22** |
| 端点 **20 条 / 19 路径** | `ROUTES` 20 条 `(method, path)` 条目、19 条唯一路径（`httpd.py:815-836`）：`/api/llm/config` 有 GET+POST，`/api/auth/me` 是 `/api/auth/profile` 的别名 |
| `GTD_BIND` | **代码中不存在此变量**。应用侧 `HOST`/`GTD_HOST`（`config.py:77`），容器侧 compose `ports` 的 `127.0.0.1:` 前缀。旧 `docs/Docker部署方案.md` 的 6 处已修正，详见 `01` §9.1 D-1 |
| `08` 的 G-01~G-10 vs 总纲 G5/G6 | 不冲突：G-01~G-10 是**安全门禁内部的检查项编号**，其放行结论汇入总纲的 G5；G6 再引用 G5 结论 |
| 测试数量 | 后端 `test_api.py` **49**、`test_zerodowntime.py` **9**；前端 `render` **80** / `auth-flow` **65** / `app-boot` **46**；合计 **249** 项，本机全绿。`deploy/smoke.sh` 本次**未实跑**，`docker compose config -q` 因开发机无 Docker **从未实跑** |

> 主理人在 8 位成员并行产出后做过一次跨文档核对，抓到并修正了 3 处真实口径漂移（D-1/D-2/D-3），
> 全部记录与原子修正过程见 `01` §9.1。这件事故本身就是「没有单一权威就会漂」的实证。

## 6. 维护规则

1. 每份文档的「更新触发条件」见表 1；改动后同步检查 `00` §5 的编号与追溯链是否仍成立。
2. 任何新需求/变更先开 `CR-` 变更单，走完追溯链；每次发布至少填 `ACC-G4` / `ACC-G5` / `ACC-G6` 三张验收单。
3. 每季度做一次「文档 ↔ 代码」一致性巡检，把漂移记进 `01` §9；**数字口径一律以代码为准，不以文档互抄为准**。
4. 存量项目接入方式（反向补课 + 增量守规矩）见 `00` §8，不要回头补历史验收单。
5. 最小可行版与增强版的边界见 `00` §10：**当前不要跳到增强版**。
