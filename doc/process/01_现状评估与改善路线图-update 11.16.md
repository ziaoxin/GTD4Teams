## 1. 本轮最重要的三个发现（都不在原计划里）

### 1.1 切流从来没有生效过（SOP-11）

`caddyfile_generate` 用 `mv` 落盘。**单文件 bind mount 绑 inode 不绑路径** ——
`mv` 产生新 inode，容器内 `/etc/caddy/Caddyfile` 仍是 11-13 的旧 inode，于是
`caddy reload` 永远读到旧配置、返回 `config is unchanged`，而脚本照样打印"已平滑重载上游"。

**影响面**：11-13 到 11-15 之间所有发布的"切流"都是 no-op。11-14 的 4 个 502 与
11-15 的 1 个 502 是同一根因，此前被误记为"偶发"。**"先摘再停"那次修复也是无效的**，因为压根没摘。

**修复**：`cat .new > 目标`（保持 inode）+ `caddy_assert_upstreams`（**顺序敏感**断言）+
一次性 `--force-recreate caddy`（实测 2.7s / 3 个请求）。

> **顺序敏感是关键**：`lb_policy first` 只走第一个上游，"谁在前"就是切流本身。
> 我最初给的规格是"排序后比集合"，运维改成了顺序敏感 —— 实证恰好是顺序反了
> （期望 `green blue`，实际 `blue green`），**集合比较会判通过，而流量根本没切**。

### 1.2 `release.sh` 没有并发锁

两次发布并行时，后一次会把前一次刚起的槽位重建成自己的镜像，前一次的构建标识核对随即失败
（看起来像代码问题）。已加 `flock`，`rollback.sh` 共用同一把锁（回滚与发布并行会把状态互换两次，
比撞车更难查）。

### 1.3 探测报告被 `rm` 掉

那是"这次发布有没有断线"的唯一物证。已改为归档到 `deploy/run/probe-<build>.log`（保留 10 份）。

## 10. 本轮教训（写进项目纪律）

1. **"0 失败"和"真的切了"是两件事。** 某次配置没生效、恰好旧槽位本在前，探测照样 0 失败。
2. **门禁两病同源**：判据与语义脱节 → 要么假放行（`probe.sh` 空档 `exit 0`），要么假失败（0-2 判据 403 vs 404）、要么描述比实际弱（冒烟 `die` 被写成 `warn`）。三者都会让人无视它。
3. **`reload` 返回 0 不等于生效，`"config is unchanged"` 也不等于没问题。** 任何"平滑重载成功"的日志都必须附带运行时状态断言。
4. **跨 agent 的"完成通知"不等于任务做了。** 必须核实产物；反过来，**开工前也要核实"是不是已经做完了"** —— 本轮 P0 五条里有两条早已完成，差点让人重做。
5. **同一文件不要两人同时改。** 表现可以是"静默覆盖"，也可以是"重复插入 N 块"，两者都不报错且 `bash -n` 都通过。
6. **两边对不上，就说明你验的不是同一个文件。** 核对 md5 再宣称"实跑通过"。
7. **根因变了，不代表处置知识过期。** 判"整节作废"前先问：这节里有没有现在还成立的部分（如 SOP-09 的"如何定位是谁建的"）。
