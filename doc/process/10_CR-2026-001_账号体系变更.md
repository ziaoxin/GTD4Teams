## 1. 变更动机（为什么必须做，且不是"体验优化"）

### 1.1 直接动因：自助注册把"匿名者"提升为"有效会话持有者"

`allow_signup` 的默认值是 **True**（`pyapp/config.py:92-94`：`_env_bool('GTD_ALLOW_SIGNUP', True)`），
即有账号的唯一门槛是"能打开登录页"。`POST /api/auth/register` 的实现（`pyapp/httpd.py:653-691`）在同一次提交里
**建号 + 建会话 + 下发 Cookie**（`:682-688`、`:690-691`），所以注册成功 = 立刻拿到一个可用的登录态。

这个登录态能做什么，决定它是不是"放大器"：

| 能力 | 需要的门槛 | 自助注册后能否达到 | 证据 |
|---|---|---|---|
| 读自己的个人数据 | 有效会话 | ✅ | `pyapp/httpd.py:764-771`（`h_rows` 只 `_require_user`） |
| 提交 `app_logs`（含伪造内容污染取证） | 有效会话 | ✅ | `pyapp/httpd.py:827-841` |
| 调用 AI 转发（消耗实例额度、探测上游） | 有效会话 | ✅ | `pyapp/httpd.py:990-996`（`h_llm_chat` 只 `_require_user`） |
| 探测"某邮箱是否已注册" | **旧版无需会话** | ✅ | `pyapp/httpd.py:627-650`（`h_check_email` 免鉴权，仅 IP 限速） |
| 读他人/他人团队数据 | 需成为该团队成员 | ❌（被 `policy.py` 挡住） | `pyapp/policy.py:57-61`、`:335-350` |

结论：注册本身不直接越权（行级策略成立），但它**消灭了"攻击者必须先有一个有效会话"这道最便宜的防线**。
`08` §0 把它定性为 R-01/R-02 的「前置放大器」（`docs/process/08_安全审计与上线门禁.md:169`、`:285`）。

### 1.2 与第 1 期修复的关系（避免把已修的问题当理由）

必须说清楚：R-01（整库导出越权）与 R-02（LLM 配置无门槛 + SSRF）**已在第 1 期代码修复**：

| 项 | 当前代码事实 | 证据 | 标注 |
|---|---|---|---|
| R-01 | HTTP 导出改走 `store.export_visible()`：逐表过 `policy` select，`settings` 整表不出现，`users` 只留自己且无凭据列 | `pyapp/httpd.py:842-860`、`pyapp/store.py:421` | 【已验证】（实读代码）　【未验证】（本次未复跑 `test_export_does_not_leak_other_users_or_api_key`） |
| R-02 | `POST /api/llm/config` 双重门：`GTD_ADMIN_EMAILS` 白名单（空 = 谁都不能改）+ `baseUrl` 协议/私网/回环/元数据校验 | `pyapp/httpd.py:933-982`（门槛 `:950-956`、`:962`）、`pyapp/config.py:110-119,152-156` | 【已验证】（实读代码） |
| 第 1 期执行记录 | 上两项均标"已修复 + 容器实测" | `docs/process/01_现状评估与改善路线图.md:158,164,166` | 【已验证】（文档原文） |

**所以本次变更的理由不是"R-01 还在"，而是 R-03 本身仍未修**：
`08` 的 G-02 判定为「☐ 不通过（E1）」（`08:253`），修复手段只有"部署时配 `.env`"
（`08:169`：`GTD_ALLOW_SIGNUP=0` 或高熵 `GTD_SIGNUP_CODE`），而它有三条绕开路径
（`.env` 已存在 / 无 openssl / 直接 `python server.py --host 0.0.0.0`，`08:169` 原文）。
**把安全结论寄托在"部署者记得配一个环境变量"上，不是代码级修复。** 本 CR 把它变成代码级下线。

### 1.3 第二条动因：运维不该是"加人"的唯一通道

`--set-password` 的 docstring 自己承认了这个尴尬：
「既是'忘密码自救'，也是'关闭注册后如何开账号'的答案」（`server.py:137`）；
实现上"账号不存在则创建"（`server.py:145-149,160-166`）。
后果是：一旦关掉注册，团队每加一个人都要运维登服务器敲命令。这在小型 IT 运维团队里不可持续，
结果是运维受不了麻烦 → 把注册重新打开 → R-03 复发。

**三级委派的核心价值**：把"建号"这个动作下沉给真正知道该给谁开账号的人（团队管理员），
同时保留一个更上层、可审计的创建者（系统管理员）来兜住"团队管理员账号从哪来"。

## 3. 角色定义（CR 版）

团队内角色枚举**不新增第 4 个**：仍是 `owner / admin / member`（`js/config.js:76-80`）。
新增的是**实例级**身份 `is_system_admin`，它不进 `ROLES`，也不参与团队内判定。

| 角色键 / 身份 | 名称 | 代码判定 | 数据范围 | 与变更前的关系 |
|---|---|---|---|---|
| `users.is_system_admin = 1` | **系统管理员**（实例级，新增） | 新增列；建议以 `AuthzContext` 之外独立读出（**不进** `policy.py` 的团队判定） | 可建「团队管理员」账号；可改 AI 配置；**不因该身份获得任何团队数据的可见性** | 替代 `GTD_ADMIN_EMAILS`（`config.py:117-119`）作为权威来源 |
| `owner` | 团队所有者 | `is_owner()`（`policy.py:66-67`）、`is_admin()` 亦为真（`:60-61`） | 本团队全部数据 + 成员治理 | 不变 |
| `admin` | 团队管理员 | `is_admin()`，与 owner **合并**（`policy.py:60-61`） | 同上（代码未区分） | 不变 |
| — | **「团队管理员」= `owner` + `admin`** | 即 `ctx.is_admin(team_id)` | — | **本单口径**：沿用合并语义（最小改动）。若要收窄为"仅 owner"，见 **O-2** |
| `member` | 成员 | `is_member()`（`policy.py:57-58`） | 本团队数据；**无建号权** | 不变 |
| `status != 'active'` | 停用成员（团队级） | `load_context` 剔除（`policy.py:341-349`） | 视为非成员；仍可登录、仍可建自己的团队 | 不变；见 BR-035 |
| — | 未登录 | 无会话 | 仅 `app_logs` 可写（`policy.py:235-248`） | 不变 |

> **"三级委派链"与"四层身份"是同一件事的两种说法**（与 `06` §10.3.3 口径一致）：
> 三级 = "谁能产账号"的委派链（系统管理员 → 团队管理员 → 成员）；
> 四层身份 = 系统管理员（实例级）+ `owner` / `admin` / `member`（团队级）。
> 团队内的权限判定仍只有 `owner/admin/member` 三档 —— **不要**在 `ROLES` 里加 `system_admin`，
> 否则会污染所有按 `ROLES` 渲染的界面（`js/views.js:1298-1301,1747`）。

## 4. 权限矩阵（CR 版）

> 图例：**允许** = 现有代码已允许且本 CR 不改；**允许（新增）** = 本 CR 新增能力，当前代码做不到；
> **拒绝** = 明确不允许；**条件** = 允许但有附加约束。
> 每格格式：**结论** + 换行 + 「当前代码位置 / 需要新增什么」。凡标「需新增」的格子，其后端缺口汇总在 §4.2。
> **读矩阵前先看这一句**：**「系统管理员」不在 `ROLES` 枚举里**（`js/config.js:76-80` 只有 `owner/admin/member`），它是 `users.is_system_admin` 表达的**实例级身份**。去 `ROLES` 里找它找不到，不是漏了 —— 这是刻意的：一旦把它加进 `ROLES`，所有按 `ROLES` 渲染的界面（`js/views.js:1298-1301,1747`）都会把它当成团队角色。18 行细粒度判定以 `06` §10.3.3 为准，本表是产品语义版。

### 4.3 三条必须写清的边界

1. **系统管理员 ≠ 所有团队的管理员**（最小权限，建议采纳）
   他只负责"产账号 + 授团队管理员 + 改实例级配置"，**不改动任何团队的成员角色与业务数据**。
   依据：`is_admin()` 是按 `team_id` 判的（`policy.py:60-61`），系统管理员若不是该团队成员，天然为假；
   要保持这一点，**不能**在 `is_admin()` 里加 `or ctx.is_system_admin`。要不要给他"跨团队只读"能力 —— 本单建议**"否"**，且不列为待确认项；若日后需要，应另开 CR（它会实质改变"实例管理员无业务数据权"这条最小权限原则）。

2. **"团队管理员"的口径必须钉死**
   `policy.is_admin()` 把 `owner` 与 `admin` 合并（`policy.py:60-61`），前端也照抄了这个合并（`js/views.js:1258,1340`：
   `me.role === 'owner' || me.role === 'admin'`）。所以"团队管理员能建成员"这句话，
   **在代码上等价于 `admin` 也能建成员**。这不是笔误，是必须显式承认的语义。
   若产品意图是"只有所有者能建号"，则必须新增一个 **`is_owner` 谓词**（已存在，`policy.py:66-67`）并改前端判断 → **O-2 仍开放**（当前默认已按 `owner+admin` 落地：`06` §10.3.3 #11 取「T 的 owner 或 admin」；如需改判，代价 = 1 个谓词 + 2 处前端判断）。

3. **`owner` 只能由"自己建团队"产生**
   这样就不需要"系统管理员授 owner"的能力，也不会出现"某个团队没有 owner"的孤儿状态
   （`store.py:208-249` 保证建团队与登 owner 是同一事务，正是为了避免孤儿空间，见 `:214-218` 注释）。
   推论：**首任团队所有者的产生路径 = 系统管理员建一个（无团队归属的）账号 → 把账号交给团队负责人 → 他登录改密后自己建团队。**
   这条路径闭合，不需要任何"授 owner"的新能力。

## 10. 破坏性判定（对齐模板 §6 与总纲 §7.3）

| 项 | 结论 |
|---|---|
| 是否涉及表 / 字段 / 索引变更 | **是** |
| 变更类型 | **新增可空/带默认值列**（`is_system_admin INTEGER NOT NULL DEFAULT 0`、`must_change_password INTEGER NOT NULL DEFAULT 0`）；**无**删列/改名/改语义 |
| 能否直接零停机发 | **能（表结构侧只做加法）**：旧代码有 `SELECT *`（`h_login`，`pyapp/httpd.py:704-706`）与**不指定新列**的 `INSERT`（`pyapp/httpd.py:683-687`、`server.py:161-166`）。前者即使多拿到两列也只按列名取用（`row['id'/'email'/'name'/'password_hash']`），不消费新列；后者**必须**靠 `DEFAULT` 才能成功 —— 所以两列必须 `NOT NULL DEFAULT 0`，否则旧槽位写入直接失败 |
| 接口侧破坏性 | **是**：删除 2 个端点。前端与后端同镜像发布（静态文件随镜像），故内部无兼容问题；外部脚本/书签会收到 `404`，故 `friendlyError` 必须给可读文案（§17 D-2） |
| 迁移 SQL / 回滚 SQL / 验证 SQL | **必须**写入 `05`（本单不写 SQL，交 `data-modeler`）；验证 SQL 见 §8.2 AC-A-41/43 |

> **给 `data-modeler` 的硬约束（一句话）**：两列都必须 `NOT NULL DEFAULT 0`，且 `users` **不得**加入 `COLUMNS`（`db.py:303-378`），否则通用 CRUD 会打开篡改系统管理员身份的通道。

## 13. 回滚口径（产品侧怎么退，逐层写清）

> 前提事实：前端是静态文件、与后端**同镜像发布**（`Dockerfile` COPY 站点文件），所以"回滚镜像"天然保证前后端同版本；本项目已有零停机回滚（`deploy/rollback.sh`，`08:404`）。

| 层 | 触发条件 | 回滚动作 | 代价 / 副作用 |
|---|---|---|---|
| **L1 · 代码回滚**（首选） | 建号/闸门导致**无法登录或无法建号**，且 30 分钟内定位不到原因 | `sudo bash deploy/rollback.sh` 回上一版镜像 | 状态互换、零停机（`08:404`）；注册入口随旧版一起回来 → **R-03 短暂复发**，须同时 `GTD_ALLOW_SIGNUP=0` 或 Caddy 层拦 `/api/auth/register` 止血 |
| **L2 · 数据处置**（回滚后**必做**） | 上一版代码**不读** `must_change_password`，闸门失效 | ① 回滚后立即查询 `SELECT email FROM users WHERE must_change_password=1`；② 对每个账号执行 `python server.py --set-password <email>` 重置为已知强密码（并**重新**发放，走 BR-031 的交接纪律）；③ 或直接 `UPDATE users SET must_change_password=0`（**不推荐**，等于把临时密码变成长期密码） | 若跳过此步，会留下一批"用一次性密码长期使用"的账号 → 违反 BR-031，属**安全事故级**遗留 |
| **L3 · 产品语义回滚**（不推荐，需新开 CR） | 用户决定"退回自助注册" | **不通过运行时开关实现**，而是新开 `CR-2026-00X` 恢复端点与前端入口 | 打开 `allow_signup=1` 属于 R-03 复发（`08:169` 三条绕开路径），不可作为常规逃生通道 |

**明确的产品口径（三条）**

1. **不保留"注册开关"作为逃生通道**。逃生通道改为：运维 CLI `--create-admin`（建管理员）、`--set-password`（破窗重置）。二者都需要服务器权限，天然受限。
2. **回滚不删列**。`is_system_admin` / `must_change_password` 作为加法列永久保留；旧代码不读它们，不影响运行（这也让"回滚后再前滚"零成本）。
3. **回滚必须处置 L2**，且处置结果记入事故记录与 `09` 回滚检查单；未处置即视为回滚未完成。
