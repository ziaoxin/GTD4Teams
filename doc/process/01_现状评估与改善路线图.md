### 2.4 D — 刻意取舍，**明确不建议改**（误判会破坏产品语义）

| 取舍 | 原因 |
|---|---|
| `work_items` 更新策略不含 owner 限制 | 团队成员必须能推进别人建的工单，否则看板流转当场失效 |
| `contexts` 更新策略含 owner 限制 | 云版遗留形状，如实保留；差异本身就是要被记录的事实 |
| 被权限拦下返回空数组而非报错 | 前端 `assertAffected` 依赖「空数组 = 没改到」如实提示 |
| 客户端提交的 `owner_id` 一律丢弃 | 本地版没有 PG 的 `auth.uid()` 列默认值，这是等价防线 |
| `team_members.status != 'active'` 视为非成员 | 有意收紧，兑现「停用即失去访问权」 |
| `schema_present` 跳过 DDL / 会话刷新 300s 节流 / 每请求一连接 | 零停机三支撑，9 项实测成立；**问题只出在「commit 后重试」与「缺迁移层」，不是这套机制本身** |
| 无构建链、零第三方依赖、原生 ESM、全中文硬编码、不做乐观更新 | 均为硬约束或明确取舍；所有改善建议都不得引入框架/打包器/ORM/连接池 |

> ⚠️ 后端评审特别核实：SSE 直通分支**确实**被 `send_header` 覆盖的 `_responded` 正确保护（实测16，`httpd.py:122-131/397/404-407`），重试确实只发生在响应未开始写之前。**不要报「SSE 中途重复响应」**——真正的问题是 P0-3 与 P1 的错误分支。

## 3. 根因：三条断层 + 一个断言层次问题

| 断层 | 表现 | 本轮证据 |

| **需求 → 代码断链** | 无需求编号、无业务规则、无验收标准；功能清单散在 `config.js` 枚举、`views.js` 视图函数、README 描述里 | `02` 反推出 40 条 REQ / 25 条 BR / 21 条 EX，全部是**从代码倒推**，无一条来自访谈记录 |

### 真实部署才暴露的 4 个缺陷（已修）

这四条**静态审查与本机测试都发现不了**，只有真的 `docker build` + 起容器 + 跑一次发布才会现形。
它们同属一类：判定器自己被软化，或产物核对被静默架空 —— 比业务 bug 更危险。

| 缺陷 | 现象 | 修法 |
|---|---|---|
| `probe.sh` 毫秒计时不可移植 | `date '+%s%3N'` 在 Git Bash 得 3 位毫秒，GNU date 忽略宽度直接吐 9 位纳秒 → 单位差 1000 倍 → 打流循环**一次都不跑**，报"总请求 0 次"，`release.sh` 在**切流之后**才失败 | 改用 bash 5 内置 `EPOCHREALTIME`，保留 `date` 兜底 |
| `GTD_BUILD` 被 compose 用空值覆盖 | `environment: GTD_BUILD: "${GTD_BUILD:-}"` 展开成空串，覆盖掉镜像里烘焙的构建标识 → `/api/health` 回传 `dev` → 每次发布的构建标识核对必然失败 | 从 compose 删除该项，让镜像 `ENV` 生效 |
| 停旧槽位前没摘上游 | 旧槽位仍挂在上游列表里当兜底，容器 shutdown 期间被转进请求 → **实测丢 2 个 502**（一次 dial 卡 1.4 秒） | `caddyfile_generate` 增加 `solo` 模式：**先摘上游 → 等 3 秒 → 再停容器**；修复后 166 次请求零失败、最大空档 256 ms |

### 10.2 运维发现的三处「门禁自伤」缺陷（本轮最值得单独记）

主理人读脚本核实，**三条全部成立**。

| # | 缺陷 | 代码事实 | 后果 |
|---|---|---|---|
| F-01 | **`install.sh` 冒烟失败只 warning 不 die** | `deploy/install.sh:139-143`：`if ! bash smoke.sh ...; then warn '冒烟测试未通过…'; fi`，之后照常 `save_state` 并打印「部署完成」 | **首次部署最容易踩**：暴露面或接口有问题时，脚本仍宣告成功，运维以为已就绪 |
| F-02 | **`probe.sh` 空档超阈值只告警不失败** | `deploy/probe.sh:101-104`：`MAX_GAP_MS > 3000` 时打印「值得看一眼」后 `exit 0`，只有 `FAILED>0` 才 `exit 1` | 「有明显空档但没丢请求」的切换被判成功，与「零停机」的判定标准不一致 |
| F-03 | **`.env` 里两个变量根本不生效** | `lib.sh:288` 用 `${GTD_PROBE_PATH:-/api/health}`、`watchdog.sh:27` 用 `${GTD_WATCHDOG_FAILOVER:-0}`，读的是**进程环境**；脚本从不 `source .env`，compose 的 `environment` 段也没列这两个变量 | 写了配置以为生效，实际按默认值跑；`GTD_WATCHDOG_FAILOVER=1` 时自动降级并不会发生 |

**为什么单独记**：本次治理的命题是「把判定标准写下来并强制执行」，而这三条恰恰是**判定器自己被软化**。它们不是业务 bug，却会让所有门禁的结论失真。建议与第 1 期 P0 **同批**修复，成本极低：
1. `install.sh` 冒烟失败 → `die`（或提供 `--allow-smoke-fail` 显式开关，绝不默认放行）；
2. `probe.sh` 空档超阈值 → 硬门槛（默认 `exit 3`，与 `release.sh` 的探测失败码一致）；
3. `lib.sh` 增 `probe_path()` 走 `read_env`、`watchdog.sh` 同样处理，或把两变量补进 compose `environment`。
