> GTD4Teams 治理体系重建 · 主理人（交付总监）汇编
> 版本：v1.0 ｜ 日期：2026-11-13 ｜ 执行模式：**严格模式**
> 适用范围：本项目全部后续需求、变更、修复与发布；存量功能按第 8 节「反向补课」接入。

## 1. 结论先行

| 项 | 判断 |
|---|---|
| 当前判断 | 代码与工程质量**高于**过程文档质量。测试资产扎实（后端 49+9 项、前端 80/65/46 项、发布期 smoke+probe），部署方案已具备零停机能力与实测证据；但**需求、设计规格、阶段验收三类过程文档为零**，`docs/` 现有 4 份全是专题技术文档。 |
| 最大风险 | **不可追溯**：任何一个线上行为都无法回答「它对应哪条需求 / 哪条业务规则 / 哪条验收标准」。后果是改一处不敢判定影响面、回归范围靠记忆、需求变更无法评估、新人（或半年后的自己）接不住。 |
| 推荐动作 | 不是补一堆文档，而是**建立一条最短的追溯链 + 7 道门禁**，让每次改动都必须留下「需求编号 → 规则 → 实现 → 测试 → 验收 → 构建标识」这条链上的证据。 |
| 是否阻塞下一步 | **两类阻塞**：① **安全门禁 G5 阻塞上线** —— `08_安全审计与上线门禁.md` 判定「不满足放行」（G-01~G-11 中 7 项不通过、2 项部分、2 项未验证），`01` §2.1 的 8 个 P0 必须先修；② **首次上服务器前必跑** `python3 tests/test_zerodowntime.py`（开发机无 Docker，蓝绿前提在 Linux 上未实测）。文档编制本身不阻塞，可边跑边补。 |
| 复杂度原则 | 本项目是 **1 人 + AI 协作**的极小团队。流程按「轻量但不断链」设计：**每个阶段只留 1 份主文档 + 1 张验收单**，绝不引入需要专职角色才能维持的流程负担。 |

## 2. 为什么必须重整：三条断层

| 断层 | 证据 | 后果 |
|---|---|---|
| **需求 → 代码断链** | `docs/` 下无需求调研记录、无 PRD、无需求编号；功能清单只散落在 `js/config.js` 的状态枚举、`js/views.js` 的视图函数、`README.md` 的描述里 | 无法回答「为什么要做这个功能」「改它会影响哪些场景」；需求变更没有影响分析依据 |
| **决策 → 实现断链** | 多处关键设计取舍只写在**代码注释或 README 的一句话**里：`work_items` 更新策略不含 owner 限制（否则看板流转失效）、`contexts` 更新含 owner 限制（云版遗留形状，如实保留）、被拦下返回空数组而非报错、`owner_id` 一律丢弃、`team_members.status != 'active'` 视为非成员 | 后来者极易把这些「刻意保留」误判成 bug 并"顺手修好"，直接破坏产品语义；本项目历史上已因此丢过改动 |
| **测试 → 验收断链** | 测试数量与覆盖极扎实，但**没有测试计划、没有阶段验收标准、没有上线验收结论表**；`docs/零停机发布方案.md` §11 用散文形式列了「已验证/未验证」，不是可勾选、可签字的门禁 | 「全绿」只说明脚本跑了，不说明「达到了什么标准才算可以上线」；发布放行依赖个人判断，无法复核 |

**因此本次重整的目标不是"写文档"，是把上述三条链补上，并让它们成为每次改动的必经路径。**

## 3. 开发流程全景

```
        ┌─────────────────── 持续迭代环 ───────────────────┐
        │                                                  │
  [调研] → [需求] → [设计] → [开发] → [联调] → [测试] → [安全] → [发布] → [运维/反馈]
    │        │        │        │        │        │        │        │          │
   G0      G0       G1       G2       G3       G4       G5       G6        └─→ 回 [调研]
    │        │        │        │        │        │        │        │
  调研记录  PRD    FDS/TDS   自测单   联调单  测试报告  安全门禁  上线验收单
                    接口契约                              结论      发布结论表
                    数据模型
```

| 阶段 | 编号 | 主交付文档 | 门禁 | 放行权 |
|---:|---|---|---|---|
| 接单与定盘 | P0 | 项目上下文档案（本总纲第 4 节） | — | 主理人 |
| 需求调研 | P1 | `02_需求调研与PRD.md` | **G0** | 产品（用户） |
| 功能设计 / 技术设计 | P2 | `03_FDS` / `04_TDS` / `05_数据模型` / `06_接口契约` | **G1** | 架构（用户） |
| 开发 | P3 | 代码 + 版本串 + 自测记录 | **G2** | 开发自审 |
| 联调 | P4 | 联调验收单 | **G3** | 测试 |
| 测试 | P5 | `07_测试体系与各阶段验收标准.md` + 测试报告 | **G4** | 测试 |
| 安全 | P6 | `08_安全审计与上线门禁.md` + 放行结论 | **G5** | 安全（阻塞权） |
| 部署运维 | P7 | `09_运维手册与监控告警.md` + 发布结论表 | **G6** | 运维（用户） |
| 迭代 | P8 | 反馈归类 / 变更单 / 发布说明 | 回到 P0 | 主理人 |

> **门禁不是会议，是一张可勾选的表。** 每张验收单都由 `docs/process/templates/阶段验收单模板.md` 生成，判定标准必须能回答「通过 / 不通过」，不允许写「基本完成」「看起来没问题」。

## 4. 阶段门禁矩阵（G0 ~ G6）

| 门禁 | 准入条件 | 必交产出 | 判定标准（摘要，完整版见 `07`） | 证据形式 | 阻塞条件 |
|---|---|---|---|---|---|
| **G0** 需求 | 调研记录齐全（访谈对象、场景、原始诉求） | `02` 中的 REQ 清单 / 角色权限矩阵 / BR 规则表 / EX 异常表 / 验收标准 | 每条需求有唯一 ID、有可判定的验收标准、有优先级；权限矩阵与 `policy.py` 逐条对齐 | 文档 + `policy.py:行号` | 存在无验收标准的需求；权限矩阵与代码不一致且未标注为「刻意取舍」 |
| **G1** 设计 | G0 通过 | `03 FDS` + `04 TDS` + `05 数据模型` + `06 接口契约` | FDS 页面/流程与 TDS 模块/接口一一对应；数据表变更含迁移 SQL + 回滚 SQL + 兼容性分析；接口契约含错误码 | 四份文档 + 追溯矩阵 | 数据库变更缺回滚 SQL；接口契约与现有 `/api/*` 冲突未说明 |
| **G2** 开发 | G1 通过 | 代码 + 自测记录 + 版本串同步证据 | 后端/前端自测清单勾完；`APP_VERSION` + 所有 `?v=` + `index.html` + `pyapp/__init__.py` 四处同版本 | git diff + 自测单 | 版本串不同步；新增交互未注册 `dispatch`；新增视图未改三处 |
| **G3** 联调 | G2 通过 | 联调验收单 | 契约一致性、错误码映射、真实 `index.html` 启动、跨域与鉴权边界 | `app-boot-test.mjs` 输出 | 挂载点缺失 / 视图未分发 |
| **G4** 测试 | G3 通过 | 测试报告 + 回归结论 | L0 49 项、L0b 9 项、L1 80/65/46 项全绿；缺陷按阈值收敛；改动类型对应的回归范围已跑 | 命令输出 + EXIT 码 | 任一断言失败；回归范围漏跑 |
| **G5** 安全 | G4 通过 | `08` 安全放行结论 + 越权用例结果 | 阻塞项清零；越权用例全过；`GTD_TRUST_PROXY` 与槽位绑定配对正确；自助注册已收紧 | 审计表 + 用例输出 | 存在任一阻塞项 → **禁止进入部署** |
| **G6** 上线 | G5 放行 | 发布结论表 + 备份 + 回滚预案 | 构建标识核对一致、`smoke.sh` 全过、`probe.sh` 零失败且最大间隔 ≤ 3000ms、备份可还原、`rollback.sh` 可用 | 发布日志 + state.env + 探测报告 | 构建标识对不上；探测失败（release.sh 以 exit 3 结束） |

**放行权归属（极小团队适配）**：G0/G1/G6 由用户拍板；G2 开发自审；G3/G4 由测试角色（可由 AI 承担，但结论须落文档）；**G5 安全门禁拥有独立阻塞权，不能被"赶进度"覆盖**。

### 5.3 追溯链（每一次改动都必须能走通）

```
REQ-xxx ──► BR-xxx / EX-xxx ──► FDS 页面·流程 ──► TDS 模块 ──► 接口契约 /api/xxx
                                                    │
                                                    ▼
                                        数据模型（表·字段·迁移）
                                                    │
                                                    ▼
                              TC-xxx ──► ACC-Gn-xxx ──► GTD_BUILD ──► 线上验证
```

**最低要求**：一个需求至少要能追到「一条规则 + 一处实现 + 一条测试用例 + 一张验收单」。追不到的，视为该需求未完成。

## 6. 责任矩阵（RACI · 极小团队版）

| 活动 | 用户（产品/架构/运维终裁） | AI 协作体（各工程角色） | 自动化 |
|---|---|---|---|
| 需求调研与优先级 | **A/R** | C（整理、追问、成文） | — |
| PRD / FDS / TDS 撰写 | A（拍板） | **R** | 文档存在性断言 |
| 代码与测试实现 | A | **R** | 全套测试脚本 |
| 测试执行与报告 | I | **R** | `test_api.py` / `test_zerodowntime.py` / 三套 `.smoke` |
| 安全门禁 | A | **R**（独立阻塞权） | `smoke.sh` 鉴权与暴露面组 |
| 发布与回滚 | **A/R** | C（脚本已就绪） | `release.sh` / `rollback.sh` / `probe.sh` |
| 监控与故障 | **A/R** | C（SOP 文档） | `watchdog.sh` / healthcheck |

> R=执行、A=终责、C=协作、I=知会。**自动化能判定的一律交给脚本，不靠人记**：这正是本项目已有的强项，流程重整要放大它，而不是用文档替代它。

## 7. 变更管理与版本纪律

1. **任何改动先开 `CR-` 变更单**（模板见 `templates/需求变更单模板.md`），写清：影响的需求 ID、影响的文档、影响的代码模块、影响的测试、是否涉及数据库、是否涉及安全边界、回归范围。
2. **版本串四处同步是硬门禁**：前端 `APP_VERSION` + 所有 `?v=` + `index.html` 引用 + 服务端 `pyapp/__init__.py`。不同步 → G2 不通过（历史上因浏览器缓存出现过"展示版本与实际代码不一致"）。建议把这条做成一条自动化断言，纳入 L1。
3. **数据库变更遵守 expand/contract**：一次发布只做加法；破坏性变更拆三次发布，或 `release.sh --stop-first`（接受短暂停机）。每次变更必须含迁移 SQL + 回滚 SQL + 兼容性分析 + 验证 SQL（见 `05`）。
4. **`--import` 是 INSERT OR REPLACE，既不清空也不去重**：灾难恢复必须先删库文件再导入，否则残留行会与新数据叠加。
5. **发布产物以 `GTD_BUILD` 为准**：切流前必须核对新槽位 `/api/health` 回传的 build 与本次构建一致；端口通 ≠ 版本对。

## 8. 存量项目如何接入：反向补课 + 增量守规矩

项目已经在线上运行，不可能推倒重走 G0。接入方式分两步：

**第一步 · 反向补课（本次交付已完成）**
- 把「代码里已实现的功能」反推成需求基线，写进 `02` 的 PRD 主体，并给每条 REQ 补上验收标准；
- 把「只存在于代码注释 / README 一句话」的刻意取舍，显式写进 `04` TDS 与 `05` 数据模型，标注「刻意保留，改动前必须先读」；
- 把现有测试资产与发布脚本映射成 G0~G6 门禁，写进 `07`；
- 把散落在 `docs/零停机发布方案.md` §11 的「已验证/未验证」升级为可勾选的上线验收单。

**第二步 · 增量守规矩（从下一次改动开始）**
- 不要求补历史验收单；**任何新需求/新变更必须走完整追溯链**；
- 每次发布至少填三张验收单：`ACC-G4`（测试）、`ACC-G5`（安全）、`ACC-G6`（上线）；
- 每季度做一次文档与代码的**一致性巡检**，把漂移记进 `01`。

> 这样既不让历史包袱压垮当前工作，又能保证从某一刻起，过程资产开始单调增长。

## 10. 最小可行版 vs 后续增强版

| | 最小可行版（本期落地） | 后续增强版（按需） |
|---|---|---|
| 文档 | `00`~`09` + 4 个模板，全部可直接使用 | 需求追溯矩阵自动化生成、文档变更自动提醒 |
| 门禁 | G0~G6 手写验收单，每次发布至少填 G4/G5/G6 三张 | 把「文档存在性」「版本串四处同步」「构建标识核对」做成 CI/预检断言 |
| 测试 | 现有 49+9+80+65+46 项 + 五层发布门禁 | 补兼容矩阵、性能基线、真机浏览器冒烟（需评估零依赖约束下的可行性） |
| 成本 | 每次改动多花一次填表 | 一次性投入自动化，之后趋近于零 |

**不要跳到增强版。** 本项目当前最大缺口是「链断了」，不是「自动化不够」。
