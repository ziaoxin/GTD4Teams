| **G-24** | 遗留（**2026-11-15 新增**） | **第 0 期 Caddy 止血规则是否已随代码修复撤销**：`deploy/run/Caddyfile` 仍保留 `@phase0_export` 与 `@phase0_llm_write` 两条 `respond 404` | 通过/不通过 | ❌ **未撤销（功能被自己挡死）**<br>经 Caddy：系统管理员 `GET /api/export` → `404`、`POST /api/llm/config` → `404`；同一会话直连槽位 → `200` / `200`（代码侧已修好）<br>连带矛盾：`GET /api/llm/models` 经入口返回 `400 LLM_NOT_CONFIGURED`，文案引导用户「在『账号 → AI 设置』里填入服务地址与密钥」—— 而那个入口的 `POST` 正被 404 挡住，形成**死循环引导**<br>判定：**不阻塞安全**（偏严），但**阻塞该两项功能**，且掩盖了 G-05 的真实暴露面（防御方以为公网打不到 `POST /api/llm/config`，实际只要有回环直连就走得通） |

### 7.1 R-01（P0）专项处置：止血 / 修复 / 用例 / 应急

**① 立即止血（不改业务代码，Caddy 层）**
在 `deploy/Caddyfile.template` 的站点块内、`reverse_proxy` 之前加入（**改模板而非 `deploy/run/Caddyfile`** —— 后者由 `lib.sh:caddyfile_generate()` 每次发布整份覆盖）：

```caddyfile
	# 止血：公网入口屏蔽整库导出（后端 HTTP 面仍存在，属临时缓解而非修复）
	@blockExport path /api/export
	respond @blockExport 404
```

执行顺序：`caddyfile_generate()` 重新生成 → `caddy validate --config /etc/caddy/Caddyfile --adapter caddyfile` → `caddy reload`。判据：公网 `curl -s -o /dev/null -w '%{http_code}' https://<域名>/api/export` → `404`。
**注意**：槽位端口只绑 `127.0.0.1`，宿主机上仍可直连 `127.0.0.1:8788/api/export`；这只能挡公网入口，**不是修复**。

**② 修复方向**（择一，推荐 A）
- **A（最小可行，零表结构变更）**：把 `GET /api/export` 从 `ROUTES` 移除，备份只走 `server.py --export` + `deploy/backup.sh`。同时同步修改 `test_37_export_requires_login`（当前把「含 users 表」当期望断言）。
- **B**：保留 HTTP 导出但要求管理员身份 + 按 `load_context` 逐表过滤可见行 + 审计日志；**至少**必须从 HTTP 导出结果中移除 `settings` 与 `users.password_hash`，CLI `--export` 可保留完整备份能力。

**③ 越权测试用例**：§5.2 **T16**（对应后端实测15 / 本次 E3）。

**④ 若已被利用的应急流程**
1. **轮换 LLM Key**：在厂商控制台吊销旧密钥并生成新密钥 → 更新 `.env` / 界面 → **重启两个槽位**（因 R-19，界面删除不会清掉另一槽位的内存密钥，只改配置不够）。
2. **强制全员改密并清会话**：对每个账号执行 `docker compose exec app-blue python server.py --set-password <邮箱>`；该命令会 `DELETE FROM sessions WHERE user_id = ?`（`server.py:170`），使所有旧会话立即失效。
3. **轮换注册口令 / 关闭注册**：`.env` 设 `GTD_ALLOW_SIGNUP=0` 或换新的 `GTD_SIGNUP_CODE`，并重启槽位。
4. **取证**：`docker compose logs app-blue caddy 2>&1 | grep 'GET /api/export'` 查调用者 IP、时间、频次；Caddy `/data/access.log` 交叉核对；保留备份文件用于取证。
5. **复核**：按 §12 复验清单重跑 E3 等价探测，确认普通账号已无法取得 `users`/`settings`。

### 14.10 追加（2026-11-18）：访问日志 `ip` 字段的可信度与「运维日志界面」裁决

> 触发：前端工程师端木灵就「系统管理页是否加一张运行日志卡片」要一个安全结论。取证对象是**当前线上实例** `build 20261117-092021`（green 槽位 `127.0.0.1:8789`，经 Caddy `:8080`），与 §14 的 11-15 取证对象（`20261114-094117`）不同批次，故单列。

**先声明接口本身没问题**：`GET /api/logs`（`httpd.py:1223 h_access_logs`）实测门槛 —— 匿名 `401 UNAUTHENTICATED`、普通成员 `403 ADMIN_ONLY`、**团队管理员 `403 ADMIN_ONLY`**（实例级门槛正确地把团队 admin 挡在外面）。`_redact_path()` 已把 query 的**所有值**换成 `***`、控制字符压平、截断 200 字符；`uid` 在认证前为 JSON `null`；`/api/health` 被排除出日志（`ACCESS_LOG_EXCLUDED`），避免健康检查刷屏。

**但 `ip` 字段在任何一种部署形态下都不可作为「来源证据」**，两条独立原因（均已实测）：

| 编号 | 缺陷 | 严重级 | 实测证据 |
|---|---|---|---|
| **S-1** | **Caddy + 端口发布形态下，日志的 `ip` 恒为网桥网关，根本不是客户端 IP**。客户端真实地址在 `docker-proxy` 这一跳被改写为 `172.18.0.1`，Caddy 用 `header_up X-Forwarded-For {http.request.remote.host}` 把「它看到的 remote」写进 XFF，而它看到的也是网关 → 整条传递链丢失真实来源 | **P2 / 中危**（日志可信度，非漏洞） | 日志 120 条中 **118 条 `"ip":"172.18.0.1"`**；带 `X-Forwarded-For: 198.51.100.9` 经 Caddy 打 `/api/workspace` → 落盘为 `"ip":"172.18.0.1"`，`198.51.100.9` 在日志中**出现 0 次**（证明客户端伪造值被 Caddy 覆盖了，同时也证明真实值不是它） |
| **S-2** | **直连槽位形态下 `TRUST_PROXY=1` 使 `_client_ip()` 采信客户端自带的 XFF → 任意伪造值原样落盘，且登录限流键可被逐次更换** | **P3 / 低危**（当前槽位只绑 `127.0.0.1`，需本机访问） | 直连 `8789` 带 `X-Forwarded-For: 203.0.113.77` 打 `/api/workspace` → 落盘 `"ip":"203.0.113.77"`（日志中出现 2 次）；**12 次不同 XFF 的错误登录全 `401`、`429` 出现 0 次**；不带 XFF 的对照组第 11、12 次均 `429` → 伪造 XFF 完整绕过了按 IP 的限流键 |

**由此得出的裁决（给前端的口径）**：

- **不做「运行日志」浏览界面**（不做列表 / 模糊搜索 / 导出）。三条理由：① 唯一正当用途「用户报 500 → 用 `request_id` 查那一条」不需要浏览能力，而浏览带来的是新增的滥用面；② 界面要展示的 `ip` 字段在 S-1 下**恒为网关**、在 S-2 下**可被伪造**，以「证据」形态呈现会直接制造误判（冤枉好人或放过坏人），风险高于收益；③ 展示会把 PII 从「宿主机上 600 权限的文件」搬进「用 cookie 登录的浏览器会话」，风险面扩大而信息价值为零。
- **替代形态（同意做）**：只提供「按 `request_id` 精确查单条」的排障入口，不提供任何列表/枚举。字段白名单 = `ts`、`request_id`、`method`、`path`、`status`、`errcode`、`duration_ms`；**不显示 `ip`、不显示 `uid`**。
- 若主理人最终要求保留列表：必须同时满足 —— i) `ip` 仍不显示（掩码也不行，因为掩码后的值是错的值）；ii) 不暴露接口的 `q` 全文搜索参数（它可搜 `ip`/`uid`，等于变相浏览）；iii) 行数上限 50；iv) 不给「复制原始行/导出」；v) 查看行为写 `app_logs` 留痕（含查询条件，失败也记）；vi) 页面横幅声明「本页数据不可用于来源归因」；vii) 前端不落任何本地缓存。**`user-select: none` 不算控制项**（DevTools 可绕过），别把它写进安全说明。
- **S-1 该修，且不是前端的事**：要拿回真实客户端 IP，需在运维层解决端口发布方式（如关闭 userland proxy / 改用 iptables DNAT 保留源地址，或让 Caddy 以 `network_mode: host` 直连），或者在 Caddy 侧显式信任 docker 网关并让 `docker-proxy` 保留源 IP。修完 `ip` 才有展示与归因的意义。**在此之前，任何依赖日志 `ip` 的判断都不成立**，包括「谁在被限流」。

### 15.2 令牌泄露爆炸半径结论

**总公式（设计层）**：一个令牌能触及的数据集合 =
`load_context(token.user_id) 的 active 成员关系`（`04` :2031） ∩ `policy.can_select/can_insert/can_update/can_delete`（`policy.py:330-348`） ∩ `scopes 闸门`（`04` :1916） ∩ `API_ROUTES 暴露面`（`04` :1974-1989）。四个集合缺一不可，**任何一层单独失守都不等于全局失守**。

**关键前提（TDS 已如实承认，不是缺陷）**：令牌没有独立于账号的权限模型（`04` :1965）——`read` 令牌 = 看到该账号能看到的**全部**团队数据（含个人域）。所以爆炸半径的上界由"绑定账号的既有数据面权限"决定，不由令牌自己决定。缓解只有五条：默认只读、默认 90 天、每账号 10 个、独立撤销、`last_used_at` 可查（:1965）。这五条必须在实现中全部成立。

#### 15.2.1 `read` 令牌（默认档）

| 维度 | 结论与设计依据 |
|---|---|
| **能做** | `GET /v1/me`、`/v1/teams`、`/v1/work-items`（列表与单条）、`/v1/projects|areas|contexts|members`、`/v1/search?q=`、`/v1/openapi.json`（`04` :1977-1980、:1987-1989）。读到的行 = 该账号 `team_id IS NULL` 且 `owner_id==uid` 的个人项 + 所有 active 成员团队的行（`policy.py:83-89`、`policy.py:351-366`）。 |
| **不能做** | 任何写：`POST/PATCH/DELETE /v1/work-items*`（最小 scope `write:*`，`04` :1981-1986）；任何令牌管理：`/api/admin/api-tokens` 在浏览器面且机器接口不得签发新凭据（`04` :1991）；主入口特权端点 `/api/export`、`/api/llm/config`（主入口不认 Bearer，`04` :730 边界 2）；`users`/`settings`/`api_tokens`/`api_idempotency` 表（不进 `COLUMNS`→不进 `WRITABLE_TABLES`，`db.py:408`；令牌表登记纪律 `04` :1899）。 |
| **越权是否被挡住** | ✅ **设计上挡得住**：读路径 `store.select_table` 逐行过 `can_select`（`04` :2031），单条 GET 先判可见性再返回、不可见一律 404（`04` :2040-2041、:2047）。**但这是设计约束，实现后需验**——最易漏在 handler 里自己拼 `SELECT ... WHERE id=?` 绕过 `store.select_table`，或单条 GET 忘了过 `can_select` 而直接回 200（详见 §15.3①）。 |

#### 15.2.2 `write:edit` 令牌

| 维度 | 结论与设计依据 |
|---|---|
| **能做** | 在 `read` 之上增加 `POST /v1/work-items`、`PATCH /v1/work-items/{id}`、`POST .../complete`、`POST .../restore`（`04` :1981-1983、:1985）；MCP 侧 `update/complete/restore_work_item`（:2193-2195）。写仍受 `can_insert`/`can_update` 逐行约束：个人域只本人、团队域只 active 成员（`policy.py:110-122`、:270-279）；`owner_id` 由服务端注入，客户端值被 `split_payload` 丢弃（`policy.py:15`、:110-122；`04` :2033）。 |
| **不能做** | **不能归档**（`write:archive`）、**不能删除**（`write:delete`）——三类 scope 独立（`04` :2201-2202）；MCP 删除还要 `confirm: true`（:2197）；不能改 `version`/`archived_at`（设计登记为 `lock`，`04` :2075、:2087）；不能改 `team_members`/`users`/`settings`（无对应 `API_ROUTES`，且策略护栏 `policy.py:157-221`）；不能续期自己（令牌管理只在浏览器面，:1991）。 |

#### 15.2.3 `write:delete` 令牌（最高档）

| 维度 | 结论与设计依据 |
|---|---|
| **能做** | 在 `write:edit` 之上增加 `DELETE /v1/work-items/{id}`（`04` :1986）与 `delete_work_item`（:2197）。语义是**软删除**：写 `archived_at=now` + `status='archived'`，行仍在库里（`04` :1820、:2205、:2299）。`DELETE` 要求 `can_update` **且** `can_delete` 都为真（:1986）；`work_items` 的 delete 策略是 `_personal_or_member`（`policy.py:278`）。 |
| **不能做** | **不能物理删除**（硬约束 6，`04` :1820；"没有物理删除"，:2205）；不能删除 `users`/`settings`/`api_tokens`/备份/日志（`app_logs` 策略 update/delete 恒 `deny`，`policy.py:251-264`；`api_tokens` 不在 `WRITABLE_TABLES`）；不能撤销/签发任何令牌（:1991）；不能夺团队所有权（`team_members` 三重护栏 `policy.py:170-172`、:190-196、:203-204、:215-219）。 |
| **越权是否被挡住** | ✅ **设计上挡得住，但爆炸半径是三档里最大的**：泄漏后可把该账号可见范围内**全部**工单软删（等价于批量归档），且没有物理恢复路径以外的回滚。因此 `delete_work_item` 的 `confirm: true`（:2197）与审计同事务（`04` :2142-2147）不是可选项。**设计约束，实现后需验**——最易漏在"软删除"被实现成真的 `DELETE FROM work_items`、或审计漏写导致无法追责。 |

> **对"一个泄漏令牌到底能干什么"的一句话答法**：`read` 泄漏 = 该账号可见数据全泄（含个人域）；`write:edit` 泄漏 = 该账号可写工单可被批量改标题/状态；`write:delete` 泄漏 = 该账号可写工单可被批量软删。三者都**碰不到**账号体系、团队所有权、LLM 密钥、令牌自身、备份与其他账号的数据——这是 `policy` 逐行过滤 + `API_ROUTES` 窄暴露面共同收敛的结果，不是靠令牌自己实现的。

### 15.3 四个专项问答（每题给"设计能否防住 + 实现最易漏在哪 + 判据"）

#### ① 令牌能否越权读他人团队数据（TC-INT-05）

- **设计是否能防住**：✅ 能，但要满足三件事同时成立。`_api_identity` 把令牌解析为 `user.id`（`04` :1936、:1939）→ `load_context(conn, user['id'])` 构造上下文（:2031）→ `store.select_table` 逐行过 `can_select`（:2031）。`load_context` 只纳入 `status=='active'` 的成员行（`policy.py:351-366`，判定在 :362-365），停用的成员立即失去可见性；`work_items.select = _personal_or_member`（`policy.py:271`、:83-89）使 A 的令牌看不到 B 的团队行、也看不到 B 的 `team_id IS NULL` 个人项。单条 GET 不可见时回 **404 而非 403**（`04` :2040-2041、:2047），不泄露存在性。
- **实现最易漏在哪**：(a) handler 内直接 `conn.execute('SELECT ... FROM work_items WHERE id=?')`，跳过 `store.select_table` 与 `can_select`——这是 `04` :2031「不写 SQL」明令禁止的；(b) 单条 GET 用 `403` 或返回空对象代替 404，形成存在性预言机；(c) `ctx` 不是由令牌 `user.id` 构造，而是复用了主入口会话的 `self._uid`（`04` :729 边界 1 禁止把 Cookie 校验套到 Bearer）；(d) 把 `status` 过滤漏掉，导致被停用成员凭旧令牌仍可见。
- **判据**：`TC-SEC-INT-05` 必须实测「A 的 read 令牌列表不含 B 团队行 + 单条 GET B 的 id → 404」；静态 grep 集成域 handler 无裸 `SELECT`/`UPDATE` 拼 SQL。**【设计约束，实现后需验】**

#### ② 令牌能否绕过 `must_change_password` 闸门（TC-INT-03）

- **设计是否能防住**：✅ 能，且 TDS 已把它列为"不许绕过"的硬点。`04` §4.8 表格最后一行与边界 3（:725、:731）写明令牌受闸门约束；`_api_identity` 设计稿在 SELECT 里取 `u.must_change_password`（:1931）、在构造 user 后立刻检查并抛 `403 PASSWORD_CHANGE_REQUIRED`（:1937-1938），要点表第 2 条重申（:1955）。主入口的对应实现是 `httpd.py:584-586`（`_require_user` 内）。
- **实现最易漏在哪**：(a) 移植 `_api_identity` 时只复制了"查令牌 + 构造 user"，漏掉闸门那 3 行——令牌于是成为 §4.7 闸门的免费旁路；(b) 把主入口豁免逻辑 `_password_change_exempt()`（`httpd.py:589`）连白名单一起带进集成域，使某些集成端点在改密阶段仍可用；(c) 判定顺序错——应先闸门后 scope，否则 `must_change_password=1` 的只读令牌发写请求会得到 `INSUFFICIENT_SCOPE` 而不是 `PASSWORD_CHANGE_REQUIRED`（优先级口径见 `httpd.py:582-583`）；(d) 令牌管理端点（浏览器面）允许为"处于改密阶段"的账号代建写令牌，间接绕过。
- **判据**：`TC-SEC-INT-03` 分别对 GET 与写请求打 `must_change_password=1` 账号的令牌，期望统一 `403 PASSWORD_CHANGE_REQUIRED` 且无业务副作用。**【设计约束，实现后需验】**

#### ③ 令牌能否从 localhost HTTP 被第三方网页 CSRF 利用（Origin 一律拒绝是否足够）

- **设计是否能防住**：✅ 设计层面充分，但**"Origin 一律拒绝"是纵深防御，不是唯一防线**。三层分别是：① 只绑 `127.0.0.1` 且没有配置项能改（`04` :1816、:2209）——公网网页打不到；② 令牌在 `Authorization: Bearer` 头里，浏览器跨域脚本**不能自动携带**，且自定义头触发预检，而集成域不开 CORS（`04` :2209）、预检由主入口 `OPTIONS→405` 兜底（既有实测 E10）；③ 任何带 `Origin` 的请求一律 403，注意是"出现即拒"而非"与 Host 相同即放行"（:2012、:2015-2017、:2209），这比主入口"只比 netloc、无 Origin 就 return"的实现（`httpd.py:431-446`）更严。
- **设计是否足够**：足够的判断前提是"网页永远拿不到令牌"。因此真正的 capability 控制是"Bearer 不在 Cookie、不进 localStorage 的页面、不进 URL query"；Origin 拒绝负责挡住"用户浏览器被诱导发出请求"这一类。**残余风险**：DNS rebinding 让 `evil.test` 解析到 `127.0.0.1` 时，请求确实来自本机——此时唯一有效的仍是"攻击页面没有令牌"；若有人图方便把令牌塞进 query 或 Cookie，两层防线会同时失效。
- **实现最易漏在哪**：(a) 直接复用主入口 `_check_origin`（`httpd.py:431-446`）——它缺 Origin 时 `return`（:434-435）、只比 netloc（:443-446），语义从"出现即拒"退化为"相同才拒"，`Origin: null` 与同源伪装都可能被放过；(b) 只对写方法查 Origin、漏掉读方法（设计说"任何带 Origin 的请求"，:2012）；(c) 给集成域加 `Access-Control-Allow-Origin`（哪怕只是调试残留）；(d) 把令牌写进 URL 或 Cookie，或被日志 `path`/幂等 `response` 带走。
- **判据**：`TC-SEC-INT-23` 打 `Origin: https://evil.test`、`Origin: http://127.0.0.1:8790`、`Origin: null` 三种都必须 403，同时不带 Origin 的脚本请求必须可用；响应无 ACAO 头；`TC-SEC-INT-14`（`TC-INT-14`）带 `gtd_session` 无 Bearer → 401。**【设计约束，实现后需验】**

#### ④ 令牌明文是否会进日志/备份（TDS 说"不进 BACKUP_TABLES、不进 `_log_access`"）

- **设计是否能防住**：✅ 能，四道封锁都有明确落点。① **存储**：只存 `sha256(整个令牌)`，复用 `security.token_fingerprint()`（`pyapp/security.py:133-135`；`04` :1867）；`api_tokens` 不进 `BACKUP_TABLES`（`04` :1902、:2248；当前 `store.py:803` 的 `BACKUP_TABLES = COLUMNS.keys() + ('users','settings')` 不含该表），所以连哈希都不备份。② **创建响应**：明文只出现一次 + `Cache-Control: no-store`（:1868、:1913），且令牌管理在浏览器面（:1991）。③ **访问日志**：9 字段固定为 `ts/request_id/uid/ip/method/path/status/errcode/duration_ms`（`httpd.py:345-355`），**根本没有 header 字段**；`_redact_path` 把 query 所有值打码并压平控制字符（`httpd.py:261-294`）；设计只允许追加一个 `token_id` 整数（`04` :1856、:1940），不是令牌本体——`TC-INT-11`（:2297）。④ **审计**：`app_logs.detail` 明令"绝不写入令牌明文、`Authorization` 头、任何请求头、私钥、口令"（:2141），只写 `tokenId`/`tokenLabel`/`scopesUsed` 等（:2140）——`TC-INT-10`（:2296）。
- **必须点破的耦合**：`app_logs` **在** `COLUMNS`（`pyapp/db.py:400`）因此**在** `BACKUP_TABLES`（`store.py:803`）。所以"令牌明文不进备份"并非独立成立——**只要 `app_logs.detail` 里写了明文，备份导出就会把它带走**。这条依赖关系必须在实现时当作硬纪律，并且实测要把备份导出纳入 grep 范围（`TC-SEC-INT-22`）。
- **实现最易漏在哪**：(a) 调试时 `print(self.headers)` 或把请求头塞进审计 `detail`；(b) `ApiError` 文案回显令牌（如 `"invalid token gtd_pat_xxx"`）——既进响应又进 `errcode`/stderr；(c) `token_id` 字段误填成 `token` 字符串而非 `row['token_id']`；(d) 令牌创建接口被误加 `Idempotency-Key`，使含明文的响应体落进 `api_idempotency.response`（`04` :2100）；(e) 用 `str(error)` 记录鉴权失败而错误对象携带了令牌。
- **判据**：`TC-SEC-INT-10/11/22` 在"创建令牌 + 用令牌写一次 + 做一次备份导出"后，对 `app_logs` 全表、访问日志 `app.jsonl`、备份 JSON 三处 `grep -cF 'gtd_pat_'` 要求全为 0，且访问日志 `token_id` 存在、`uid` 等于令牌所属账号。**【设计约束，实现后需验】**
