### 0.2 实现状态四档定义（本文自定，用于消除"基本完成"这类模糊判断）

| 状态 | 判定规则 |
|---|---|
| `✅ 已实现并验证` | 代码存在 **且** 至少一条自动化测试**直接**断言该 REQ 的核心行为，且本轮实跑通过 |

> ⚠️ 与 ✅ 的区别**不是**"做得差不差"，而是"有没有断言守住"。这正是 02 §2.2 GAP-17 的教训：46 项集成测试全绿，仍漏掉了「点修改密码没反应」。

| 能力 | ① `release.sh` 用 `flock -n` 抢 `deploy/run/release.lock`，抢不到直接报"另一发布正在进行"并退出（不硬上）；② 切流时用 `install`/`cp` 原地写而非 `mv` 换文件，避免破 inode 导致 Caddy 静默不重载（原缺陷：`mv` 后 Caddy 仍持有旧 inode，看起来切流成功实际没生效） |
| 代码证据 | `deploy/release.sh`（`flock` 出现在发布入口，注释"与 watchdog.sh 同一套做法，拿不到锁就直说，不要硬上"）；`deploy/watchdog.sh`（同一把锁范式）；`deploy/Caddyfile.template` |
| 测试证据 | **无自动化**（脚本级，需真实发布环境）。`test_zerodowntime.py` 的 `test_06` / `test_07` 只验证**冒烟脚本对正确/错误构建的放行与拦截**，不验证锁与 inode |
| 基线缺口 | 02 仅在 §7.6「失败处理方案」把 `release.sh` 当既有工具引用（"`release.sh` 以 exit 3 结束"、"不绿用 `release.sh --stop-first`"），**无需求条目**。inode 修复则完全不提 |
| 处置建议 | **已由 `02` v1.3 立为 REQ-058**（发布互斥锁 + 切流原子性），配 1 条 BR（"同一时刻只允许一个发布，抢不到锁必须失败而非排队/硬上"）+ 1 条 EX（并发发布 / 切流后 Caddy 未重载）+ AC-R（可在 `AC-R-06` 现状条目上追加两个断言：并发起两个 `release.sh` 第二个必须非 0 退出；切流后 `curl` 新槽位必须返回新 `build`）。**归 `ops-engineer`；这类"脚本级缺陷修复"最容易被当成实现细节漏掉，但它直接决定"发布是否可信"** |

### 5.4 三项的共同处置建议
